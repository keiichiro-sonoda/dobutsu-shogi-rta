# どうぶつしょうぎ完全解析 RTA

**2021年に自分が書いた完全解析プログラムを、同じ答えを出したまま、どこまで速くできるか。**

初期盤面から到達可能な全局面を洗い出し、後退解析で全局面の勝敗と手数を確定させるまでの所要時間を計測する。
出発点は当時のコードをそのまま走らせたタイムで、そこから1手ずつ改善していく。

新規性は無い。どうぶつしょうぎの完全解析は 2009年に田中哲朗により達成済みで、
到達可能局面数 **246,803,167** も既知の値である。
このリポジトリが記録するのは**同じ答えに辿り着くまでの時間**だけ。

---

## 計測する区間

```
初期盤面 (0x000a003c914b002)
   ↓  前向き全探索 … 到達可能局面をすべて列挙
   ↓  後退解析     … 全局面の勝敗と手数を確定
終了 (新たな負け局面が1つも見つからなくなった時点)
```

プロセスの起動から終了まで。ビルド時間は含まない。

## レギュレーション

| | |
|---|---|
| **計測機** | 固定（下記「計測環境」）。変更したら記録はリセットして別表にする |
| **開始状態** | 初期盤面のみ。事前計算したテーブル・定跡・中間成果物の読み込みは禁止 |
| **成果物** | 到達可能な全 246,803,167 局面について勝敗と手数が確定していること。総数や分布だけを出すのは不可 |
| **保存形式** | 自由。pickle でも生バイナリでもメモリ上の配列でもよい |
| **検証** | 下記オラクルとの完全一致が必須。不一致の記録は無効 |
| **カテゴリ** | `1スレッド` と `全コア` を分ける。物量とアルゴリズムを混ぜない |
| **ウォームキャッシュ** | 可。ただし計測前に何を温めたかを記録する |

保存形式を自由にしているのは、**そこが一番大きな改善点だから**。
形式を固定すると「ディスクを使うのをやめる」という最大の改善が禁止されてしまう。
代わりに、下のオラクルで答えを固定する。


### 成果物どうしの照合

オラクルが見ているのは手数別の**局面数**だけで、「どの局面がどの手数か」までは見ていない。
実装の集計経路を書き換えたときは、`dat/` そのものを突き合わせる。

```bash
python3 tools/fingerprint_dat.py <dat>          # 指紋を出す
python3 tools/fingerprint_dat.py <datA> <datB>  # 2つを照合
```

指紋は深さごとの `(件数, 総和 mod 2^64, XOR)`。3つとも要素の順序に依存しないので、
チャンクの分かれ方が違っても一致する（同じ答えでも `win003te_000` と `_001` の分割は
集合の pop 順で変わるため、バイト比較では判定できない）。
ただし異なる集合でも同じ指紋になる場合があり、**PASS は集合の完全一致の証明ではない**。
例えば `{1, 6}` と `{2, 5}` はどちらも `(2, 7, 7)` になる。
記録 #2 〜 #5 の `fingerprint.txt` もこの指紋の一致を記録したもの。
完走とオラクル一致を別途確認した成果物に対する補助的な検査として使う。

## ベースラインの素性

`baseline/` は2021年11月に書いた実装を**一切変更せずに**置いたもの。
詳細は [`baseline/README.md`](baseline/README.md)。

構成は Python + C の共有ライブラリを ctypes で叩くハイブリッド。
Python が集合演算とファイル分割を担当し、C が指し手生成と鏡面正規化を担当する。

遅い理由は分かっている。**当時のマシンの制約がそのまま設計に焼き付いている。**

- **全局面をディスクに置いている。** 局面を 5,000,000 個ずつ pickle に分割して書き出し、
  ラウンドごとに読み直す。最終成果物だけで約 4.5GB
- **後退解析の中で前向きに指し手を生成し直している。** 本来の後退解析は前任局面を生成して
  カウンタを減らせば各辺を一度しか通らないが、この実装は毎ラウンド未知局面から
  次局面を再生成して集合に含まれるか調べる。87ラウンドぶん繰り返す
- **局面ごとに ctypes 越しに C を呼ぶ。** 呼び出し回数は10億回オーダーになる
- **C側に最適化フラグが無い。** `gcc animal_shogi.c -o animal_shogi.so -Wall -fPIC -shared`（＝`-O0`）

## 改善の梯子（予定）

上から順に効くと見ている。実際にやってみて外れたらそれも記録する。

1. `-O3 -march=native` を付ける（ビルドフラグだけ）
2. pickle をやめて生バイナリ（`array('Q')` / `mmap`）にする
3. ファイル分割をやめて全部オンメモリに載せる
4. ハッシュ集合をC側へ移し、Pythonは司令塔だけにする ← **記録 #8**（⚠️ 効いたのは「呼び出し回数を削る」ではなく**照合そのものをC側で終わらせる**ことだった）
5. 60bit エンコードを密なインデックスへ写して配列引きにする ← **記録 #6 で 6 とまとめて実施**
6. **前向き生成 → 前任生成＋カウンタ方式**（アルゴリズムの本丸）← **記録 #6**
7. C / Rust へ全面移行
8. マルチスレッド化（`全コア` カテゴリ）
9. ビットボード・SIMD

### 記録 #1 で分かったこと

**最初の大きな一手は、この梯子に載っていなかった。** ctypes ラッパーの1行で 1.36×。

`nextBoardInvNormalWrap` が `list(nba)[:nbn]` と書いていた。`nba` は長さ48固定の
ctypes 配列なので、これは `nbn` に関係なく毎回48個の PyLong を作ってから捨てている。
ctypes 配列はスライスが直接リストを返すので `nba[:nbn]` で足りる。

- 1局面あたり **7.01µs → 1.51µs**（記載値の比で約4.64×）。`-O0`・分岐9〜11の実局面 117,649 件で実測。
  原文のコストは分岐数に対してほぼ平坦（n=4 で 6.76µs、n=21 で 6.91µs）で、
  常に48個ぶん払っている。実際の平均分岐は約9.8手なので5分の1しか使っていなかった
- **ラッパー変更の効果と整合する傾向が出た。** 指し手を再生成するフェーズが大きく速くなり
  （N手勝ちの確定 1.67× / N手負けの確定 2.03×）、再生成しない `周辺勝ち盤面の更新` は
  **1.02× とほぼ同じ**。ただし各1回の計測なので、実行間のばらつきは未評価
- **1段目の `-O3 -march=native` はマイクロベンチマークで 1.06×**（同条件で実測）。
  完全解析全体の高速化率はまだ計測していない
- **4段目「FFI呼び出し回数を削る」も狙いがずれている。** 呼び出し自体は 1.01µs で安い。
  高いのは結果を Python オブジェクトへ変換する部分だった

事前予想は 2.1× だったが、外れた。後退解析の約80%がこの経路だと見積もったのに対し、
実際は約38%。`周辺勝ち盤面の更新` が baseline 後退解析の 2:07:47 を占めていて、
そこはこの修正で直接短縮できる処理ではなかった。

**次の標的は `周辺勝ち盤面の更新`。** 記録 #1 では 2:05:41 で、全体 6:33:28 の32%を占める単独最大。

### 記録 #2 で分かったこと

**2段目「pickle をやめる」より先に、中間ファイルの存在理由そのものが消えた。** 2.67×。

`unknown{i}_next.pickle` と `unknown{i}_next_win.pickle` は、
「勝ち集合全体をメモリに置けないから、いま必要な部分だけ切り出したキャッシュ」だった。
**2021年当時のマシン制約の産物**で、62GB の現計測機では前提が成立していない。
勝ち盤面 196,773,087 個を1つの集合としてメモリに常駐させ、両方を廃止した。

等価性は次の観察で言える。`_next_i` は「チャンク i に残る未知盤面の後続の和集合」なので、
`searchLoseBoard` が調べる後続 `nb` は必ず `_next_i` の要素。したがって
`nb ∈ _next_win_i ⟺ nb ∈ 全勝ち盤面` で、全体集合に置き換えても答えは変わらない。

|---|---|---|---|
| N手勝ちの確定 | 1:41:23 | 0:49:01 | **2.07×** |
| N手負けの確定 | 1:00:05 | 0:53:55 | 1.11× |
| 周辺勝ち盤面の更新 | 2:05:41 | — | **消滅** |
| 勝ち集合の初期ロード | — | 0:01:21 | 新規 |

記録 #2 の上表の合計は 1:44:17。全探索後の経過時間 1:46:42 との差 0:02:25 は、
上表に含めていない整理処理等の時間を含む。

- **深さが浅いほど効いた**（深さ1〜8 で 3.02×、深さ10〜16 で 2.21×）。
  未知盤面が多い序盤ほど `_next` の構築量が大きいため
- **懸念していた所属判定の悪化は起きなかった。** 196,773,087 個の集合を引いても
  負け確定フェーズは 1.11× で**速くなっている**。`_next_win` のロードが消えた分が上回った
- ピーク RSS 4.72 → **18.35 GiB**。メジャーフォルト 0・スワップ 0 で、
  巨大な常駐集合でもスワップを踏んでいない
- ディスク書き込みは 102.4 GiB → **26.8 GiB**（74%減）

事前予測は 40.8〜43.0% の削減だったが、**実際は 49.1%** で外した。
深さ10〜16 の実測比（2.21×）を全体へ外挿したのが原因で、
実際の重心である序盤（深さ1〜8 で 3.02×）を過小に見ていた。

**次の標的は `N手負けの確定` (0:53:55)。** 全体 3:20:14 の27%で単独最大になった。
全探索 (1:33:32) が47%を占めるので、そちらも無視できない。

### 記録 #3 で分かったこと

**全探索の重複排除も同じ形の化石だった。** 全探索だけで 2.31×、全体で 3.62×。

`searchNext()` は未探索チャンク1個ごとに呼ばれ、毎回 `unknown{i}` / `win001te_{i}` /
`lose000te_{i}` / 他の `unexplored{i}` を**全部読み直して**重複排除していた。
この4系統は「発見済み盤面」の分割なので、順に引くことと和集合を1回引くことは同値になる。
常駐集合1つに置き換えた。**読み直しの累計は 9,886,637,087 局面**だった
（各ラウンドの読み直し量は、ちょうどその時点の発見済み盤面数に等しい）。

| 区分 | #2 | #3 | |
|---|---|---|---|
| 全探索 | 1:33:32 | **0:40:30** | **2.31×** |
| 勝ち集合の初期ロード | 0:01:21 | 0:01:22 | — |
| N手勝ちの確定 | 0:49:01 | 0:49:14 | — |
| N手負けの確定 | 0:53:55 | 0:54:12 | — |

事前に登録した予測は削減 **18.3〜21.0%**、タイムにして **2:38:11〜2:43:35**。
完走前の門番で **18.3〜19.3%**、**2:41:35〜2:43:35** に絞り込んだ。
**実際は 26.2%（2:27:46）で、どちらも外した。今回は速すぎる方へ外れている。**

**原因は「単価は一定」という暗黙の仮定。** 読み直しの単価を、末尾ラウンドから測って
248 ns/局面と見積もった。末尾は探索対象が数百局面しか残っていないので、
かかった時間がほぼ読み直しだけになる——きれいな測り方に見えた。
ところが CPython の `set_difference_update_internal` には
**「相手が自分の8倍より大きければ、相手を先に intersection に置き換える」**最適化がある。

- **末尾ラウンド**: `new` が数百件、チャンクが 500万件 → 8倍差がつき、**`new` 側だけを走査**。
  つまり実質 unpickle のコストだけ。これが 248 ns
- **中盤のラウンド**: `new` が1000万件、チャンクが 500万件 → **8倍差がつかず、500万件側を走査**。
  unpickle に加えて、過去の1件ごとに `new` への問い合わせが乗る

**「一番きれいに測れる区間」が、一番安い区間だった。** 実際の平均単価は約 340 ns。
最小二乗で全ラウンドから出した 422 ns という推定もあったが、
末尾ラウンドの実測（68秒）を 126秒 と過大に予測するので棄却していた。
正しい結論は「回帰が間違っている」ではなく **「単価が一定ではない」** だった。

これは記録 #2 と**同じ型の失敗**である。#2 は「深さ10〜16 の比を全体に外挿した」、
#3 は「末尾ラウンドの単価を全ラウンドに外挿した」。
どちらも、測りやすい区間が代表的でなかった。

- **後退解析は対照群として機能した。** 1:44:17 → 1:44:48（**+0.5%**）。
  全探索しか触っていないことと、計測機に前回と比べて大きな変動が無かったことを同時に示唆する。
  ただし各1回の計測なので、実行間のばらつきは未評価
- **ピーク RSS は増えなかった。** 18.35 GiB → **18.35 GiB**（19,238,276 → 19,236,960 KiB）。
  +1〜4 GiB と予測したが外れ。全探索の常駐集合 246,803,167 件は 16.2 GiB で、
  後退解析の勝ち集合（196,773,087 件）の山 18.35 GiB を超えなかった。
  メジャーフォルト 0・スワップ 0
- **総未知/総勝ち/総負けは完全一致**（99485568 / 140298614 / 7018985）。
  読み直しループの副産物だった総数をカウンタに置き換えたので、そのまま自己検査になった
- **チャンクの分かれ方はラウンド17 から変わった。** 予測どおり分岐したが、
  境目の予測（ラウンド11）は外れ。答えは変わらないので `fingerprint_dat.py` で照合した
- **完走前の門番は −14.9%（ラウンド24 時点）** で、これも過小だった。
  読み直しは発見済み集合に比例して増えるので、**序盤は常駐方式のほうが遅い**
  （交差点はラウンド15）。浅いラウンドで足切りする門は、この改善を殺していた

**次の標的は後退解析。** 全体 2:27:46 のうち 1:44:48 で 71% を占める。
`searchWinBoard` / `searchLoseBoard` は毎ラウンド全 `unknown{i}` を読み直して指し手を
再生成しており、**局面の訪問回数は 1,479,788,351 回**（全探索の 246,803,167 局面に対して6倍）。
梯子の6段目「前任生成＋カウンタ方式」は、各辺を一度しか通らないことでここを直す。

## 実行方法

Linux 前提（`u_long` と `.so` に依存）。Python 3 と gcc があれば動く。

```bash
tools/run.sh                    # baseline/ を計測
tools/run.sh impl/01_wrapper    # 改善実装を計測
tools/run.sh impl/01_wrapper w1 # ラベルだけ変える
make measure IMPL=impl/01_wrapper LABEL=w1 # make 経由でも同じ指定
```

第1引数が**計測する実装ディレクトリ**。無指定なら `baseline/`。
`runs/<日時>_<ラベル>/` を作り、そこへ実装ディレクトリの中身を丸ごとコピーしてから、
ビルド・実行・検証までをその中で完結させる。実装のソースは書き換えない
（`./dat/` と `./kaiseki_log/` をカレント相対で使う実装があるので、作業ディレクトリを切って `cd` している）。

改善実装は `impl/<番号>_<名前>/` に置く。記録表の `#` 列と番号を揃える。

ビルドと実行のコマンドは、実装ディレクトリに `impl.env` を置けば差し替えられる。

```bash
# impl/07_rust/impl.env の例
BUILD_CMD="cargo build --release"
RUN_CMD="./target/release/solver"
MAIN_LOG="kaiseki_log/main.log"
```

`impl.env` が無ければベースラインと同じ既定値
（`make animal_shogi.so` / `python3 ./animal_shogi.py` / `kaiseki_log/kaizenkaiseki1.txt`）を使う。
`baseline/` は凍結されていてファイルを足せないので、**既定値は常に `baseline/` が動く値に保つ**。
`tests/test_run_harness.py` がベースラインの実際のログ出力先と既定値の一致を検査している。

成功と見なすのは、**解析プロセスの終了コードが 0** かつ **オラクル検証が PASS** の両方が揃ったときだけ。
どちらか一方でも欠けたら `tools/run.sh` は非ゼロで終わる。

`env.txt` には何を測ったのか（`impl` / `impl_sha256` / `build_cmd` / `run_cmd`）も記録される。
記録を取った実装ディレクトリはそのあと凍結する（`tests/test_recorded_impls_frozen.py` が
`git_commit` 時点との差分で見ている）。

⚠️ 記録 #1 の `impl_sha256` だけは今の `tools/run.sh` で再計算しても一致しない。
ファイル順を `LC_ALL=C` で固定したのが記録 #1 の**あと**（`e186af8`）だったため。
`impl/01_wrapper/` の中身は記録時のコミット `773057c` から動いていない。

記録 #0（ベースライン）完走時の実測: gcc 13.3 / Python 3.12.3 で無警告ビルド、**8時間55分31秒**で検証 PASS。
内訳は全探索 1:42:56 / 後退解析 7:12:35。ピーク RSS 4.65GiB、ディスク書き込み約 102GiB、CPU 使用率 99%（＝1スレッド）。

⚠️ 計測機のシステムTZは UTC。ログのタイムスタンプは UTC で出る（`env.txt` に JST も記録する）。

⚠️ **ピークで 40GB 程度の空きディスクが必要**（最終成果物 4.5GB + 探索中の中間ファイル）。
実行後 `runs/*/dat/` は消してよい。

## 開発

改善の実装とツールを触るとき用。**計測そのものには要らない**
（ベースラインは Python 標準ライブラリと gcc だけで走る）。

```bash
make setup   # .venv を作って開発ツールを入れる (uv)
make hooks   # コミット時に自動チェックを掛ける (pre-commit)
make check   # CI と同じ一式: ruff / shellcheck / mypy / pytest
make help    # 全ターゲット
```

| ツール | 役割 |
|---|---|
| ruff | 整形 (black 相当) と lint (flake8 + isort 相当) |
| mypy | 型検査 (strict) |
| pytest + coverage | テスト。`tools/` は 95% 以上を必須 |
| shellcheck | `tools/run.sh` |
| `tools/fingerprint_dat.py` | 成果物の集合レベルの照合 |
| pre-commit | 上をコミット時に自動実行 |

C / Rust へ移行しても導線は変わらない。`make lint-<lang>` / `make test-<lang>` を足して
`check` に繋ぎ、pre-commit にフックを1つ追加すればよい。

### テストが守っているもの

- **`oracle/` の内部整合** — 分布174行 + キャッチ + depth0負け = 確定数、
  それに引き分けを足すと到達可能数 246,803,167 になる。この鎖が1つでも切れたら記録は無効
- **`baseline/` の凍結** — ソース3ファイルの sha256 と、`-O0` のままの Makefile。
  RTA の出発点が動いたらタイムの意味が消える
- **`tools/verify_log.py` の回帰** — 記録済みの実測ログ
  （[`results/00_baseline/main.log`](results/00_baseline/main.log)）を今も PASS させられること

`baseline/` `impl/` `experiments/` `oracle/` `results/` にはフォーマッタも自動修正フックも
掛からない。
**末尾空白の除去すら禁止**にしてある。`impl/` を外しているのは、各実装の `baseline/` からの
差分そのものが計測の単位だから。整形が入ると「1試行1変数」が崩れて、タイム差が何の効果なのか言えなくなる。
