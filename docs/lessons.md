# 取り決めの経緯

[CLAUDE.md](../CLAUDE.md) の規則を、なぜそう決めたかと、そのときの数字。
CLAUDE.md には規則と罠だけを置き、経緯はここに置く（CLAUDE.md は毎回読み込まれるので、
長いと大事な規則が埋もれる）。見出しは CLAUDE.md の規則の言い回しに揃えてある。

## 計測

### 途中で落ちたら再走する

ベースライン由来の窓があり、`searchNext()` が未探索ファイルを空にした直後に落ちると、
次の起動では空のファイルを見て全探索を打ち切る（baseline / impl/02 / impl/03 で再現する）。
`writeAndBackup()` が書き込み中なら pickle も壊れる。中間成果物からの再開はレギュレーション違反でもある。
#22 からは全探索が作業ファイルを書かないので、入口の `forwardInit()` が空でない `dat/` を止める。

### 計測した `dat/` や `impl/` の中へ `cd` しない

Claude Code がそこに `.claude/.cc-writes/` を作るので、`diff -rq` が `Only in ...: .claude` で落ちる
（記録 #15 のバイト比較で踏んだ）。いまのところ中身は空で、`tools/run.sh` の `impl_sha256` は
`find . -type f` なので値は変わらない（`impl/14_c_retreat` で再計算して `results/14_c_retreat/env.txt` と
一致を確認済み）が、ファイルが置かれるようになれば証拠のハッシュが動く。

実際に起きた例が `__pycache__/*.pyc`。記録 #16 の測定前に `impl/16_raw_binary/` へテストが直接 import した
副作用で `.pyc` が残っていて、`impl_sha256` に混ざった。clone した人は `.pyc` を持たないので再現できない
（最初の1本は走り直した。[記録ノート](records/16-raw-binary.md)）。

### プロセスの生存確認はサンドボックスの外で行う

Claude Code のサンドボックス内で、呼び出し終了時にデタッチしたプロセスも終了した事例がある。
サンドボックス内の `pgrep` は PID 名前空間が別なのでホストのプロセスが1つも見えず、動いているものを
「落ちた」と誤判定する。ファイル（`freq.log` の更新時刻など）で見るならサンドボックス内でよい。
`pgrep -f '<起動コマンドの一部>'` は自分自身のコマンド行にもマッチするので、生存判定には使えない。

### 走る前に、巨大ページに使える空きを確かめる

`impl/21` 以降は、索引（8 GiB）と発見済み表（4 GiB）に巨大ページが付くことを前提に速くなっている。
lever_scan_2 の1回目はノード0のメモリが断片化していて巨大ページが付かず（`thp_fault_fallback` 909）、
P1 が 10.86 秒になった（#22 の門番では 7.35 秒）。付かなかった本を走ったあとで捨てて走り直すと、
引き直しと同じになる。そこで記録 #23 から、走る前にだけ確かめる。16 GiB は、索引 8 GiB と、
発見済み表を作り直す瞬間の 2 ＋ 4 GiB に余裕を見た値。#23 では落とす前と直後の値を手で読んだだけで
残さなかったので、#24 から門番に `free_snapshot.sh` を置いた。

### 門番は固定し、本走は固定しない

門番は小さい差を検出する装置なので分散を下げる。[`numa_bind`](../experiments/numa_bind/) で
後退解析合計の sd 16.25 → 2.56、変動係数 3.16% → 0.52%。本走は記録なので機械の素の条件で走らせ、
`#0` 以降と地続きにする。速さの利得は確定していない。固定すると全8本で 24.7 秒速い（区間 11.1〜38.3）が、
固定なしの高群が固定ありの直後に偏っていて、持ち越しを除くと +12.69 秒・t 1.71・区間 −10.51 〜 +35.89 で
0 をまたぐ。未確定の利得のために梯子の地続きを捨てない。そのぶん本走は索引のページの振れを引きうる
（固定なし8本は 490.34〜532.07 秒で幅 8.1%）。`ru_minflt` の計装で毎回記録に残す。
門番と本走の値を直接引き算しないのは、`#17` の採番順の見積もりで踏んだため（下の「採番順は効果量に大きく効く」）。

## 数字の読み方と書き方

### 対照群の帯は ±3% を目安にする。ただし前回の1本を基準にしない

同一コードの全探索は 2396 / 2430 / 2436 / 2443 / 2503 / 2523 秒とばらついた
（6本で幅 5.3%、標準偏差 2.0%、平均 2455秒）。後退解析も 2087 / 2144 / 2156 秒で幅 3.3%。
**記録 #7 で、前回の1本（たまたま最速だった）を基準に ±3% を引いたせいで、+3.3% の差を退行と読みかけた。**
その +3.3% が何だったのかは未確定。雑音とも、#7 で変わった入力チャンクの配置の影響（差の大半が辞書を
作る段に集中していた）とも読めて、1本からはどちらも決められない。観測から言えるのは「この幅が出た」までで、
検出限界が決まったわけではない。平均まわりの幅は [`measurement-noise.md`](measurement-noise.md) にある。

### フェーズ単独の帯に、合計の帯を流用しない

同一コードの観測で、`buildIndex` を1バイトも触っていない P1 が 161 / 167 / 180 秒（11.8%）振れた。
後退解析合計の振れは 3.3%、P4 は 1.7%。段ごとに帯が違う。数十秒の効果をフェーズ単独 n=1 で分離しようと
しても、たいてい見えない（#8 の門番 G1a がそうなった）。
記録 #8 の最初の書き方は、バッファ再利用を入れた実験版の P2 と後退解析合計を「同一コードのばらつき」に
混ぜていた。**評価しようとしている測定を雑音の基準に使う**ことになり、循環する。

### 段ごとの揺れの標本と統計値は手で書かない

[`measurement-noise.md`](measurement-noise.md) の表は [`tools/noise_table.py`](../tools/noise_table.py) が
`experiments/<門番>/logs/` の生ログから組み立て、`make check` が食い違いを落とす。文中で「sd X / Y%」と
書いた箇所も表と突き合わせている（`tests/test_noise_table.py`）。

### 統計値は生値から計算する

174段＋残差の3本を1桁に丸めた 291.1 / 293.4 / 296.1 から sd を出すと 2.50 になるが、
生値 291.08 / 293.43 / 296.12 から出るのは 2.52。「凍結側の数字と合わない」と思ったら、
まず自分が丸めた値を使っていないか見る。

### 効果の有無を、1本のタイム差だけで判断しない

記録 #7 の前向き探索は平均の差で 179 秒（点推定）縮んでいたのに、合計タイムは 12 秒しか動かなかった。
旧版6本・新版2本で Welch 検定すると、**自由度 1.56 / 両側 p = 0.081 / 95% 信頼区間 −69〜427 秒**で
区間が 0 をまたぐ。これは「約4%が検出限界」という意味ではない。言えるのは「その本数では確定できなかった」
までで、本数を増やせば区間は狭くなる。フェーズ単独を測る門番（記録 #6・#7 の G1）は観測を増やせるぶん分が良い。

### 時間効果が確定できない試行でも、出たタイムをそのまま記録表に載せる

レギュレーションは「1本の壁時計」で、そこを曲げると記録表の意味が壊れる。
記録 #9 は備考に「目的はピーク RSS」と書いた。出たタイムの差を改善とも退行とも読まない。

### 小さい差を決めるときは、完走タイムではなく雑音の小さい量で判定する

記録 #18 の `-O2` 対 `-O3` は差が 0.24 秒で、完走タイム1本では決められない。4本ずつでの 95% 半幅は
全探索合計 1.4〜5.7 秒に対し完走タイム 28 秒で、雑音はほぼ全部が後退解析から来ている。
記録 #18 は「区間が 0 を含むなら `-O2`」と測る前に書いた。

### 腕が3つ以上の門番では、実行順と位置ごとの回数を明記する

記録 #18 は5腕を4ブロックで回し、各腕が4つの異なる位置に来る不完全な配置にした
（[`gate_18_opt/run_all_forward.sh`](../experiments/gate_18_opt/run_all_forward.sh)）。各腕には一度も来ない
位置が1つあり、各位置の回数が均等なラテン方陣ではない。区間で判断しても多重比較の問題は解消しない。

### 「1バイトも変えていない」は、そのファイルが本当にバイト同一のときだけ書く

記録 #12 は全探索の出力を変えていないが、`-3` の修正で `searchNext` の分岐は書き換えている。
`results/12_c_predecessors/bytecompare.txt` の見出しには誤った書き方が残っている
（凍結なので直さず、訂正は README 側に置いた）。

### 「メモリ律速だから最適化は効かない」は段の名前では決まらない

記録 #18 は後退解析全体では −18.3%（全探索の −30.5% より小さい）だったのに、P2 単独は −35.4% で
全探索を上回った。`-O` が効く純ビット演算の `nextBoardInvNormal` が F1 だけでなく P2 の中にも居たため。

## 採番順と答えの検査

### 保存形式を変えると採番順は必ず動く

pickle の往復は `set` の反復順を保たない。ただし集合の疎密に依存する。`range(1_000_000)` のような密な連番では
0.0%（まったく動かない）だが、盤面のような疎な48bit整数では 100.0% 動く
（[`pickle_order_demo.py`](../experiments/gate_16_raw_binary/pickle_order_demo.py) が固定シードで再現する）。
記録 #15 までは `pickle.load()` が返す「作り直した集合の順」で番号を振っていて、記録 #16 は `frombytes` で
「書いたときの順」を読む。一致させるには読むたびに集合を作り直すしかなく、それでは形式を変えた意味が消える。
効果を分けたければ、両腕に同じ採番順を渡す門番を別に立てる（[`gate_16_raw_binary`](../experiments/gate_16_raw_binary/)）。
形式を変えなくても、記録 #17 のように書き出しの `set(...)` を外せば、ファイルに並ぶ順序が
「集合の反復順」から「渡された並びそのまま」に変わる。

### 採番順は効果量に大きく効く

記録 #17 の門番は両腕に同じ入力を渡したので P4 が 166.00 → 165.00（区間 −2.78 〜 +0.78）で動かなかったのに、
本走では 158 → 70 秒になった。コードは記録 #12 のままで、違うのは入力の採番順だけ。完走の −471 秒のうち
116 秒がこの副作用で、門番からは出てこない（[`gate_17_no_set`](../experiments/gate_17_no_set/)）。
記録 #12 の門番は本走より旧新どちらも 4〜6% 遅かった（原因は未分離）。旧新を同じ入力で交互に比べるぶんには
影響しないが、採番順に反応する段（P4 の乱書きなど）の効果量を「本走の値」としては書けない。

### 区切りも順序も動かさない変更では指紋ではなくバイト比較

記録 #9 が最初。指紋（件数・総和・XOR）より強い検査で、一致しなければ区切りが動いた証拠になる。

### 全探索だけを走らせる門番

空の `dat/` から始まるので入力を揃える必要が無い代わりに、手数別174行が出ない（あれは後退解析の出力）。
答えの検査は「総未知 ＋ 総勝ち ＋ 総負け ＝ `oracle/totals.tsv` の `reachable_total`」と、両腕の成果物の
指紋照合で代える（[`gate_17_forward`](../experiments/gate_17_forward/)）。

### pickle が書いた順を知りたいときは `pickletools.genops` でストリームから取る

`array("Q", pickle.load(f))` を「書かれた順」として比べると、採番順が同じでも食い違って見える
（記録 #16 の門番でこれを踏み、設計が崩れたと読み違えた）。

### 組み直したフィクスチャは採番順を復元しない

`tools/rebuild_forward_fixture.py` は、後退解析が手数別に散らしたファイルから未知集合を詰め直すので、
集合は戻るが並びは戻らない（小さく回すと 2,925 件中 2,903 件＝99.2% の位置が変わった。
`tests/test_rebuild_forward_fixture.py` が固定している）。組み直した入力で測ると、先読みのように並びで
効き目が変わるレバーを測り違える。

## コミットと文書

### `.gitignore` に入れたのは「プロジェクトのファイルには絶対ならない名前」だけ

作業ディレクトリにはサンドボックスが置く 0 バイトの覆い（`.gitconfig` や `.claude/agents` など）が並んでいる。
`.gitmodules` / `.mcp.json` / `.claude/settings.json` / `.claude/{agents,commands,hooks,workflows}` にも覆いが
置かれるが、どれも共有すべき本物が同名で来るので無視していない（無視すると `git add` が `-f` を要求して、
本物を入れるときに詰まる）。

### `push` と PR 作成は指示されるまでしない

公開リポジトリでは両方が point of no return で、PR は削除できず、クローズしても `/pull/N.diff` は
認証不要で取得できる。

### `make publish-check` が見るもの

`tools/publish_lint.py` が落とすのは、追記で回復できないものだけ（鍵・計測機や個人の同定情報・凍結物の変更・
記録の証拠の欠損・`Claude-Session:` 行）。説明の誤りや命名はわざと見ない。直せるものを門番に積むと、
鳴っても push を止めない癖がつくため。鍵と同定情報は `origin/main..HEAD` のコミットを1つずつと、その
メッセージを見る（足して次のコミットで消しても blob は履歴に残る）。凍結と証拠は base との差と `HEAD` の
中身を見る。git が答えを返さなかったときは指摘ゼロではなく終了コード 2。`make hooks` で入る pre-push フックは
push 対象の ref を1つずつ見るので、別のブランチにいるまま `git push origin <別のブランチ>` をしても検査される。
比較先は `BASE=` で変えられる。

### あとから辿れないものを指さない

セッションに送った指示（このリポジトリでは「指示書」と呼んでいるが、ファイルとしてはどこにも残らない）、
マージ後に消えるブランチ名、git 管理外の `runs/` の中身、「前回」「さっき」は、読む人が参照できない。
既に公開したぶん（「指示書」20行とコミットメッセージ9件、`0631252` が指す消えたブランチ名）は凍結物を
含むので直さない。

### コミット SHA も「辿れる」とは限らない

記録 #18 で、レビューを受けて直したコミットを指した行が、そのコミットを2回 `amend` したせいで
reflog にしか無い SHA を指す形になった。本走の `env.txt` が指すコミットの祖先は書き換えられないので、
訂正はあとのコミットのメッセージに書く（記録 #23 と #24 の門番のコミットのメッセージを、
それぞれの記録のコミットで訂正した）。
