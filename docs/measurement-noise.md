# 計測機のばらつきについて（記録 #5 から計装）

`tools/run.sh` が1分おきに CPU 周波数・温度・スロットル回数を `freq.log` に残すようにした。
記録 #4 で、**まったく同じ全探索コードのタイムが 3.8% ばらついた**ためで、
その原因はまだ分かっていない。

前向き探索が同一コードの実測（5本）:

| | |
|---|---|
| 記録 #3 | 2430s |
| 記録 #3 のフィクスチャ | 2436s |
| 記録 #4 | 2503s |
| 記録 #5 のフィクスチャ | 2523s |
| 記録 #5 | 2443s |
| 記録 #6 | 2396s |

**幅 5.3% / 標準偏差 2.0%（平均 2455s）。** ⚠️ ここまでが `impl/03`〜`06` の同一コード6本。
`impl/07` で全探索に手を入れたので、以降の観測は別の系列になる（2237.6s / 2315s）。 ⚠️ 観測が6本になって**幅は広がった**
（#6 が最速を更新した）。CLAUDE.md の「対照群の帯は ±3%」は平均まわり ±2.6% に相当し、
いまのところ矛盾していないが、**検出限界が決まったわけではない**ことは変わらない。

⚠️ **有力だった「連続負荷の直後は熱でターボが下がる」という仮説は、記録 #5 で弱まった。**
この記録は門番の55分の直後、**61°C から始まって 77°C まで上がりながら 2443 秒**（速い側）。
`freq.log` は125本。**1本目は解析プロセスを起動する前に同期で取っている**ので
（2300 MHz / 61.0°C）、以下はそれを除いた **124本**での集計:

| | |
|---|---|
| `freq_max` 中央値 | **3490 MHz**（この CPU の単コアターボ上限は 3.5GHz） |
| 同 四分位 | 3415〜3492 MHz（最小 2986 / 最大 3500） |
| 3400 MHz 未満 | **24本 / 124本** |
| 温度との相関 | **+0.31**（負ではない） |
| 前半 → 後半 | 3441 MHz（72.0°C）→ **3445 MHz（74.7°C）** |
| サーマルスロットル | 全区間 **0** |

温度が上がっても周波数は下がっておらず、熱でターボが落ちた形跡はこのログに無い。

⚠️ **ただし「解析スレッドが乗っていたコアの周波数」は測れていない。**
`freq_max` は全56論理CPUの最大値で、解析は1スレッドだから、その最大値を出していたのが
解析スレッドのコアだという確認はしていない。
スロットル回数も cpu0 の `package_throttle_count`、つまり**2ソケットのうちパッケージ0だけ**を
見ている（温度は2ゾーンの最大）。言えるのは「この取り方で見たかぎり低下は見えない」まで。

**記録 #6（2本目のデータ、同じく1本目を除いた74本）**: `freq_max` 中央値 3450 MHz /
四分位 3399〜3492、3400 MHz 未満 19本、スロットル 0。温度は **57〜72°C** で #5（61〜77°C）より低い。
⚠️ **#6 は後半のほうが涼しい**（前半 3441 MHz / 67.8°C → 後半 3435 MHz / 64.2°C）。
後退解析がメモリ待ちの多い仕事になったぶん発熱が減ったと見えるが、**2本では何も言えない。**

## 段ごとの揺れ（門番で取れた同一コードの標本）

合計タイムの帯をフェーズ単独に流用しない。**段ごとに桁が違う。**
下の標本はどれも「その段のコードがバイト同一な観測」だけを並べてある。

⚠️ **この表は手で書かない。** [`tools/noise_table.py`](../tools/noise_table.py) が
`experiments/<門番>/logs/` の生ログから組み立てていて、`make check` が食い違いを落とす。
直すときは `python3 tools/noise_table.py --write`。

載せる条件は2つ。**このツールが読める形でログがコミットされていること**
（`<ラベル>_main.log` と `console.log` を並べた形。いまはこの4つ）と、
**その段のコードがその本たちでバイト同一であること**。P4 は `gate_12` の、P2 は `gate_15` の
レバーなので、その組み合わせは載せていない。**条件を満たす組み合わせを全部載せている
とは言っていない。**

`gate_12` の P0 は6本とも 93 秒で、変動係数が 0.00% になっている。
**これは「揺れが無い」ではなく「表示の刻み（1秒）より小さい」。**
P0〜P4 は `s2hms()` が秒未満を切り捨てた表示値なので、1秒未満の差は見えない。

**平均・sd・変動係数は標本の生値から計算する**（`statistics.stdev`、標本標準偏差）。
**丸めた値から計算しないこと。** 174段＋残差の3本を1桁に丸めた 291.1 / 293.4 / 296.1 から
sd を出すと 2.50 になり、生値から出る 2.52 と合わない。`s2hms()` を通した段（P0〜P4）は
ログの時点で秒未満が切り捨てられているので、整数がそのまま生値。

[`records/14-c-retreat.md`](records/14-c-retreat.md) の174段ループの表は、
標本を1桁に丸めて表示しつつ sd は生値から計算している（2.52）。表示と計算の精度が
違うだけで、値そのものは食い違っていない。

### 本数の決め方

見込む効果量とこの sd から決める。記録 #15 は P2 の効果量を 30〜70 秒と見込んでいて、
sd 14.39 だと旧新3本ずつでは低い側で 95% 区間が 0 を跨ぐ（±33 秒）。8本ずつなら
±15 秒に収まるので8本にした。**実測は −88.0 秒（95% 区間 −98.9 〜 −77.1）**で、
結果的には3本でも足りたが、それは測る前には分からない。

⚠️ **P1 索引は段によっては裾が長い。** `retreat_profile` の8本で 20〜34 秒、
変動係数 **22.27%** と、`gate_14` の同じ段（2.02%）の10倍以上に広がった。
`buildIndex` は `impl/11` から**バイト同一**なので、コードの違いではない。
34 秒の1本は索引 8.59 GB のページを **2.41 回**踏んでいて、原因は
[`experiments/retreat_profile/`](../experiments/retreat_profile/) に書いてある。
**P1 にレバーを当てるなら、sd 0.41 の行ではなく 4.90 の行で本数を決めること。**

この表は「この幅が出た」までしか言っていない。検出限界が決まったわけではない。
本数を増やせば区間は狭くなる。

### 対のなかの位置が乗ることがある

`gate_12` と `gate_14` は `old new` の固定順で、`gate_14` では **P0 が3本とも新版のほうが
高かった**（92/92/93 → 94/96/94、+2.3 秒 / +2.5%）。`loadForwardResult` は1行も
変えていないので効果ではありえない。

`gate_15` で `old new new old` にしたところ、**P0 の差は −0.25 秒
（95% 区間 −2.06 〜 +1.56）**になった。⚠️ **1回の観測で、機序は特定していない**が、
**門番の並びは ABBA にする**（位置の効きが4本ごとに相殺される）。
