# 記録 #6 で分かったこと

**後退解析を「各辺1回」にした。2:04:47 → 1:14:43（40.1% 短縮、対ベースライン 7.17×）。**
後退解析だけで見ると 1:24:04 → 0:34:47 で **2.42×**。

#5 までの後退解析は、未確定局面を174ラウンド舐め直し、そのたびに指し手を作り直していた。

| | |
|---|---|
| 延べ訪問回数 | 1,479,788,351（全局面 246,803,167 の6倍） |
| うち同一ラウンド内の作り直し | 48.1% |
| うち引き分けの空振り | 31.5%（2,682,700局面を174回舐めて一度も確定しない） |
| 実際に必要な辺 | **938,671,869 本を1回ずつ** |

原因は**前任局面を引けないこと**の一点。連番を振って前任リスト（CSR）と
残り出次数のカウンタを作れば、**各辺を高々1回しか通らない**
（辺は行き先が確定したときに1回だけ辿るので、最後まで引き分けの局面へ向かう辺は一度も通らない）。
構築で数えた辺は **938,671,869 本ちょうど**で、事前に別経路（#5 のログからの再現計算）で
出していた数と一致した。

🔑 **引き分けは特別扱いのコードを1行も書かずに残る。** ただし「一度も触られない」のではない。
成果物から数え直した実際の姿は次のとおり:

| | |
|---|---|
| 引き分け局面 | 2,682,700 |
| そこから出る辺 | 23,648,662 |
| うち**勝ち**へ向かう辺（＝`cnt` が減る回数） | **20,163,568（85.3%）** |
| 負けへ向かう辺 | **0**（1本でもあればそれは勝ち局面になる） |
| 後続が全部引き分けの局面（＝本当に一度も触られない） | **495**（0.018%） |

つまり引き分けが残る理屈は「勝ち後続が来ない」ではなく、**負け後続が無いので勝ちにならず、
勝ち後続で `cnt` を減らしても引き分けの後続が残るので 0 にならない**、である。

⚠️ **`impl/06_csr_counter/animal_shogi.py` のコメントには、この誤った説明（「勝ち後続も来ない」
「一度も触られない」）がそのまま残っている。** 記録を取った実装はコメントの訂正でも触らない、
という取り決めなので直さない（`results/06_csr_counter/env.txt` が指す先が嘘になる）。
正しい説明は次の実装に書く。動作そのものは正しく、オラクルとも指紋とも一致している。

それでも効果は大きい。#5 は引き分けを174ラウンド舐め直して **466,789,800 訪問**（延べ訪問の
31.5%）を費やし、その全部で指し手を作り直していた。#6 でかかるのは **20,163,568 回のカウンタ減算**
（辺の 2.1%）だけで、**23分の1**になり、指し手の再生成も伴わない。

## 構築が新しい後退解析の 85% を占める

| 区分 | 時間 | 割合 |
|---|---|---|
| P0 読み込み（`dat/` から 2.4 億局面） | 93 s | 4.5% |
| P1 索引（パック値 → 連番の `dict`） | 161 s | 7.7% |
| P2 後続生成（9.4 億辺の生成と辞書引き） | **969 s** | **46.4%** |
| P4 前任リスト（計数ソートで辺を逆向きに詰め直す） | **554 s** | **26.5%** |
| 174段のループ（**これが本来の仕事**） | 265 s＋ | 12.7%＋ |
| 残差（下記） | 45 s | 2.2% |

⚠️ **この表の値はログの表示値で、各段は秒未満を切り捨てている。**
とくにループの 174 行は **144 行が「0秒」と表示**されているので、265 秒は**下限**である。
したがってループの実時間は **265〜310 秒のあいだ**にある。

残差 45 秒に入っているのは、計測区間の外にある次のものと、上の端数:

- `del idx` — 辞書 24.41 GiB の解放。**493,606,334 個の int オブジェクト**（キーと値）の解放を含む
- `del succ, succ_off` — 3.87 GiB の解放
- `dtm` の確保と初期化（`cnt` は `buildSuccessors` の中で作るので P2 に入っている）
- 引き分けの抽出（`dtm` の 99,485,568 件を走査する）
- 書き出し（これだけは別途 1 秒とログにある）

⚠️ **どれが支配的かは測っていない。** メモリの解放が軽いという保証はない。

🔑 **それでも、本来の仕事は 300 秒前後しかない。** 残り 1,777 秒は「前任リストを作るための
下ごしらえ」で、これが次の標的になる。事前に「構築が 85% を占める」と見込んで書いていたのが、
実測 **85.1%**（1,777 / 2,087）だった。構築の4段は個別に計測しているので、
この割合はループと残差の分かれ方には左右されない。

## メモリの見積もりは小規模実測からの外挿で足りた

`dict{60bit int → 小int}` の実寸を 4,000,000 件で測ると **106.2 B/件**（表の成長は正確に倍々で、
246,803,167 件なら `dk_size = 2^29`）。ここから外挿したピーク 30.12 GiB に対し、実測 **30.64 GiB**。

| 局面 | 内訳 | |
|---|---|---|
| P2 の終わり（**ピーク**） | packed 1.84 + dict 24.41 + succ 3.50 + succ_off 0.37 | 30.1 GiB |
| ループ中（定常） | packed 1.84 + pred 3.50 + pred_off 0.92 + dtm 0.23 + cnt 0.09 | 6.6 GiB |

⚠️ **ピークを決めたのは「辞書をいつ捨てるか」の一行だった。** 入次数を数えるのに辞書は要らない
（`succ` には既に連番が入っている）ので、`pred[]` を確保する前に捨てられる。
辞書を P4 まで持ち越すと辞書 24.41 GiB と前任配列 3.50 GiB が同時に常駐し、
**P4 の常駐が 24 GiB ぶん増える**。実行全体のピークがそのぶん上がるわけではない
（ピークは P2 の終わりにあるため）。各配列の寸法から計算すると全体のピークは
**30.6 → 36 GiB 前後**になる ⚠️ **これは計算であって実測ではない**。
中止線 45 GB（41.9 GiB）までの余裕が 11 GiB から 6 GiB に減る、という程度の話である。
