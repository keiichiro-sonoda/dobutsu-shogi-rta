# 記録 #15 で分かったこと

**これは対称性のために取った記録で、速さは目的ではない。**
F1 の展開ループだけがCに居て P2 が居ない、という非対称を畳むのが狙いだった。
そうすると Python と C の境界が「バッチで1回呼ぶ」の一形だけになる。
効果量は門番に任せ、区間が 0 を跨いで終わってもこの記録は失敗ではない、と
先に決めてから測った。

**P2 後続生成が 194 → 105 秒。完走 0:21:31 → 0:19:49（27.02×）。**

`buildSuccessors()` の 99,485,568 周のループが、プログラムに最後まで残っていた
「局面ごとの FFI 往復」だった。`#8`・`#11`・`#12`・`#13`・`#14` と同じ手の6回目。

⚠️ **成果物は #14 とバイト一致した。** 213 ファイル 2,216,050,387 バイト、
`diff -rq` の終了コード 0、md5 一覧の sha256 も同じ（`f0f29335…`）。
**#11 から #15 まで5つの記録の成果物が同一**で、バイト比較4回（#12・#13・#14・#15）で
つながっている。#11 自身の照合は指紋だったが、#12 がその `dat/` とバイト比較している。

## 3本ずつでは足りないと先に分かっていた

[`gate_14`](../../experiments/gate_14_c_retreat/) は **P2 を1行も変えていない旧新6本**を
取っていて、そこでの P2 は 190/193/194/197/220/222 秒（平均 202.7 / sd 14.4 /
変動係数 7.1%）と振れていた。174段ループの揺れ（sd 2.5 / 0.86%）より一桁悪い。

見込んでいた効果量 30〜70 秒に対し、3本ずつだと低い側で区間が 0 を跨ぐ。
**先にある同一コードの標本から本数を決められた**のが、今回いちばん効いた段取り。

⚠️ **新版の sd 12.21 は2本の外れ値で膨らんでいる**（129 / 131、他の6本は 103〜104）。
落とせば sd は 0.5 になるが、落とす理由を持っていないので落としていない。

## `old new` の固定順で出ていた P0 の差は消えた

`gate_12` と `gate_14` は `old new` の固定順で、`gate_14` では **P0 が3本とも新版のほうが
高かった**（+2.3 秒 / +2.5%）。`loadForwardResult` は1行も変えていないので効果では

今回 `old new new old` にしたところ、**P0 の差は −0.25 秒（95% 区間 −2.06 〜 +1.56）**。
本走でも P0 は 96 → 95 秒で動いていない。

⚠️ **「並びを変えたら消えた」という1回の観測で、機序は特定していない。**
ページキャッシュの温まり方を疑ってはいるが、測っていない。

## ピーク RSS が上がった理由は分からなかった

**本走で 13.8172 → 13.8776 GiB（+61.8 MiB）。** 門番でも +16.6 MiB で、
**旧8本と新8本が完全に分離した**（旧の最大 14,499,136 KiB < 新の最小 14,514,988 KiB）ので
揺れではない。狙いは「13.82 GiB のまま」だったので、**外した予測**。

新版が P2 で余分に持つのは中継バッファ **256 KiB** だけで、桁が合わない。
[`experiments/rss_array_growth/`](../../experiments/rss_array_growth/) で4組（8回の起動）測った:

| 測ったもの | 旧 | 新 | 差 |
|---|---|---|---|
| `succ` の積み方（9 要素ずつ / 65,536 要素ずつ） | 3591.0 MiB | 3591.0 MiB | **0** |
| `succ_off` と `cnt`（append / 先に確保） | 484.3 MiB | 484.3 MiB | **0** |
| P2 の3本を同じ順序で作る | 4065.7 MiB | 4065.7 MiB | **0** |
| 索引 8.59 GB と `packed` 1.97 GB を先に置く | 14140.4 MiB | 14140.9 MiB | **+0.5** |

⚠️ **どれも +16.6 MiB を再現しない。** 最後の1つが出した +0.5 MiB は中継バッファ
256 KiB とほぼ同じで、残りは説明できていない。**Python 側の割り付けだけでは出ない**
ところまでは言える。残っている違いは C の呼び出し方（99,485,568 回 → 14,300 回）だが、
そこは測っていない。

## `succ` を先に確保しなかった理由

最初の設計は「平均出次数 × `n_uk` × 1.1 で `succ` を先に確保し、C が直接書く」形だった。
**触っていないページは RSS に入らないが、`array("I", bytes(4)) * n` は 0 で埋めるので
確保したぶん全部が常駐する。**

| | ピーク RSS の増分 |
|---|---|
| `mmap.mmap(-1, 2 GB)` で予約のみ | **+0 MiB** |
| そのうち 300 MB だけ書く | +286 MiB |
| `array("I", bytes(4)) * 5e8`（2 GB） | **+1,907 MiB** |

最終 3.75 GB の 1.1 倍を先に確保すると、**余分な約 375 MB がそのままピークに乗る**。
プログラム全体のピークを決めているのは P2 の末尾（索引 8.59 GB ＋ `packed` 1.97 GB ＋
`succ` 3.75 GB ＋ `succ_off`/`cnt` 0.50 GB ＝ 14.82 GB、実測 14.84 GB）なので、
**レバーと関係ない理由で記録表の数字が動く**ことになる。

中継バッファを経由する形にすると `succ` の伸び方が #14 のままになり、容量の見積もりも
容量不足からの再開も要らず、`buildPredecessors` を1行も触らずに済んだ。
⚠️ それでも +61.8 MiB 動いたので、**この判断は「もっと動くのを避けた」までしか言えない。**

## 戻り値を下流と衝突させない

最初の設計は「引数不正は `-1`、それ以外は下流の戻り値をそのまま返す」だったが、
`nextBoardIndexNormal` は**トライ負けに `-1` を返す**（`impl/15_c_successors/animal_shogi.h`）。
そのまま返すと引数不正と区別できない。**下流の値は `out[3]` に入れ、戻り値は `-5`** にした。

| | |
|---|---|
| `0` | 正常（`out[1] == hi` なら完走、`hi` 未満なら中継バッファが一杯） |
| `-1` | 引数不正（`lo > hi` / `hi > n_uk` / 容量が1局面ぶんに満たない / NULL） |
| `-5` | 後続を作れない局面（`out[1]` にその番号、`out[3]` に下流の戻り値） |
| `-6` | 出次数が `cnt`（1バイト）に収まらない |
| `-7` | 辺の総数が `uint32` に収まらない |

⚠️ **`-6` は今の指し手生成では起こせない**（出次数は `MAX_ACTION_NUM` = 48 以下）。
テストで固定しているのは「検査がコードにあること」と「起こらない理由」だけで、
**通したとは書かない**。`-7` は `base` を上限に置けば実際に起こせるので通してある。

## 記録 #13・#14 の積み残しを片付けた

空入力のラウンドで `expandNewCount()` が前のラウンドの値を返す不具合で、
CLAUDE.md の「次の実装で必ず直すもの」に積んであったもの。

⚠️ **これはレバーではない。** `impl/13`・`impl/14` は凍結なので直っておらず、
