## ⑥を外した理由

### F1 の −34 秒は、区間の切り方のせい

`_profMark("F1_begin")` の直後に `arr = array("Q", unexp_boards)` がある。
**この変換が F1 の区間に入っている。** #15 では `unexp_boards` が pickle から来た
**集合**なので、500万個の `PyLong` を舐めて `array` を作っていた。#16 では
`frombytes` が返した `array` なので、ここは `array` → `array` の写しで済む。

つまり F1 の −34 秒は展開ループが速くなったのではなく、**読み込みの費用の残りが
F1 に計上されていた**ぶん。

⚠️ **README の「次の標的」は、これを先に書いていた。** F1 の行に
「Python 側に残るのは `array("Q", unexp_boards)` の詰め替えが主で、それが要るのは
`unexp_boards` が pickle された `set` で返るから。**pickle の行に含まれる**」とある。
読んでいたのに、事前登録では F1 を「誤差内」に入れた。**外したのは予測のほうで、
リポジトリの分析は当たっていた。**

## この記録に至るまでに1本、汚染された走行があった

**最初に完走させた1本は `results/` に載せていない。** `impl/16_raw_binary/` に

`tools/run.sh` の `impl_sha256`（`find . -type f` の総ハッシュ）にそれが混ざった。
clone した人が `env.txt` の値を再現できない状態だったので、`__pycache__` を消して
走り直した。**いま `results/16_raw_binary/` にあるのは2本目。**

その1本目では、成果物のチャンク分割が `#15` と 213 ファイル中 208 で違っていた
（集合は一致、オラクルも指紋も PASS）。採番順は P2・P4・174段ループの局所性を

**P2 の差はちょうど 0 秒。** 1本目の +23 秒は形式の効果ではなく、

⚠️ **`__pycache__` は `impl_sha256` の値だけを壊し、計算そのものは壊していない。**

P0 の −89.50 から来ている。**形式の効果は P0 に閉じている。**

## 採番順が動いたのはなぜか — `set(...)` を残しても避けられない

指示は「書き出しの `set(...)` を外さないこと」だった。**外していない。**
11 か所の書き出しは `set(...)` が10・素の `[]` が1で、#15 とまったく同じ内訳。
それでも順序は動いた。原因は**読む側**にある。

**pickle の往復は `set` の反復順を保たない。** 実測した。

```
要素 1,000,000 の集合 (48bit 一様乱数、盤面番号に近い疎さ):
往復で反復順が同じ = False / 位置が動いた要素 999,807 (100.0%)
（`range(1_000_000)` のような密な連番では 0.0%。集合の疎密に依存する）
```

pickle はストリームには書いたときの順で並べるが、`pickle.load` が作り直す集合は
別の反復順になる（`experiments/gate_16_raw_binary/pickle_order_demo.py` が固定シードで
確かめている。密な連番集合では起こらないが、盤面のような疎な集合では起こる）。整数の集合は開番地法の表なので、同じ要素を同じ順に入れ直しても
先に入った要素が本来の巣に収まってしまい、配置が変わる。

- #15 は `pickle.load(f)` が返す**作り直した集合の順**で番号を振っていた
- #16 は `frombytes` で**書いたときの順**をそのまま読む

一致させるには読むたびに `set(readBoards(...))` と作り直すしかなく、それでは
F0 53 → 1 秒、P0 95 → 3 秒という利得が丸ごと消える。
**保存形式を変えると採番順は必ず動く。** この記録で分かったいちばん大きいこと。

| | |

| 4つの `*_PATH_FORMAT` | `.pickle` → `.bin` |

バックアップ機構は落とした。`BACK_UP = False` が `baseline/` を含む16ファイルすべてで
一度も動いておらず、`import re` と `import shutil` はこの分岐のためだけに在った。
拡張子が正規表現に埋まっているので `.bin` にすると「死んでいる」から
「有効にしたら必ず落ちる」に変わる。CLAUDE.md が「途中で落ちたら再開ではなく再走」と
定めていて、戻れても使い道がない。

### 記録 #15 の積み残し3件も直した

CLAUDE.md の「次の実装で必ず直すもの」に積んであったもの。どれもレバーではなく、
空入力でしか、あるいは不変条件が崩れたときしか挙動が変わらない。

1. `expandRound` の `g_exp_n = 0;` を `if (!out) return -1;` より前へ。#15 は
   コメントが「どの早期 return よりも前に 0 に戻す」と書いてあって**実コードより
   強いことを言っていた**。`out` が NULL の経路で件数が残らないことを実際に走らせて見る
2. `buildSuccRange` の `-6` が `degree > 255` と `n_found > degree` の2つを束ねていた。
   後者を `-8` に割り、`.h` の説明も分けた
3. `outside += degree - n_found;` を `n_found > degree` の検査より後ろへ

⚠️ 2 を直すとき、`-8` の診断を `out[4]` に入れようとして気づいた。**`out` は4要素**
（`c_int64_array4`）なので、書けば呼び出し側の領域を踏む。`out[3]` に収めた。

印字だけの死んだ行（`countTotalBoardNum` の「末端盤面数」が `tbn_win` を2回足していた）も
直した。どこからも呼ばれないので `dat/` にも記録にも影響しない。
