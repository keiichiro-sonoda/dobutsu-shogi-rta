# 記録 #17 で分かったこと

**書き出しの `set(...)` を10か所とも外した。それだけ。**

記録 #16 で読む側の `PyLong` 生成は消えた（F0 53.16 → 1.15 / P0 95 → 3 秒）。
同じ無駄が書く側に残っていて、`writeBoards(path, set(arr[start:start + N]))` は
N 要素につき `PyLong` を N 個起こしてハッシュし、約 2N スロットの表を組み、
それをランダム順に反復して `uint64` に戻して捨てていた。

**完走 0:15:06 → 0:07:15（35.45× → 73.86×）。−471.37 秒。**

**コードを変えたのは2種類だけ。** `set(...)` の皮を10か所剥ぐことと、空を書く
4経路を `[]` に揃えること。差分の変更行をコードとコメントに分けて連続した塊で
数えると **コード 10 か所 / コメント 11 か所**。コードの10は上の2種類とちょうど
一致する（皮剥ぎ 7 ＋ `set()` → `[]` の 3）。コメントのほうは `set`／`集合` という
語を消す追従で **11 か所・5関数**、挙動には関係しない。`writeBoards` の本体
（`array("Q", obj).tobytes()`）も C も `.h` も `Makefile` も触っていない。

数えるときは**差分のハンクではなく変更行で数える**。コメントがコード行の
すぐ下にあるとハンクが繋がって、コメントの変更が1つ見えなくなる
（`updateUKFile` の「残りは新ファイルへ」がそれで、ハンクで数えると 10 になる）。

## 効果の3分の2以上は、採番順が動いたことから来ている

`set(...)` を外すと、ファイルに並ぶ順序が「集合の反復順」から「渡された並びそのまま」に
変わる。本走ではそれが採番順を動かし、後退解析の局所性まで変える。
**門番を2本立てて、コードの効果と採番順の効果を分けた。**

| | 全探索 | 後退解析 |
|---|---|---|
| **本走で動いた量** | **−317.91** | **−153.46** |
| 門番（両腕に同じ入力） | −318.00（区間 −323.10 … −312.89） | −37.40（区間 −42.71 … −32.10） |
| 差（＝採番順が動いたぶん） | ほぼ 0 | **−116.06** |

全探索は空の `dat/` から始まるので、そもそも本走と門番で条件が同じ。実測 −317.91 は
門番の区間 −323.10 … −312.89 のなかに入った（[`gate_17_forward`](../../experiments/gate_17_forward/)）。

後退解析は違う。門番（[`gate_17_no_set`](../../experiments/gate_17_no_set/)）は両腕に
同じフィクスチャを渡したので、P0・P1・P2・P4 は4段とも区間が 0 をまたいだ。
ところが本走では:

| 段 | `#16` の本走 | `#17` の本走 | 差 |
|---|---|---|---|
| P0 読み込み | 3 | 3 | 0 |
| P1 索引 | 23 | 20 | −3 |
| P2 後続生成 | 106 | 96 | −10 |
| **P4 前任リスト** | **158** | **70** | **−88** |
| 174段ループ | 87 | 36 | −51 |

**P4 が 158 → 70 秒。** 門番では `old` 166.00 / `new` 165.00（区間 −2.78 … +0.78）で
まったく動かなかった段が、本走では半分以下になった。両者の違いは**入力の採番順**
しかない。`#17` の全探索が書く順は「発見した順」で、`#16` までの「集合の反復順」より
局所性がよかった、と読める。

⚠️ **この −116.06 秒は「採番順の効果」の見積もりであって、分離された値ではない。**
門番は `numactl` で片ノードに固定してあり本走は固定していないので、そのぶんも混ざる
（[`numa_bind`](../../experiments/numa_bind/) では固定で後退解析合計が −24.7 秒
だったが、区間 +11.1 … +38.3 が 0 をまたいでいて確定していない）。段ごとの
−3 / −10 / −88 / −51 の和は −152 で、後退解析合計の −153.46 とは 1.5 秒しか違わない。

## 外す前に一意性を確かめた

`set` はスライス内の重複除去も兼ねていた。外してよいのは中身が一意なときだけなので、
作業コピーに `assert len(set(x)) == len(x)` を4か所（`new_unexp_boards` /
`known_uk + ukl` / `wlbl` / `rest`）入れ、小さいフィクスチャで等価性検査を通した。
到達した20観測すべてで重複ゼロだった（`new_unexp` 4〜10,881 / `ukl` 1〜2,887 /
`wlbl` 1〜1,622 / `rest` 2,866。`BOARD_NUM_MAX` を超えて分割も起きている状態）。
⚠️ この `assert` は記録実装には入れていない。

10か所とも `set(x[start:start + BOARD_NUM_MAX])` という**スライス単位**だったので、
チャンク境界をまたぐ重複は `#16` でも落ちていない。つまり一意性は `set` の有無に
関わらず前提になっていた。全件規模で崩れれば `indexBuild` が `-5`（キーが重複）で
止まり、サイズ検算（合計バイト ÷ 8 = 246,803,167）も閉じない。実際どちらも通った。

| | |
|---|---|
| 書き出し10か所 | `set(x)` → `x`。中身の式は一字も変えていない |
| 空を書く4経路 | `set()` 3つ ＋ 素の `[]` 1つ → `[]` 4つ |

`#16` とバイト同一であること。3つの変異を入れてどれも落ちることを確かめてある。

## 後退解析の秒の出し方について

この記録では **後退解析 = 完走の壁時計 − `forward_summary.tsv` の `forward_total`**
とした（435.00 − 182.50 = 252.50）。この差には Python の起動と後片付けが入る。

⚠️ `#16` の記録ノートはここから `residual_total` をもう一度引いていて、
404.70 としている。`residual_total` は `forward_total` の**内側**の量なので
（`_total - _in_rounds - _f6 - _release_wl - _release_seen`）、同じ定義で出し直すと
`#16` は **405.96** になる。差は 1.26 秒で結論は動かないが、この記録の
−153.46 は両方を 405.96 / 252.50 で揃えて出した値。
