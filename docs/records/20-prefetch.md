## 先読みで何を読んでいるか

どの段も、**次に触るメモリの場所が計算で先に分かる**のに、1つずつ「読みに行って、届くまで待つ」を
繰り返していた。先読みは「この場所をもうすぐ使う」と CPU に伝えるヒントで、待っている間に
次の場所の取り寄せを重ねられる。**書く値は変わらない**（ヒントを無視されても答えは同じ）。

- **F1・P2・P1（ハッシュ表を引く段）**: 盤面から後続を作った時点で、それぞれのスロットの位置
  （ハッシュ値）は全部分かっている。全部の取り寄せを先に出してから、1つずつ挿入・探査する
- **P4_scatter（前任リストを散らす段）**: 辺ごとに `pred[pred_off[q]++] = src` を書く。
  書き込み先は `pred_off[q]` を読み終えるまで決まらないので、1辺ごとに
  「`pred_off` を読む → `pred` に書く」の DRAM 待ちが**直列に2回**並んでいた。
  そこで **2段**にした。32 本先の辺で `pred_off[q]` を取り寄せ、16 本先の辺で
  （もう届いている）その値から `pred` の書き込み先を取り寄せる

**16 本先で読んだ `pred_off[q]` が古くても、答えは変わらない。** その間に同じ行き先の辺があると
カーソルが進み、取り寄せた場所は本当に書く場所から1つ以上ずれる。先読みはヒントなので、
実際の書き込みは本処理がその瞬間のカーソルで行う。ずれた辺は、先読みしなかったときと同じだけ
待つだけ。ただし `pred_off[q16]` は先読みではなく**本当に読む**ので、`q16 < n_all` を確かめてから読む。

同じ `succ` を読み同じ `pred_off` を叩く `P4_count` に比べて、`P4_scatter` は本走で 9.2 倍
（61.8 対 6.7 ns/辺）遅かった。#20 の本走では **13.9 対 6.6 ns/辺（2.1 倍）**になった。
依存で並んでいた待ちが、ほぼ `P4_count` と同じ形に崩れた。

## `moves = NULL;` を入れた

CLAUDE.md「次の実装で必ず直すもの」の1件。`nextBoardInvNormal` の `moves` が `default:` 経路
（`koma` が 1/2/3/5）で未設定のまま抜ける。直後の `if (!moves_num) continue;` で読まれないので
挙動は正しいが、値域解析が `moves` と `moves_num` の相関を追えない処理系では
`-Wmaybe-uninitialized` が出る。#19 は、C に足した行（`gatherPacked` / `gatherDraws`）が
全探索では実行されないことを予測⑤の前提にしていたので見送った。#20 の先読みは C の F1 経路
（`nextBoardSeenNormal`）にも入るので、見送る理由がない。宣言での初期化にした
（コードの行は増やしていない。直前にコメントを3行足した）。

`tests/test_impl_19_c_gather.py` の「まだ残っている」固定は、凍結した `impl/19` を見ているので残した。
