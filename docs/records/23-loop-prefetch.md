## 先読みで何を読んでいるか

174段ループは手数を1つずつ戻しながら、前の段で決まった局面の並び（`frontier`）を先頭から取り、
その前任を CSR（`pred_off` と `pred`）から引いて、前任の残り出次数（`cnt`）と手数（`dtm`）を書き換える。
1つの局面について、読みは

`frontier[i]` → `pred_off[q]` → `pred[e]` → `cnt[p]`・`dtm[p]`

と、**前の読みの値で次の番地が決まる**形で続く。どれも億単位の配列のあちこちを指すので、1つずつ DRAM を待つ。
#20 の前の P4_scatter と同じ形なので、#20 の `predScatter` と同じ2段にした。

- 32 個先の局面で `pred_off[q]` を取り寄せる
- 16 個先の局面で、（もう届いているはずの）`pred_off[q]` から `pred` の読み出し先を取り寄せる

**先読みはヒントで、書く値は変わらない**（`dtm`・`cnt`・`found` は本処理だけが書く）。ただし `frontier[i + k]` と
`pred_off[q16]` は先読みではなく本当に読むので、`i + k < hi` と `q < n_all`（と `pred != NULL`）を先に確かめる。
3段目（`cnt[p]`・`dtm[p]`）は取り寄せていない。lever_scan_2 で3段目まで足した `pf3` は、`pf2` との差が
−0.02 秒（区間 −0.18 … +0.15）で、上乗せが見えなかった。

## 走る前の空きメモリ（記録 #23 から）

`impl/21` 以降は、索引（8 GiB）と発見済み表（4 GiB）に巨大ページが付くことを前提に速くなっている。
lever_scan_2 の1回目は、ノード0のメモリが断片化していて巨大ページが付かず（`thp_fault_fallback` 909）、
P1 が 10.86 秒（#22 の門番では 7.35 秒）になった。**付かなかった本を、走ったあとで捨てて走り直すと、引き直しと同じになる。**
そこで、**走る前にだけ**確かめることにした。

- `tools/run.sh` は `/proc/buddyinfo` の order 9 以上（2 MiB 以上の空きブロック）を足し、両ノードの合計が
  16 GiB（`HUGEFREE_MIN_GIB`）に満たなければ、作業ディレクトリも作らずに止まる
- 通ったら `env.txt` の `hugefree:` と `cache_drop:`、作業ディレクトリの `hugefree.txt` に残す
- 止まったら、人かエージェントが root で `drop_caches` と `compact_memory` を行い、`CACHE_DROP` に何をしたかを入れて
  起動し直す。`run.sh` 自身はキャッシュを落とさない
- 門番は `numactl` でノード0に固定するので、ノード0だけを1本ごとに見る

16 GiB は、同時に要る巨大ページの最大（後退解析の索引 8 GiB。全探索の発見済み表は作り直しの瞬間に 2 ＋ 4 GiB）に
余裕を見た値。

今回の記録:

- 門番を起動する前に手で確かめると、ノード0は 12.80 GiB で届かなかった（ページキャッシュが約 5.6 GB 溜まっていた）。
  root でキャッシュを落として 22.79 GiB に戻した。**この2つの値は記録が残っていない**（手で読んだだけ）。
  残っているのは落としたあとの値で、門番の12本は走る前が 22.90 → 21.51 GiB で全部通った
  （[門番の `logs/`](../../experiments/gate_23_loop_prefetch/logs/) の `console.log` と `<ラベル>_hugefree.txt`）
- 本走は落とさずに通った（ノード0 21.46 / ノード1 23.91 / 合計 45.37 GiB。
  [`hugefree.txt`](../../results/23_loop_prefetch/hugefree.txt)）。落としたのは門番の前の1回だけで、`cache_drop:` にはそれを書いた
- 本走の `thp_fault_fallback` は 0、`compact_stall` も 0（#22 本走は 471）。`AnonHugePages` は発見済み表 4,194,304 kB、
  索引 8,388,608 kB で、全部付いた
