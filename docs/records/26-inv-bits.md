# 記録 #26 で分かったこと

**C の `invBoard()`（先手と後手を入れ替える）の中身を、ループと分岐の無い形に替えた。** 変数はこれ1つ。

**完走 0:02:43 → 0:02:33（196.39× → 208.85×）。−9.76 秒（−6.0%）。**
内訳は全探索 78.43 → 71.40 秒（−7.04）、後退解析 85.18 → 82.45 秒（−2.72）。
`dat/` は #25 と全213ファイルでバイト一致した。

| | #25 まで（`baseline/` から変わっていない） | #26 |
|---|---|---|
| 作り方 | 12マスを1つずつ読み、空きマスを飛ばし、駒のあるマスを反対側（マス i → 11 − i）へ所有者ビットを反転して置き直す | 8バイトの逆順と16ビットの右シフト → 各バイトの上下4ビットの入れ替え → 駒のあるマスだけ所有者ビットを反転（マスク） |
| 大きさ | 87 バイト | 137 バイト |
| 単体の時間（gen_bench） | 46.5 ns | 4.4 ns |

コードは実験 [`gen_bench`](../../experiments/gen_bench/)（記録ではない）の候補 B、
[`invbits.patch`](../../experiments/gen_bench/patches/invbits.patch) のままで、コメントだけを書き直した。
`invBoard()` を呼ぶのは `nextBoardInvNormal()` の冒頭だけで、F1（全探索の全局面、246,803,167 回）と
P2（後退解析の未知局面、99,485,568 回）の両方から呼ばれる。出力は全局面で旧版と1ビットも違わないことを gen_bench で
確かめてあり、生成器の後続の列も順番まで変わらない。`tests/test_impl_26_inv_bits.py` が、コード（コメントを除く）が
「`impl/25` ＋ `invbits.patch`」と一致すること、`invBoard()` を新旧で突き合わせて（端の場合と固定の種の乱数 4 万個）一致すること、
打ち切って回した `dat/` が `impl/25` とバイト一致することを固定している。

## マイクロベンチの外挿はどこまで効いたか

gen_bench は生成器（`nextBoardInvNormal()`）だけを取り出し、局面の種類ごとに温めて測った。その差に本番の件数を掛けたのが
「換算」で、発見済み表への挿入（F1）や索引引き（P2）との重なりは入っていない。

| | gen_bench の換算（生成器だけ） | 門番 | 割合 | 1局面あたり |
|---|---|---|---|---|
| F1 | −9.72 秒 | −7.29 秒 | **75%** | −29.5 ns（生成器の中では 3種類とも −38〜−40 ns） |
| P2 | −3.98 秒 | −3.30 秒 | **83%** | −33.2 ns（同、未知局面で −40.0 ns） |
| 計 | −13.70 秒 | −10.59 秒 | **77%** | |

**生成器だけの差の 4 分の 3 以上が本番でも出た。** 向きと桁は換算どおりで、目減りは 2 割前後。
F1 のほうが目減りが大きい。F1 は1局面ごとに後続を発見済み表へ挿入し（#20 の先読み入り）、P2 は索引を引く。
表を引く待ちのあいだに、反転の計算がいくらか隠れていたと読めるが、どちらの待ちにどれだけ隠れたかは分けていない。

外挿が効いた理由として考えられるのは、`invBoard()` の旧版の重さの多くが、空きマスを飛ばす分岐の読み違いだったこと
（局面ごとに空きの並びが違うので当たらない）。読み違いはパイプラインを捨て直すので、メモリの待ちの陰には隠れにくい。
これは測っていない（性能カウンタは取っていない）。
