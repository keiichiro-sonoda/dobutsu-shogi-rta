# 記録 #32 で分かったこと

**#30 の `rankOf()` に `__attribute__((always_inline))` を付け、呼び出し元へ必ずインライン展開させた。** 変数はこれ1つ（#31 は欠番）。
ランクの計算の中身は変えていない。`.h` / `.py` / `Makefile` は #30 とバイト同一（`Makefile` のフラグで全体の展開の基準は変えていない）。

**完走 0:02:14 → 0:02:15（238.08× → 237.64×）。+0.25 秒。** 内訳は全探索 55.94 → 55.67 秒（−0.27）、後退解析 79.02 → 79.54 秒（+0.52）。
本走は1本なので、この差を改善とも退行とも読まない（下の門番を見る）。`dat/` は #30 と全213ファイルでバイト一致した（#30 本走の `dat/` と直接 `diff -rq`）。

**目的は、次の記録（索引のランク化の測り直し）の土台を作ること。** 門番 #31（欠番）では、後退解析の索引をランクで引くようにしたところ、
P2 が +1.48 秒になった。後続ごとに `rankOf()` の `call` が足されたぶんと読めたので、先に `rankOf()` を展開させる。

## 何が変わったか

#30 の `rankOf()` は `static inline` だが、`gcc -O2` が大きさの見積もりで展開せず、後続ごとに `call` していた。

| | #30 | #32 |
|---|---|---|
| `rankOf` への `call` | 3（`nextBoardSeenNormal`・`seenInsert`・`seenContains`） | **0**（`rankOf` の本体も `.so` から消えた） |
| `nextBoardSeenNormal` の命令 | 90 | 237 |
| `rankOf` から呼ぶ小さな関数（`rankFindKoma`・`rankSqueeze`・`rankHalf`） | 展開済み（`call` 無し） | 同じ |

数え方は門番の [`calls.py`](../../experiments/gate_32_inline_rank/calls.py) / [`insns.py`](../../experiments/gate_32_inline_rank/insns.py)、
門番の本が作った `.so` での表は [`calls.txt`](../../experiments/gate_32_inline_rank/logs/calls.txt) と
[`insns.txt`](../../experiments/gate_32_inline_rank/logs/insns.txt)。

**関数の番地は大きく動いた**（[`symbols.txt`](../../experiments/gate_32_inline_rank/logs/symbols.txt)）。`rankOf` の本体（140 命令）が消えて前の関数が
詰まり、展開した先が大きくなって後ろの関数が押し出された: いちばん熱い `nextBoardInvNormal` と `nextBoardIndexNormal` は −560 バイト、
`expandRound`・`retreatStep`・`buildSuccRange` は +1,632 バイト。

`tests/test_impl_32_inline_rank.py` が、`.c` の差が `rankOf()` の定義の行と直前のコメントだけであること、`rankOf`（と小さな関数）への `call` と
`rankOf` の本体が無いこと、打ち切って回した成果物が #30 とバイト一致すること（それぞれの `Makefile` の `.so` で）を固定している。
門番 #31 のパッチ（[`rank_index.patch`](../../experiments/gate_31_rank_index/patches/rank_index.patch)）は、この版の上に fuzz なしで当たる
（`patch --dry-run`。当てたものも警告なくビルドでき、`rankOf` への `call` は無い）。

`call` を消した得の大半は、もともと DRAM の待ちに隠れていたと読める（#27 で `normalBoard()` の `call` を消したときの約 2 ns とは違った）。

### 止める条件3に掛かり、本人の判断で本走した

**P2 が +0.63 秒（区間 +0.35 … +0.90）、ほぼ全部ユーザー時間**で、回す前に決めた「動かないはずの段が区間の外れで 0.2 秒以上動いたら、本走の前に
原因を調べる」に掛かった。この版の P2 は `rankOf()` を使わない。P2 の熱い経路の関数（`buildSuccRange`・`nextBoardIndexNormal`・
`nextBoardInvNormal`・`normalBoard`・`invBoard`）を2腕で比べると、**命令の並びは同じで（番地からの相対の数値を除く）、置き場所だけが違った**。
P2 で実行する命令は変わっていないので、**+0.63 秒は関数の置き場所（命令の取り込みや分岐予測の表の当たり方）の効果**と読める。
どの関数の置き場所が効いたかは分けていない。同じ理由で、F1 の −0.41 秒にも置き場所の効果が混ざっている可能性がある
（`nextBoardInvNormal` は F1 でも通る）。

これを本人に報告し、「このまま本走して記録にする」と決めてもらった（ほかの選択肢は、欠番にして次の記録と一緒に入れる、置き場所を調べてから決める、
だった）。門番の完走の差（+0.36）は区間が 0 をまたいでいて、本走の +0.25 秒もその中にある。

置き場所の振れがこの大きさで出たのは、#25 の門番の P2 −0.84 秒（置き場所か `cnt` の巨大ページか分けていない）、#30 の門番の P2 −0.24 秒
（原因を分けていない）に続く。小さい改善を測るほど邪魔になる。
