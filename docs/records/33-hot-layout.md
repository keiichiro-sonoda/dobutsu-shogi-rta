# 記録 #33 で分かったこと

**熱い関数12個を `.text` の前の専用の区画に並べ、ほかの関数を変えても動かないようにした。** 命令は変えていない。
`.c` / `.h` / `.py` は #32 とバイト同一で、変えたのは `Makefile` の `gcc` 行に足した2つ（`-ffunction-sections` と `-Wl,-T,hot_layout.ld`）と、
リンカースクリプト [`hot_layout.ld`](../../impl/33_hot_layout/hot_layout.ld) だけ。

**目的は速さではなく、以後の門番が「変えたコードの効果」だけを測れるようにすること**（#9 が「目的はピーク RSS」だったのと同じ扱い）。
#32 の門番で、実行する命令が同じ P2 が、関数の番地がずれただけで +0.63 秒（区間 +0.35 … +0.90）動いた。残っているレバーは1つあたり
1秒前後かそれ以下が多く、C を1か所変えるたびに後ろの関数がずれると、レバーの効果と置き場所のぶんを分けられない。

**完走 0:02:15 → 0:02:14（237.64× → 238.66×）。−0.58 秒。** 内訳は全探索 55.67 → 55.63 秒（−0.05）、後退解析 79.54 → 79.00 秒（−0.53）。
本走は1本なので、この差を改善とも退行とも読まない（判定は下の門番）。`dat/` は #32 と全213ファイルでバイト一致した。

## 何を変えたか

`-ffunction-sections` で関数ごとに `.text.<名前>` の区画を作らせ、リンカースクリプトで熱い関数だけを拾って、既定のリンカースクリプトの
`.text` の前に足した区画 `.text.hot_layout` に並べる（`INSERT BEFORE .text`）。

| | #32 | #33 |
|---|---|---|
| 熱い関数の置き場所 | `.text` の中、C のファイルの順（ほかの関数と混ざる） | `.text` の前の `.text.hot_layout`（先頭 `0x2000`） |
| 区画の先頭 / 関数の先頭 | — / 16 バイトの区切り | **4 KiB / 64 バイトの区切り** |
| 熱い関数の並び | C のファイルの順 | 同じ順（#32 の `.so` と同じ） |
| 命令 | — | 全32関数 2,932 命令で、並びと命令ごとのバイト数が同じ（番地の数値を除く） |

`__attribute__((hot))` と `section` 属性は使わなかった。`hot` は最適化を強め、`section` 属性は gcc の関数の分割を止めるので、どちらも
命令が変わりうる。`-ffunction-sections` とリンカースクリプトなら C を触らずに済み、命令が同じことを全関数で確かめられる。

### 熱い関数（`perf` で確かめた）

F1・P1・P2・P4・174段ループで実行される C の関数: `invBoard`・`nextBoardInvNormal`・`indexBuild`・`nextBoardIndexNormal`・
`nextBoardSeenNormal`・`predCount`・`predScatter`・`expandRound`・`retreatStep`・`buildSuccRange`・`gatherPacked`・`gatherDraws`。

#32 を門番と同じくノード0に固定して1本、`perf record -F 499` で測った（標本 68,370 個、[`perf_top.txt`](../../experiments/gate_33_hot_layout/logs/perf_top.txt)）。
`animal_shogi.so` が 85.93%（`nextBoardInvNormal` 28.98%、`nextBoardIndexNormal` 16.03%、`nextBoardSeenNormal` 15.28%、`retreatStep` 8.34% …）、
カーネル 10.36%、libc 3.27%、Python 0.41%。上の12個はすべて標本を持つ。**初めの読みに入れていた `normalBoard` は標本 0 で、一覧から外した。**
呼び出し元の `nextBoardInvNormal` に全部インライン展開されていて、外にある実体は Python から `ctypes` で引けるだけで、解析の中では実行されない。
libc の `memcpy`・`memset`・`memmove`（`.plt` 経由）は固定の外。

`perf` は計測機の `perf_event_paranoid` を一時的に 4 → 1 にして使い、測ったあと 4 に戻した。`perf.data` は計測機の名前を含むので残していない。

## 固定できる範囲とできない範囲

- **熱くない関数を変えても、熱い関数は1バイトも動かない。** 熱くない関数は後ろの `.text` に入る。区画の先頭を 4 KiB に揃えたので、
  前の `.plt` が伸びても（新しい libc の関数を呼ぶなど）区画は動かない。前の区画が 4 KiB の区切りを越えるほど伸びたときは、区画は
  4 KiB の倍数で動き、ページの中の位置は変わらない
- **熱い関数そのものを変えたら、後ろの熱い関数はずれる。** ずれは 64 バイト単位になり、命令の読み込みの区切りに対する位置は保たれる。
  解読済み命令の置き場（uop キャッシュ）や分岐予測の表の当たり方までは保証できない
- 実行時の番地は、読み込む位置（4 KiB の倍数）だけずれる。ページの中の位置と、熱い関数どうしの相対の位置は変わらない
- 熱い関数ごとに 4 KiB に揃える案は採らなかった。全部の先頭が L1 命令キャッシュの同じ組に集まって取り合うため
- **熱い関数を足したのに `hot_layout.ld` に書き漏らすと、その関数は `.text` に入って固定されない。** テストが見られるのは
  「一覧の関数が区画にあるか」までなので、一覧は人が保つ（CLAUDE.md に1行足した）

## 詰め物の検査（時間を測らずに、番地で）

`.c` に熱くない関数（N バイトの `nop` を持つだけ。呼ばれない）を足して両方の `Makefile` でビルドし、熱い関数12個のうち番地が動いた数を数えた
（[`layout.txt`](../../experiments/gate_33_hot_layout/logs/layout.txt)。`tests/test_impl_33_hot_layout.py` が固定している）。

| 足した場所 | #32 の作り方 | #33 |
|---|---|---|
| ファイルの頭（8・24・40・100・1000 バイト） | **12個全部が動く**（末尾の関数は +16・+32・+48・+112・+1008） | 0 |
| `nextBoardSeenNormal` の前（同） | 後ろの8個が動く | 0 |
| 末尾（同） | 0 | 0 |
| まだ使っていない libc の関数（`getpid`）を呼ぶ関数を末尾に | **12個全部が動く**（`.plt` が伸びる） | 0 |

#32 の作り方では、ファイルの末尾に足したときしか熱い関数が動かずに済まない。#26〜#32 の記録はどれも C の途中かコンパイラのフラグを変えていて、
そのたびに熱い関数の番地が動いていた。
