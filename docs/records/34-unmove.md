# 記録 #34 で分かったこと

**後退解析を「一手前を直接作る」作りに替えた。** #33 までの後退解析は、全探索の結果に連番を振り（P0）、番号を引く索引を作り（P1、8 GiB）、
未知局面の後続を全部作り（P2）、向きを逆にして前任の表に並べ替え（P4）、174段ループでその表を引いていた。#34 では、全探索が展開した局面ごとに
種類とキャッチ抜きの数をランクを添字にした 1 バイトの配列に書いておき、後退解析では決まった局面から手を1つ戻して前任をその場で作る。
**P0・P1・P2・P4 と 174段ループが無くなった。** 実験 [`unmove_bench`](../../experiments/unmove_bench/) から [`forward_prep`](../../experiments/forward_prep/) までの7本で
1つずつ確かめた形を実装に移したもの。

**完走 0:02:14 → 0:02:04（238.66× → 257.73×）。−9.96 秒。** 内訳は全探索 55.63 → 64.17 秒（＋8.54。準備を書く分）、後退解析 79.00 → 60.50 秒（−18.50）。
**ピーク RSS 14.88 → 3.69 GB。** [門番](../../experiments/gate_34_unmove/)では完走 **−11.21 秒（区間 −11.78〜−10.64）**。
後退解析の採番順が変わったので、`dat/` はバイト一致ではなく、ファイルの名前と件数が #33 と全213ファイルで同じ・オラクル174行・指紋で見た。

## 何を変えたか

### 全探索の側（`forward_prep` の腕 `carry` そのまま、に1つ足した）

- `nextBoardSeenNormal` が呼ぶ生成器を、`nextBoardInvNormal` の写しに「相手の利きの一覧」（[`attack_count`](../../experiments/attack_count/) の B1′）を足した
  `nextBoardInvNormalNC` に替えた。局面の頭で相手の駒の利きの一覧を1回作り、後続ごとにビット演算で「その後続がキャッチ局面か」を見て、
  キャッチ局面でない後続の数（キャッチ抜きの数）を数える。後続の列と順番、戻り値は変えない
- 展開した局面の種類と数を、ランクを添字にした 1 バイトの配列（855,232,344 バイト、巨大ページ）に書く: 0 到達しない / 1〜49 未知局面（キャッチ抜きの数 ＋ 1）/
  0xFE トライ負け / 0xFF キャッチ
- 書く場所のランクは計算し直さず、後続として見つけたときのランクを、待ち行列に盤面と同じ区切りで積んで使う（`queue_rank`）。`forward_prep` で、計算し直す形より
  F1 が 3.1 秒軽かった。盤面の待ち行列の区切り（500万件ずつ）と並びは変えない
- **実験から足したのは1つだけ**: キャッチ抜きの数が 0 の未知局面（6,254,985 個。後続がキャッチ局面だけなので手数 2 の負け）を、見つけた順に C の列に積む。
  後退解析ではランクから盤面に戻せないので、手数 2 の段のフロンティアに足すにはここで持つしかない（実験の試作では、初期化で全未知局面の後続を作り直して数えていた）

全探索の側の `dat/`（キャッチ局面とトライ負け）は #33 とバイト一致する。

### 後退解析の側

| #34 の段 | 中身 | 対応する #33 までの段 |
|---|---|---|
| `U_init` | 準備の配列から手数の配列（ランクを添字にした 1 バイト）を作り、準備の配列をその場で残りの数に読み替える。キャッチ局面は手数 1、トライ負けは 0、キャッチ抜きの数が 0 の未知局面は 2、到達しない番号に「到達しない」の印 | P0・P1・`R_dtm`（と P2・P4 の配列の確保） |
| `U_loop` | 手数 nd − 1 で決まった局面から、逆向きの生成器（[`unmove_prune`](../../experiments/unmove_prune/) の絞った版）で前任を作り、手数を決め、手数ごとに `dat/` に書く | P2・P4・174段ループ（手数ごとの書き出しを含む） |
| `U_draw` | 未知局面の列を順に見て、ランクで手数を引き、未定のもの（引き分け）を集める | `R_draw` |
| `U_uk` | 引き分けを書く | `R_uk` |

- **キャッチ局面からは前任をたどらない。** 残りの数を最初からキャッチ抜きで数えておけば、答えは変わらない（負けに決まる局面の手数は「1 ＋ 後続の勝ちの手数の最大」で、
  キャッチ局面は手数 1 の勝ちなので最大を決めない。[`unmove_catch`](../../experiments/unmove_catch/) の README に導き方）
- **前任を作る前に絞る。** 前任がキャッチ局面になる戻し方は、盤を見るだけで分かるので作らない（どの駒も1マスしか動かないので、手を戻しても戻した駒以外の利きは
  変わらない）。素朴な逆向きの生成器より候補が 47.1% 減る
- 前任の候補は手数の配列だけで「未定の未知局面か」を見る（実験の試作では種類の表を先に引いていたが、手数の配列に「到達しない」の印を入れたので要らない）
- **P0 は消した。** P0 は全探索の結果に連番を振る段で、連番は索引・後続の列・前任の表を引くためのものだった。#34 の後退解析はランクで配列を引くので連番が要らない。
  キャッチ局面の列（1.1 GB）は後退解析の入口で手放し、未知局面の列は引き分けを拾うときに読み、トライ負けの列は最初のフロンティアにする
- [`unmove_flip`](../../experiments/unmove_flip/) の反転を1回にする版は遅かったので使わない。キャッチの先行判定などほかの工夫も入れていない
- 消した関数: `indexBuild`・`indexFree`・`nextBoardIndexNormal`・`predCount`・`predScatter`・`retreatStep`・`buildSuccRange`・`gatherPacked`・`gatherDraws`

### 熱い関数の置き場所

`hot_layout.ld` の一覧を作り替えた（9個: `invBoard`・`nextBoardInvNormal`・`nextBoardInvNormalNC`・`nextBoardSeenNormal`・`expandRound`・`unmoveCandidates`・
`unmoveInit`・`unmoveStep`・`unmoveDraws`）。詰め物の検査は [`tests/test_impl_34_unmove.py`](../../tests/test_impl_34_unmove.py) に写した。熱くない関数を足しても
熱い関数の番地は動かない。まだ使っていない libc の関数を呼んで `.plt` を伸ばすと、#34 では前の区画が 4 KiB の区切りをまたいで区画ごと 1 ページ後ろへずれる
（ページの中の位置は動かない。#33 のノートに書いた「区切りを越えるほど伸びたとき」に当たる）。

## 答えの検査

**後退解析の採番順（局面を決める順）が変わったので、後退解析の側の `dat/` はファイルの中の並びが #33 と違う**（後退解析の側の182ファイルのうち、#33 とバイトまで
同じものは1個）。CLAUDE.md の「保存形式を変えると採番順は必ず動く」のとおり、次で見た（[`bytecompare.txt`](../../results/34_unmove/bytecompare.txt)）。

- 全探索の側の31ファイル（`lose000te_*` と、キャッチ局面を書く `win001te_000`〜`028`）が #33 本走とバイト一致
- ファイルの名前の集合（213個）と、ファイルごとの件数が #33 本走と同じ
- オラクル174行（[`verify.txt`](../../results/34_unmove/verify.txt)）、指紋176項目（[`fingerprint.txt`](../../results/34_unmove/fingerprint.txt)）、サイズ検算（[`sizecheck.txt`](../../results/34_unmove/sizecheck.txt)）

打ち切った全探索の上では、#34 の答えは #33 と同じにならない（#33 は「索引の外の後続」を出次数に数えて決まらないまま残すが、#34 はキャッチ局面の形の後続を
最初から数えないので、まだ展開していないキャッチ局面の形の後続だけが残った局面が決まりうる）。だからテストは #33 とではなく、同じ規則を Python で素直に書いた
参照解と比べる。最後まで回した答えは、門番の12本と本走でオラクルと指紋が通った。

## 言えないこと

- `U_loop` が試作のループより速かった理由（種類の表を引かなくなった分か、ほかの差か）は分けていない
- minor fault の減り方が予測より小さかった理由は分けていない
- 本走は1本で `numactl` で固定していない。門番の −11.21 秒と本走の −9.96 秒の差は、固定の有無と本数の違いを含む
- 後退解析の側の `dat/` は #33 とバイト一致しない（並びが違う）。答えが同じことは、手数ごとの件数（オラクル）と、ファイルごとの件数と、指紋で見た。
  指紋は異なる集合でも同じ値になりうるので、集合の完全一致の証明ではない

## 次

段の顔ぶれが変わった。大きい順に **F1 展開 58.5 秒（47.0%）、`U_loop` 56.8 秒（45.6%）**、F6 2.4 秒、`U_draw` 1.8 秒、`U_init` 1.7 秒、F5 1.6 秒。
#33 までのレバーのうち、P1・P2・P4・174段ループに効くもの（索引をランクで引くなど）は段ごと無くなった。残っている候補（[`docs/levers.md`](../levers.md)）:

- **`U_loop` の到達しない候補を減らす**: 残った候補の 14.3% が到達しない局面で捨てられている。全部ただで捨てられても上限 3.4 秒（`unmove_prune`）
- **反転を1回にする**: `unmove_flip` では遅くなった（理由は分けていない）。`perf` で分けてから
- **引き分けを拾う区間**（`U_draw` 1.8 秒）: 未知局面のランクを持っておけば、ランクの計算が要らなくなる
- **キャッチの先行判定**（F1）: B1′ の一覧と同じ部品で入れられる
- malloc の mmap のしきい値、待ち行列の塊の大きさ（どちらも全探索）
