実験 [`bitboard_gen`](../../experiments/bitboard_gen/) の腕 `bb_nibble` をそのまま実装に移したもので、`.so` は実験の腕とバイト一致する。

**完走 0:02:04 → 0:01:54（257.73× → 281.75×）。−10.63 秒。** 内訳は全探索 64.17 → 53.71 秒（−10.46。ほぼ F1）、後退解析 60.36 → 60.19 秒。
[門番](../../experiments/gate_35_bitboard/)では完走 **−10.26 秒（区間 −10.73〜−9.79）**。

バイト一致の鎖が、#34 との間でつながった。

## 何を変えたか

`impl/34_unmove` に [`experiments/bitboard_gen/patches/bb_nibble.patch`](../../experiments/bitboard_gen/patches/bb_nibble.patch) を当てただけ。変わったのは
`nextBoardInvNormalNC()` と、行き先の表・それを作る `dstTableBuild()` だけで、`.py`・`Makefile`・`hot_layout.ld`・逆向きの生成器・`nextBoardSeenNormal()`・
`normalBoard()`・`invBoard()`・ランクは #34 とバイト同一（[`tests/test_impl_35_bitboard.py`](../../tests/test_impl_35_bitboard.py) が固定している）。

### 生成器の形

1. `invBoard` の直後に、盤から集合を1回作る。マス k をビット `4k`（各4ビットの最下位）に置く形で、手番側の駒 `(b >> 3) & 0x111111111111`、
   駒がいるマス `(b | b>>1 | b>>2 | b>>3) & 0x111111111111`。`ctz` の値がそのまま今までの `src` / `dst`（0, 4, …, 44）になる
2. 手番側の駒のマスを `ctz` で番号の小さい順に取り出し、`koma = getKoma(b, src)` を添字に行き先の表を引く（駒の種類の `switch` は無い）。
   行き先の集合 ＝ 表 ∧ ¬手番側の駒。自分の駒のマスと、盤の外・左右の回り込みは、表と AND で消える
3. 行き先を `ctz` で番号の小さい順に取り出す。相手のライオンなら今までどおり走査の途中で `return 0`。取るか動くかは分岐にせず、
   空きの行き先も `delKomaDouble` で消してから、持ち駒の更新を「行き先に駒があるとき」のマスクで掛ける
4. トライ（相手のライオンが `src % 16 == 12` の段）はビットで判定し、全部の駒を見たあとで `-1`。打つ手は、空きマスを番号の小さい順に並べてから今までのコードのまま
- **行き先の表は、今までの判定（移動量の表の順に、盤の外・左右の回り込み2条件を当てる。ひよこは奥の端なら動けない）を全通り回して作る。**
  `.so` を読み込んだときに1回作る（`__attribute__((constructor))`。生成器に「表があるか」の分岐を足さない）。表は 1,536 バイトの `.bss`

### 後続の順番を保つ仕組み

今までの生成器は、マスを `src` = 0, 4, …, 44 の順に見て、手番側の駒ならその駒の手を移動量の表の順に出し、空きマスは控えて最後に打つ手を出していた。
移動量の表はどれも昇順なので、1つの駒の行き先は番号の小さい順に出る。新しい生成器は「手番側の駒のマスを番号の小さい順 → その駒の行き先を番号の小さい順」に
取り出すので、**後続の列は並びまで同じ**になる。駒の種類ごとに集合をまとめて処理すると並びが入れ替わるので、そうはしていない。

### 機械語（`bitboard_gen` の `check_asm.py` を `impl/35_bitboard` に当てた。[`logs/asm_impl35.txt`](../../experiments/gate_35_bitboard/logs/asm_impl35.txt)）
