# 記録 #36 で分かったこと

**後退解析の逆向きの生成器 `unmoveCandidates()` をビットボード型にした。** #35 までの逆向きの生成器は、戻す駒を探して 12 マスを1つずつ見て（直前に指した側 X の駒か）、
駒の種類の `switch` で移動量の表を選び、戻し方ごとに「元のマスが盤の外か・端の回り込みか・空いているか・戻した先から相手のライオンに利くか」を分岐で調べていた。
#36 では、元のマスの候補をビット集合と表引きで出し、X の駒のマスもビット集合で取り出す。実験 [`unmove_gen`](../../experiments/unmove_gen/) の腕 `bb_unmove` をそのまま実装に移したもので、
`.so` は実験の腕とバイト一致する。

**完走 0:01:54 → 0:01:40（281.75× → 320.25×）。−13.71 秒。** 内訳は全探索 53.71 → 54.25 秒、後退解析 60.19 → 45.95 秒（`U_loop` 56.65 → 42.27 秒）。
[門番](../../experiments/gate_36_bb_unmove/)では完走 **−14.98 秒（区間 −15.38〜−14.58）**。**`dat/` は #35 本走と全213ファイルでバイト一致した**
（[`bytecompare.txt`](../../results/36_bb_unmove/bytecompare.txt)。#34・#35 とつながったバイト一致の鎖が続く）。

（[`tests/test_impl_36_bb_unmove.py`](../../tests/test_impl_36_bb_unmove.py) が固定している）。`CLAUDE.md` の「次の実装で必ず直すもの」は空だった。

### 逆向きの生成器の形

マス s はビット s（各4ビットの最下位）に置く（#35 の全探索の生成器と同じ形）。

1. 局面（手を指した直後の盤 nb）ごとに、空きマスの集合を `(nb | nb>>1 | nb>>2 | nb>>3)` から1回作る。王手をかけている駒の集合 A を作るところは今までのまま
2. A が空なら、X の駒（持ち主のビット 0b1000）のマスを `(nb >> 3) & 0x111111111111` から `ctz` で番号の小さい順に取り出す（12 マスのループと「X の駒か」の分岐が消える）
3. 駒ごとに: 打った手を戻せるかは「打てる駒のビットの表」と持ち駒の数で見る。駒を動かした手の元のマスは
   **`g_usrc[駒][d]` ∧ 空きマス ∧ ¬`g_uatk[駒][L]`**（L は相手のライオンのマス。`g_uatk` は置くとライオンに利くマス）で、盤の外・端の回り込み・空いているか・戻した先から利くかの
   分岐がまとめて消える。にわとりが端の行にいるときの「ひよこが成った」を戻す候補は `g_upromo` を同じ形で引く（分岐が1つ残る）
4. 元のマスごとに「取っていない版 → 取った駒の4種類」を出すところ、正規形だけを残すところ、q と鏡像の q の両方から戻すところは今までのまま
- **表は今までの判定をそのまま全通り回して作る**（`unmoveSrcTableBuild`。`s = d - moves[i]`、盤の外、端の回り込み2条件、ひよこの特別扱い）。今までの `unmoveTableBuild` の中で
  1回だけ呼ぶ。`noinline, cold` にして生成器に展開させない。表は 3 × 1,536 バイトの `.bss`

### 候補の並びを保つ仕組み

今までの並びは、X の駒のマス d を番号の小さい順 → d ごとに「打った」→「動かした」元のマス s → s ごとに「取っていない版 → 取った駒の4種類」。**移動量の表はどれも昇順で
`s = d - moves[i]` なので、s は番号の大きい順に出ていた。** そこで s は `63 - clzll`（`lzcnt`）で大きい順に取り出す（`ctz` で取り出すと逆になる）。にわとりが端の行にいるときの
「ひよこが成った」候補（`s = d + 4`）は、ほかの s の**あと**に出す（にわとりの普通の戻し方にも同じ `s = d + 4` があり、そちらが先）。1つの駒の移動量の表に同じ s は2回出ないので、
ビット集合にしても候補は落ちない。**前任の候補の列は並びまで #35 と同じ**なので、後退解析が局面を決める順も、`dat/` の並びも変わらない。
