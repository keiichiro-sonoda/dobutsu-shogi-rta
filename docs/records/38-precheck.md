利きの一覧を作り、手番側の駒の行き先を番号の小さい順に作っていき、相手のライオンに当たったところで `return 0` していた。#38 は、反転の直後・利きの一覧より前に
「取れるか」だけを先に決め、取れれば後続を作らずに `return 0` する。実験 [`f1_select_catch`](../../experiments/f1_select_catch/) の腕 `precheck` をそのまま実装に移したもので、
`.so` は実験の腕とバイト一致する。

**完走 0:01:29 → 0:01:25（357.73× → 374.92×）。−4.12 秒。** 内訳は全探索 53.63 → 49.65 秒（F1 47.95 → 43.97 秒）、後退解析（完走 − 全探索）36.19 → 36.05 秒。
[門番](../../experiments/gate_38_precheck/)では完走 **−4.23 秒（区間 −4.83〜−3.63）**。ただし生成器だけのベンチの換算（F1 −7.49 秒）の 56% しか出なかった。

## 何を変えたか

`impl/37_mirror1` に [`experiments/f1_select_catch/patches/precheck.patch`](../../experiments/f1_select_catch/patches/precheck.patch) を当て、前提を述べるコメントを3行足しただけ
（コメントを足しても `.so` は実験の腕とバイト一致した）。変わったのは生成器 `nextBoardInvNormalNC` と、表を作る `dstTableBuild`（表 `g_reach` を足す）と、足した `static inline` の
`komaSet` だけで、`.py`・`Makefile`・`hot_layout.ld`・`nextBoardSeenNormal()`・`normalBoard()`・逆向きの生成器・`unmoveStep()`・ランクは #37 とバイト同一
（[`tests/test_impl_38_precheck.py`](../../tests/test_impl_38_precheck.py) が固定している）。`komaSet` はインライン展開され、関数の記号は #37 と同じ。`CLAUDE.md` の「次の実装で必ず直すもの」は空だった。

### 先行判定の形

1. 相手のライオンのマス L を出す。`komaSet(b, k)` は、盤を `k` と XOR して 0 になるマスの集合（今の `try_flag` の作りと同じ）で、`L = ctz(komaSet(b, LION1)) / 4`
2. 駒の種類（`CHICK2`〜`CHICKEN2` の5つ）ごとに、表 `g_reach[駒][L]`（その駒が L へ動ける元のマスの集合）と `komaSet(b, 駒)`（手番側のその種類の駒がいるマスの集合）の AND を取り、
   5つを OR でまとめる。0 でなければ `return 0`（`*non_catch` は 0 のまま。今と同じ戻り値）
- **ループが無い。** 駒の種類は5つで固定なので、局面ごとに回数が変わる取り出しも無く、条件分岐は `if (hit) return 0;` の1つだけ（命令 80）
- **`g_reach` は `g_dst` を裏返して作る**（s から L へ動ける ⟺ L ∈ `g_dst[駒][s]`）。本体が `return 0` するのは「手番側の駒のどれかの行き先の集合 `g_dst[駒][src] & ~own` に L がある」
  ときなので、先行判定が当たる局面と本体が `return 0` する局面は同じになる。表は `.bss` の 1,536 バイトで、`dstTableBuild()` の最後で1回作る（表を作る関数を新しく足すと記号が増えるため）
- 先行判定のあとの本体は #37 のまま（本体の `if (dst_koma == LION1) return 0;` も残した。先行判定が外れた局面では、本体でキャッチに当たることはないが、消すのは別の変更）
- **前提: 反転したあとの盤に相手のライオン（`LION1`）がちょうど1ついること。** いないと `komaSet(b, LION1)` が 0 になり、`__builtin_ctzll(0)` は未定義動作。到達可能な局面には必ずいる
  （ライオンを取った局面は生成器に渡らない）。`f1_select_catch` の一致の検査で全 246,803,167 局面を通し、テストが打ち切った走行の展開する全局面で確かめる。C の先行判定の上にも書いた

### `gen_bench` の候補 A から何が変わったか

[`gen_bench`](../../experiments/gen_bench/) の候補 A（#25 の生成器の上）は、相手のライオンのマスをループで探し（最大 12 マス）、周り8方向を分岐で見ていて、判定が外れる局面

払うどころか軽くなった（理由は確かめていない）。キャッチ局面は 230.5 → 33.1 cycles。

## 言えないこと

- **ベンチの換算の 56% しか出なかった理由**（上の2つの候補はどちらも確かめていない）。本物の F1 でキャッチ局面と外れる局面がそれぞれどれだけ縮んだかは、計装では分けられない

- 本体に残した `if (dst_koma == LION1) return 0;` を消したときの差は測っていない
