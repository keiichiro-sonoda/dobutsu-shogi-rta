# 記録 #40 で分かったこと

**後退解析のループ `U_loop` で、手数の配列 `g_dtm` の先読みを1局面先にした。** 実験 [`perf_39`](../../experiments/perf_39/) で、#39 の `U_loop`（30.6 秒）のうち
約 6.0 秒が `unmoveStep` の1行（未定の候補をふるう `g_dtm` の読み）に付いていた。番号を出して `prefetchw` したすぐあとに同じ局面の候補を読むので、先読みが間に合っていなかった。
実験 [`dtm_ahead`](../../experiments/dtm_ahead/) の腕 `ahead1` をそのまま実装に移したもので、`.so` は実験の腕とバイト一致する。

**完走 0:01:21 → 0:01:18（391.89× → 409.16×）。−3.46 秒。** 内訳は全探索 47.70 → 47.08 秒、後退解析（完走 − 全探索）34.29 → 31.45 秒（`U_loop` 30.63 → 27.90 秒）。
[門番](../../experiments/gate_40_dtm_ahead/)では完走 **−2.66 秒（区間 −3.11〜−2.20）**、`U_loop` −2.66 秒（区間 −2.86〜−2.46）で、ほかの段は ±0.04 秒の中。
**`dat/` は #39 本走と全213ファイルでバイト一致した**（[`bytecompare.txt`](../../results/40_dtm_ahead/bytecompare.txt)）。

## 何を変えたか

`impl/39_rank_lean` に [`experiments/dtm_ahead/patches/ahead1.patch`](../../experiments/dtm_ahead/patches/ahead1.patch) を当てただけ。変わったのは `unmoveStep()` の中だけで、
`.py`・`Makefile`・`hot_layout.ld`・ヘッダ・ほかの関数は #39 とバイト同一（[`tests/test_impl_40_dtm_ahead.py`](../../tests/test_impl_40_dtm_ahead.py) が固定している）。
関数の記号は #39 と同じ。`CLAUDE.md` の「次の実装で必ず直すもの」は空だった。

`unmoveStep` は、手数 nd − 1 で決まった局面（フロンティア）を1つずつ取り、前任の候補を作り（逆向きの生成器 `unmoveCandidates`）、候補ごとに番号を出して `g_dtm` の行を
先読みし（`rankOf` と `prefetchw`）、手数が未定の候補だけを残し（ふるう）、残った候補を決める（odd の段では `g_prep` の残りの数を減らして 0 になったら決める）。

- **#39 まで**: 局面 i について「候補を作る → 番号と先読み → ふるう → 決める」。先読みから読みまでの間は、残りの候補の `rankOf` だけ
- **#40**: 候補と番号の配列を2組（`cand2[2][UNMOVE_MAX]`・`r2[2][UNMOVE_MAX]`。スタックが 16 → 32 KiB）持ち、局面 i は組 `i & 1` を使う。
  ループの前で先頭の局面の候補を作って先読みを頼み、i 回目は **局面 i + 1 の候補を作って番号と先読みを済ませてから、局面 i をふるい、決める**。最後の局面では次を作らない。
  局面 i + 1 の行を頼んでから読むまでの間に、局面 i のふるう・決めると、局面 i + 2 の生成器と `rankOf`（局面1つ分、約 1,000 cycles）が入る
- ふるう・決めるの中身は1文字も変えていない（`g_prep` の先読みもふるうループの中のまま）。`g_dtm` の先読みの引数も同じ。`out[0..2]` の意味とエラーの返り値（`-2`・`-4`）も同じ

### 決める順が変わらない理由

候補を作ることと番号を出すことは、盤と静的な表だけで決まり、`g_dtm` も `g_prep` も読まない。先読みは中身を変えない。局面 i をふるう・決めるのは、#39 と同じく局面 i − 1 を
決め終えたあとで、ふるう・決めるのコードも同じ。だから `g_dtm`・`g_prep` を読み書きする順は #39 と1つも変わらず、決める順も `found` に積む順も同じになる。
途中で返るとき（`found` があふれる `-2`、残りの数を 0 から減らそうとする `-4`）も、先に作った局面 i + 1 の候補はどの配列にも書かないので、返す値と `found` の中身は #39 と同じ。

### `dtm_ahead` の `perf` で分かったこと

記録にしない完走の比較（各腕6本、`numactl` で固定）のあとで、`U_loop` の区間だけを `perf` で数えた（腕ごとに1本ずつ）。

| `U_loop` の cycles / フロンティア | #39（`base`） | #40（`ahead1`） | 差 |
|---|---|---|---|
| 全体 | 972.8 | 873.0 | −99.8 |
| ふるいの `g_dtm` の読みの1行 | 193.8 | 20.9 | **−172.9**（約 −5.3 秒） |
| 決めるの `g_prep` の読みの1行（odd の段） | 44.9 | 100.2 | **＋55.2**（約 ＋1.7 秒） |
| `stalls_mem_any`（M1） | 236.5 | 143.9 | −92.6 |
| instructions | 1,601.4 | 1,651.9 | ＋50.5 |

- **`g_dtm` の待ちはほぼ全部消えた。** 残った 20.9 は候補 5.57 個の読みと比べ・分岐の分
- **消えた待ちの一部は、決めるの `g_prep` の読みに移った。** `g_prep` の先読みは、ふるうループの中で残した候補にだけ頼み、そのすぐあとの決めるで読むので、#39 の `g_dtm` と同じ
  「頼んですぐ読む」形のまま。#39 では `g_prep` の行を待つ間に `g_dtm` の待ちも重なっていて、`g_dtm` の待ちが消えたぶん `g_prep` の待ちが表に出たと読める（確かめていない）
- 命令は ＋50.5 / フロンティア増えた（ループの組み替えと、ループの前とループの中に2つある候補の生成と番号の展開）。それでも IPC は 1.65 → 1.89 に上がった

## 次

- **段の大きい順**: 本走で F1 41.4 秒（52.7%）、`U_loop` 27.9 秒（35.5%）
- **`g_prep` の先読みも早める**（`dtm_ahead` の推奨の4つ目。作っていない）: #40 で `g_prep` の読みの1行が 100.2 cycles / フロンティア（約 3.1 秒。odd の段だけ）になり、
  `U_loop` でいちばん重い1行になった。odd の段で局面 i + 1 の候補全部の `g_prep` を `g_dtm` と一緒に先読みすれば、決める順も `out` も変わらない。
  ただし残す候補は候補の 41% なので、`g_prep` の先読みの数は odd の段で約 2.4 倍になる。#40 の上で別の実験にする

- ほかに残っているレバーは [`docs/levers.md`](../levers.md)（到達しない候補を減らす、番号の付け方を変える、生成器に残った分岐など）
