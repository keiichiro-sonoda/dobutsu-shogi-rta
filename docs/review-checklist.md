# 公開前レビューの観点

`make publish-check` は「出したら取り消せないもの」だけを見る。機械に持たせられない
残りをここに置く。`/code-review` は一般的な正しさを読むが、このリポジトリ固有の
決まり（凍結・レギュレーション・帯の引き方）は知らないので、そこを補う。

読み方の基本は2つだけ。**主張を見たらその対象を開く**、**変わった数字は grep する**。
記録 #13 で外した2件（`out[3]` の説明、README の表の取り残し）はどちらもこれで出る。

## 優先順位

| | 種類 | 扱い |
|---|---|---|
| A | 鍵・同定情報・凍結物の破壊・証拠の欠損 | `make publish-check` が止める。push しない |
| B | 説明の誤り・数字の不一致・命名・設計 | 直すが、push は止めない（訂正を足せる） |

B を A に混ぜない。止めない指摘を門番に積むと、鳴っても止めない癖がつく。

## 主張とログを突き合わせる

記録ノートと README の数字は、すべて `results/<番号>_<名前>/` から再現できるはず。

- 「〜秒縮んだ」「〜%」「下限〜上限」は、`main.log` / `forward.tsv` / `time.txt` の
  どれで検算できるかを言えるか。言えないなら推定と書いてあるか
- 幅を書いたなら、**両端それぞれの出どころ**が違うことを書いてあるか
  （記録 #13 は上限だけ書いて下限を残差で代用し、266 秒を 298 秒と書いた）
- 「バイト同一」は本当にバイト単位で比べたときだけ。出力が同じことと、コードを
  触っていないことは別（記録 #12 の `bytecompare.txt` の見出しがその混同）

⚠️ 同じ数字を2か所以上に書いたら、片方を直したときに必ず全部を grep する。
記録表・frontmatter・ノート本文・「次の標的」のレバー表は同じ値を持つ。

## 効果量の言い方

[`docs/measurement-noise.md`](measurement-noise.md) が実測の幅を持っている。

- 1本のタイム差を改善とも退行とも読んでいないか
- 帯を「前回の1本」ではなく**そのコードの観測の平均**に引いているか
- フェーズ単独に合計の帯を流用していないか（段ごとのほうが大きく振れる）
- 少数標本で検定したなら、t 値だけでなく自由度と区間まで書いてあるか
- 「測定限界以下」と書いていないか（観測の幅から検出限界は決まらない）

## C と Python をまたぐところ

過去2回の不具合はどちらもこの境界で出た。記録 #11 の `-3` 握りつぶしと、
記録 #13 の空入力で初見バッファが戻る件。

- 早期 return が**飛ばしている初期化**は無いか（`return` より後ろにリセットがある形）
- 呼び出しをまたいで残る static を、次の呼び出しが前提にしていないか
- 同じ量を2か所から取れる形になっていないか。なっているなら**本当に同じ量か**
  （延べ数と初見の数のように、名前が似ていて別物のことがある）
- C の戻り値を握りつぶしていないか。異常時に Python 側へ上がるか
- テストが「2回目の呼び出し」「空入力」「エラー経路」を通しているか。
  1回目だけを通すテストは、状態が 0 から始まるので素通りする

⚠️ テストの本数は根拠にならない。緑が「覆っている」のか「挟んで外している」のかは、
テストが何を呼んでいるかを読まないと分からない。

## 凍結の扱い

- 記録済みの実装・`results/`・`baseline/`・`oracle/` を直そうとしていないか
- 記録ノートの訂正を本文に書いていないか（末尾に「訂正（日付）」節を足す）
- 見つけた不具合を CLAUDE.md の「次の実装で必ず直すもの」に積んだか
- 実験は `experiments/` に置き、生ログをコミットしたか（`runs/` は git 管理外）

## 文書

- 記録 #N の分析が README に書かれていないか（README は入口・記録表・索引・次の標的）
- `⚠️` が1見出し節に2個以上ないか、`🔑` を使っていないか（`make check` の `doc_lint`）
- 試行をまたぐ話が `docs/` 直下にあるか
- **読む人が辿れないものを指していないか。** セッションに送った指示（「指示書」）、
  消えるブランチ名、`runs/` の中身、「前回」「さっき」。書いた本人には自明でも、
  あとから読む人には実体が無い。`doc_lint` は見ていないので目で見る

## 検査そのものを書くとき

道具の側（`doc_lint` / `publish_lint`）を足すときに、このリポジトリで実際に踏んだもの。

**規約を書いた文が、その規約で落ちる。** 「この形はエラーにする」と書いた行は、
その形そのものを含んでいる。`doc_lint` の `⚠️` の数え方、`publish_lint` の鍵の検体・
IP の実例・`Claude-Session:` の説明と4回踏んだ。検査は**使用と言及を分ける**。
手は3つあり、下にいくほど弱い。

1. 検体を実行時に組み立てる（ソースの上に連続した形を置かない）
2. パターンに長さや値の形を要求する（`ghp_` のあとに36文字、URL か UUID が続くとき）
3. バッククォートとフェンスの中を数えない（`doc_lint` の方式）

⚠️ 「自分のファイルだけ検査から外す」で逃げない。検査が弱くなるうえ、同じ形を
書いた別のファイルで結局鳴る。

**見る範囲を疑う。** `publish_lint` に出たレビュー指摘4件は、全部「どこを見るか」の
誤りだった。最終差分か履歴か、ファイルかコミットメッセージか、作業ディレクトリか
`HEAD` か、出力か終了コードか。パターンより範囲のほうを間違える。

**鳴らないことを確かめる。** 既に公開済みの履歴全体に掛けて0件になるか見る
（`publish_lint --base <最初のコミット>` で 60 コミット / 311 ファイル）。
誤検知は見逃しと同じくらい悪い。鳴っても止めない癖がつく。

## スキルから呼ぶ

`/review-record`（[`.claude/skills/review-record/SKILL.md`](../.claude/skills/review-record/SKILL.md)）
がこのファイルを読む。**観点の本文はここにしか置かない。** スキル側に写すと
2か所持ちになり、片方が腐っても気づけない。スキルが持つのは手順と、
指摘を A（push を止める）と B（止めない）に分ける決まりだけ。
