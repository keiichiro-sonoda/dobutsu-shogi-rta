# attack_count: キャッチ抜きの数を、相手の利きの一覧で数える（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。

**工夫は1つだけ入れる。** [`unmove_catch`](../unmove_catch/) の B1（全探索で後続を作るその場で、キャッチ局面への手を見分けて数える）の、
見分け方だけを替える。同じ一覧は「相手のライオンをすぐ取れるか」の先行判定（gen_bench の候補 A）や、逆向きの生成器で「作る前に絞る」のにも
使えるが、この実験では入れない。

## 目的

`unmove_catch` で、キャッチ局面への手を残りの後続の数から外しても答えが変わらないことを全局面で確かめ、試作の後退解析のループは
171 → 80 秒になった。ところが、キャッチ抜きの数を全探索で数える B1 が、未知局面で1局面 ＋396 ns（後続1本あたり約 42 ns）と重く、
合計でいまの4段（76.70 秒）を上回った。B1 は後続を1本作るたびに、指したあとの盤でライオンを探し、まわり8方向を分岐で調べている。
同じ局面の後続どうしでは相手の駒の並びはほとんど変わらないのに、それを後続の数だけ見直している。

## 相手の利きの一覧

いまの生成器は局面 p を反転した盤 b の上で、手番側の駒（9〜13）を動かす。後続 q がキャッチ局面か（q を生成器に通すと 0 が返るか）は、
手を指した直後の盤で「相手の駒（1〜5）が手番側のライオン（`LION2`）のマスへ届くか」で決まる。届くかどうかの写し方は `unmove_catch` の B1
（`catchAfterMove`。全未知局面で B2 と一致を確かめた）と同じ: 相手の駒がマス s から L ＝ s − m へ届く（m は移動表の値）、回り込みを捨てる2条件、
相手のひよこは L ＝ s ＋ 4 で s が反転した盤の端の行でないこと。

**なぜ駒を動かしても一覧が崩れないか:** どうぶつしょうぎの駒は、どれも1マスしか動かない（遠くまで利く駒が無い）。だから手番側が駒を1つ
動かしても、相手の駒の利きは1つも変わらない（間に入って遮る、遮っていた駒がどく、が起きない）。変わるのは、相手の駒を取ったときに
その駒の利きが消えることだけ。成り・持ち駒への加算・手番側のライオンが奥の段に入ること（トライ）も、相手の利きには関わらない。

### 一覧の持ち方と作る位置（[`attack.c`](attack.c)）

- 表 `g_att[k][sq]`: 相手の駒 k がマス sq にいるとき届くマスの集合（12ビット）。いまの生成器の移動表から最初に1回作る（`attackTableBuild`）。
  空きマスと手番側の駒（9〜13）は 0
- 一覧は**局面の頭、反転（`invBoard`）の直後**に作る。12マスを分岐なしに1周し、表を引いて2本のビット列を重ねる
  - `att1`: 相手の駒が1つ以上届くマスの集合（相手の駒がいるマスにも数える）
  - `atkL`: 手番側のライオンのマス L（`rankFindKoma` で探す）に届いている相手の駒の、いるマスの集合
- 後続ごとの判定（キャッチ局面になるか）:

| 手 | キャッチ局面になる条件 |
|---|---|
| ライオンを dst へ動かす（取る手・奥の段に入る手も） | dst が `att1` に入っている（取られる相手の駒は、自分のマスには届かない） |
| ライオン以外を dst へ動かす（取る手・成る手も） | `atkL` から dst を除いて空でない（dst の相手の駒を取れば、その駒の利きが消える） |
| 持ち駒を打つ | `atkL` が空でない（打つ手は全部同じ答え） |

局面の頭で作るので、キャッチ局面（取れる手に当たった時点で打ち切る）でも一覧づくりのぶんは払う。最初の後続を作る直前まで遅らせる形は測っていない。

B1′（`nextBoardCountNonCatchX`）は、いまの生成器の本体の写しに、一覧づくりと後続ごとの判定を足したもの。後続の列と戻り値は変えない。
一致の検査用に、後続ごとの判定と手の種類も返す形（`nextBoardCatchFlagsX`）を同じ本体から作る（`always_inline` の本体を2つの口から呼ぶ）。

## 一致の検査（[`run_count.sh`](run_count.sh)、[`bench.c`](bench.c) の `count`）

- **全局面（246,803,167）で、B1′ の戻り値がいまの生成器と同じ**（全探索では全局面が生成器を通るため。キャッチ局面 0、トライ負け局面 −1 も含む）

  ライオンが奥の段に入る手・ほかの駒の手・ほかの駒で取る手・ひよこが成る手・打つ手）に件数と食い違いを出す

- 換算は試験台の値で、段どうしの重なりは入らない。作り替えた後退解析の見積もりは、試作のループ（丸ごと測った値）に、抜き出しで測った増分 × 件数と
  `unmove_bench` の `degw` を足したもの。本当の効果は、記録にするときの門番で測る
- 一覧を最初の後続を作る直前まで遅らせる形（キャッチ局面で一覧づくりを省ける）は測っていない。キャッチ局面ぶんの 2.76 秒がどれだけ減るかは分からない

## 次の工夫の推奨（決めない）

**同じ考え方の一覧を、逆向きの生成器の「作る前に絞る」に使うのが次の候補。** `unmove_catch` で、`drop` の候補 1,094,348,081 個のうち
31.2%（341,669,361 個）が「前任の候補がキャッチ局面（前任の手番側が、相手のライオンを取れる）」で捨てられていた。

逆向きの生成器は、q（と鏡像）の上で「直前に指した側」X の駒（9〜13）の手を1つ戻す。前任 p がキャッチ局面かは、戻した盤で X の駒が相手のライオン（`LION1`）の
マスへ届くか（いまの生成器の向きのまま: s から s ＋ m）で決まる。ここでも駒は1マスしか動かないので、手を戻しても X の利きが変わるのは戻した駒の分だけ。

- 手を指した直後の盤ごとに1回、「相手のライオンのマスに届いている X の駒のマスの集合」を作る（一覧づくりはこの実験と同じ約 20 ns の桁。q と鏡像で2回）
- 駒 k を d から s へ戻す候補は、集合から d を除き、「k が s にいれば相手のライオンへ届くか」を表で引いて足す。空でなければキャッチ局面なので、作らずに捨てる
- 打った駒を戻す候補は、集合から d を除くだけ。取った駒を戻すのは、相手の駒が増えるだけで X の利きは変わらない（相手のライオンは取られていないので、
  ライオンのマスも変わらない）
- X のライオンを戻す候補も同じ形（ライオンの移動表で、s から相手のライオンへ届くか）

粗い見積もり: 捨てていた 3.4 億個ぶんの候補作り（`unmove_bench` の候補1個あたり約 57 ns）とふるい（約 30 ns）が要らなくなって約 30 秒、
一覧づくりで 103,821,853 局面 × 2 × 約 20 ns ≈ 4 秒が足される。差し引き 25 秒前後なら、作り替えた後退解析の見積もり 94.25 秒は 70 秒前後になり、
いまの4段（76.70 秒）を下回る見込み。ただし候補1個あたりの 57 ns には、捨てない候補とも共通する仕事（駒を探すループなど）が混ざっているので、
