# bitboard_gen: 全探索の生成器をビットボード型にした試作を、生成器だけのベンチで測る（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。完走の門番・本走はしない（推すところまで）。

## 目的

[`perf_branch_34`](../perf_branch_34/) で、F1 の予測ミス（1局面あたり 12.16 回）の内訳が分かった。上位の多くは、生成器 `nextBoardInvNormalNC()` が
「このマスに何がいるか」「行き先は使えるか」を1マスずつ分岐で聞いているところだった。

| 束 | 段の中 | 中身 |
|---|---|---|
| 駒の種類と空き | 37.1% | マスが空きか（623 行、単独で 20.2%）・ライオンか（643 行）・駒の種類の `switch`（646 行） |
| 行き先の駒 | 21.2% | 行き先に駒があるか（661 行、15.2%）・自分の駒か（662 行） |
| ループの回数 | 12.5% | 指し手の表のループ（655 行）など |
| 盤の端 | 10.6% | 行き先が盤の外（657 行）・端の回り込み（659・660 行） |

そこで、生成器を**マスの集合をビットで持ち、表引きとビット演算で行き先の集合を作って `ctz` で1つずつ取り出す形**に書き換えた試作を2つ作り、
`perf_34` / `perf_branch_34` の生成器だけのベンチで今の生成器と比べる。完走の門番にかける価値があるかと、どちらの腕を持っていくかを推す。

## 腕

どの腕も `impl/34_unmove` の写しにパッチを当てて作る（[`build_arm.sh`](build_arm.sh)）。`impl/34_unmove` そのものは触らない。
**変えるのは `nextBoardInvNormalNC()` と、そのための行き先の表と表を作る関数だけ**（[`patches/`](patches/)）。逆向きの生成器・`nextBoardSeenNormal()`・
`normalBoard()`・`invBoard()`・ランク・待ち行列・Python は触らない。`Makefile` は `impl/34_unmove` のまま。

| 腕 | 集合の持ち方 |
|---|---|
| `base` | `impl/34_unmove` のまま（`.so` は #34 本走と同じバイト列、sha256 の先頭 `572517006344`） |
| `bb_nibble` | 盤と同じ4ビットおきの形。**マス k をビット `4k`（各4ビットの最下位）に置く。** 手番側の駒 `(b >> 3) & 0x111111111111`、駒がいるマス `(b \| b>>1 \| b>>2 \| b>>3) & 0x111111111111`。`ctz` の値がそのまま今の `src` / `dst`（0, 4, …, 44） |
| `bb_pext` | `_pext_u64` で 12 ビットに詰める。手番側の駒 `pext(b, 0x888888888888)`、駒がいるマス `pext(上の OR, 0x111111111111)`。行き先の表も 12 ビット（`uint16_t`）。`src = 4 × ctz` |

### 生成器の形（両腕共通）

1. `invBoard` の直後に集合を1回作る（手番側の駒・駒がいるマス）。頭の「利きの一覧」（`att1` / `atkL`、キャッチ抜きの数に使う）は今のまま
2. 手番側の駒のマスを `ctz` で番号の小さい順に取り出し、`koma = getKoma(b, src)` を添字に行き先の表を引く（`switch` を使わない）。
   行き先の集合 ＝ 表 ∧ ¬手番側の駒（自分の駒のマスと、盤の外・回り込みは表と AND で消える）
3. 行き先を `ctz` で番号の小さい順に取り出す。行き先ごとに:
   - `dst_koma == LION1` なら `return 0`（今と同じく走査の途中で返る。**キャッチの先行判定はしない**）
   - 取るか動くかは分岐にしない。`nb = delKomaDouble(b, src, dst)`（空きの行き先を消しても盤は変わらない）に、持ち駒の更新（`own_p` の三項演算は今の書き方）を
     `dst_koma != 0` のマスクで掛けて足す
   - ひよこの成り（`dst % 16 == 0` の行）は `(koma == CHICK2) & (端の行のビット)` を足し算で効かせる。キャッチ抜きの数の `c`（ライオンは `att1`、ほかは `atkL`）は今の式
4. トライ（相手のライオンが `src % 16 == 12` の段にいる）は、`LION1` のマスをビットで探して段のマスクと AND する。全部の駒を見たあとで `-1`（`return 0` が先に勝つのは今と同じ）
5. 空きマスを `ctz` で番号の小さい順に `emp_adrs` に並べ、打つ手（持ち駒の3種類 × 空きマス）は今のコードのまま

### 後続の順番を保つ仕組み

今の生成器は、マスを `src` = 0, 4, …, 44 の順に見て、手番側の駒ならその駒の手を移動量の表の順に出し、空きマスは控えて最後に打つ手を出す。
移動量の表（`GIRAFFE_MOVE` など）はどれも昇順なので、1つの駒の行き先は番号の小さい順に出る。
試作は「手番側の駒のマスを番号の小さい順に取り出す → その駒の行き先を番号の小さい順に取り出す」なので、同じ並びになる。
駒の種類ごとに集合をまとめて処理はしない（マス 3 のぞうより先にマス 7 のきりんの手が出る、などの入れ替わりを起こさない）。

### 行き先の表

**今のコードの判定をそのまま全通り回して作る**（パッチの `dstTableBuild()`）。各 `(駒, src)` について移動量の表の順に、
`dst < 0 || 44 < dst`、`src_mod16 == 0 && dst_mod16 == 12`、`src_mod16 == 12 && dst_mod16 == 0` を当てて行き先を集める。ひよこは `src % 16 == 0` なら空、
でなければ `src - 4`。**表は `.so` を読み込んだときに1回作る**（`__attribute__((constructor))`。生成器に「表があるか」の分岐を足さない。
ベンチの `glue.c` は `prepInit` を呼ばないので、遅延では作られない）。表は `.bss` に置く（`hot_layout.ld` は `.text` だけを並べる。
生成器の名前は変えていないので、`.text.hot_layout` の中にある。`build_arm.sh` が確かめる）。新しい熱い関数は無い（表を作る関数は1回しか走らない）。

`ctz` は `__builtin_ctzll` で、ループを `while (x)` にして 0 を渡さない。`-march=native`（Broadwell）で `tzcnt`、`bb_pext` は `pext` になる。

## 測るもの

[`run_all.sh`](run_all.sh) が順に回す（進行は `logs/console.log`。開始の行は `date --iso-8601=seconds`）。完走は回さない（入力は `runs/` に残っている）。

1. **一致の検査**（[`run_verify.sh`](run_verify.sh)、[`verify.c`](verify.c)）: `base` と腕の `.so` を `dlopen` し、どちらも `prepInit()` で利きの表を作る。
   #34 本走の `dat/`（`runs/` の全 213 ファイル、到達可能な全 246,803,167 局面）を全部通し、(a) 戻り値、(b) 正のときの後続の列（並びまで）、
   (c) `*non_catch`（`return 0` と `-1` のときに 0 のままであることも）が同じかを見る。外れた局面は最初の 20 個まで `logs/verify_<腕>.txt` に残す
2. **ベンチ**（[`run_bench.sh`](run_bench.sh)、[`build_bench.sh`](build_bench.sh)）: `perf_34` の `glue.c`・`bench.c` をそのまま使い、腕ごとにその腕の
   `animal_shogi.c` を取り込んだ `bench.so` を `impl/34_unmove` の `Makefile` の gcc 行で作る。`benchFwd`（生成器 ＋ 後続ごとの `rankOf`）は3腕で同じ。
   `base` の `bench.so` が `perf_branch_34` のものとバイト一致することを見る
   - 入力: order（F1 の各ラウンドの真ん中の 4,096 局面。本物の並び）・random（並びを崩した 262,144 局面）・catch / other（order をキャッチ局面とそれ以外に分けたもの）
   - `perf stat -e cycles:u,instructions:u,br_inst_retired.all_branches:u,br_misp_retired.all_branches:u`。3腕 × 7周、周ごとに腕の順を1つずつずらす。
     腕ごとに1局面だけのファイルで固定の分を5回測って引く。`numactl --cpunodebind=0 --membind=0`
   - ⚠️ ベンチは `prepInit` を呼ばないので、利きの表 `g_att` は空のまま回る（`perf_34` から同じ）。キャッチ抜きの数の値は本物と違うが、
     3腕で同じ条件で、その12マスのループは分岐が無い
3. **束ごとの帰属**（[`run_attr.sh`](run_attr.sh)）: 腕ごとに `-g` の `bench.so` で order の 74 ブロックを1プロセスで回し、
   `perf record -e br_misp_retired.all_branches_pebs:upp -c 211`（素数。ベンチ1プロセスの予測ミスは約 600 万回なので、数万の標本になる周期）。
   `perf_branch_34` の `aggregate.py pebs` で分岐の行に寄せ、上の束ね方で束ねる。3回
4. [`summary.py`](summary.py) が `logs/summary.txt` を作る（手で書かない）。腕どうしの差は**同じ周の `base` との差を周ごとに取ってから**、7周の中央値と範囲。
   F1 の秒への換算は「order の cycles の差 × 246,803,167 ÷ 周波数」（周波数は `perf_branch_34` と同じ式で 3.408 GHz）。**換算は見込みで、効果量ではない**
   （`gen_bench` の換算は門番で 75〜83% しか出なかった）

## 選び方（回す前に決めた）

- ビットボード型を推すかの判定の量は **order 入力の1局面あたり `cycles`**
- `bb_*` − `base` の範囲（7周）が 0 をまたがずに下なら、完走の門番にかける候補として推す
- `bb_pext` − `bb_nibble` の範囲が 0 をまたぐなら `bb_nibble` を推す（`pext` に頼らず、今のコードの `src` と直接つながるため）

## 条件

- 一致の検査もベンチも `numactl --cpunodebind=0 --membind=0` で固定
- 回す前に、`kernel.perf_event_paranoid` が 1、`impl/34_unmove` に `__pycache__` が無い、CPU 使用率（全 CPU）が 3% 以下（ほかの計算が動いていない）を確かめる。
  合わなければ回さずに本人に知らせる。負荷は load average と CPU 使用率だけを残す
- `runs/` の中身（`dat/`・入力・`perf.data`）はコミットしない

## 止める条件（回す前に決めた）

1. どちらかの `bb_*` 腕で、一致の検査が1局面でも外れる（その腕は計時しない。両方外れたら計時に進まない。`run_all.sh` が見る）
2. 後続の順番を保てない箇所が見つかる（直し方を自分で決めずに、どこで・なぜ保てないかを報告する）
3. `check_asm.py` で、`bb_*` の生成器に `tzcnt`（`bb_pext` は `pext` も）が無い、または今の分岐の形が残っている（`run_all.sh` が組むたびに見る）
4. `kernel.perf_event_paranoid` が 1 でない
