# dtm_ahead: 後退解析 `U_loop` で、`g_dtm` の先読みを1局面先にする試作を、完走で比べる（記録試行ではない）

番号を取らず、`impl/40_*` を作らず、タイムを `results/` にも README の記録表にも載せない。記録の門番・本走はしない（推すところまで）。
ここでの12本の比較は、記録の門番の証拠には流用しない（#40 にするなら門番を改めて回す）。

## 何を確かめるか

[`perf_39`](../perf_39/) で、#39 の `U_loop`（30.6 秒）のうち **約 6.0 秒（195 cycles / フロンティア、`U_loop` の 19.6%）が `unmoveStep` の1行**、
1174 行 `if (g_dtm[r[j]] != DTM_UNDECIDED) continue;`（未定の候補をふるう読み）に付いた（[`results.md`](../perf_39/results.md)）。
今の `unmoveStep` は、フロンティアの局面 i の前任の候補を作り、候補ごとに番号を出して `g_dtm` の行を `prefetchw` した**すぐあとに**、同じ局面 i の候補の `g_dtm` を読む。
先読みから読みまでの間が「残りの候補の `rankOf`」だけなので、行が届く前に読みに行って待っている。
この読みは取りに行っている途中の行で当たるので、L2 のロードミスには数えられず、cycles の標本の側（1174 行）に出る（`perf_39` の結果）。

試作 `ahead1` では、**局面 i の候補をふるう前に、局面 i + 1 の前任の候補を作り、番号を出し、先読みを頼む**（ソフトウェアパイプライニング）。
局面 i + 1 の行を頼んでから読むまでの間に、局面 i のふるう・決めると、局面 i + 2 の生成器と `rankOf` が入る（局面1つ分の仕事、約 1,000 cycles ≈ 0.3 µs）。
待ちが消えたかを、完走の `U_loop` の秒と `perf` で見る。

生成器だけのベンチ（`benchUnmove`）には `g_dtm` が無く、この待ちが出ないので、**完走で比べる**（[`mirror1_keep`](../mirror1_keep/) の完走の比較と同じ扱い）。

### `ahead1` の作り

変えるのは `unmoveStep()` の中だけ。`unmoveCandidates()`・`rankOf()`・ほかの関数・`.py`・`Makefile`・`hot_layout.ld` は触らない。関数名も同じで、新しい関数は足していない。

- **配列の持ち方**: 候補の配列と番号の配列を2組（`cand2[2][UNMOVE_MAX]`・`r2[2][UNMOVE_MAX]`）持ち、局面 i は組 `i & 1` を使う（偶数番目と奇数番目の局面で交互）。
  ループの頭で `cand = cand2[i & 1]`・`r = r2[i & 1]` と置くので、ふるう・決めるのコードは名前も含めて #39 のまま。スタックは 16 KiB から 32 KiB になる
- **先頭と最後**: ループに入る前に、フロンティアの先頭（局面 0）の候補を組 0 に作り、番号を出して先読みを頼む。ループの i 回目は、`i + 1 < n` のときだけ局面 i + 1 の候補を組 `(i + 1) & 1` に作り、
  番号を出して先読みを頼んでから、局面 i（組 `i & 1`。候補の数は前の回に作ったときの数）をふるい、決める。最後の局面では次の候補を作らない。`n == 0` なら何もしない
- **ふるう・決めるの中身は1文字も変えていない**（`g_prep` の先読み `if (odd) __builtin_prefetch(&g_prep[r[j]], 1, 3);` もふるうループの中のまま）。`g_dtm` の先読みの引数（`1, 3`）も同じ
- **`out` とエラー**: 候補の数 `n_cand` は、局面を作ったときに足す（`ahead1` では1局面早く足す）。`out[0..2]` は、`base` と同じく最後まで進んだときにだけ書く（途中で返るときは関数の頭で書いた 0 のまま）。
  `-2`（`found` があふれた）と `-4`（残りの数を 0 から減らそうとした）は、ふるう・決めるの中から、`base` と同じ局面 i・同じ候補 j で返る。
  そこまでに `found` に積んだものは `base` と同じで、`ahead1` が先に作った局面 i + 1 の候補は `found` にも `g_dtm` にも `g_prep` にも書かないので、返す値と `found` の中身は `base` と同じになる

### 決める順が変わらない理由

前任の候補を作ること（`unmoveCandidates`）と番号を出すこと（`rankOf`）は、`g_dtm` も `g_prep` も読まない（盤と静的な表だけで決まる）。先読みは中身を変えない。
局面 i をふるう・決めるのは、`base` と同じく局面 i − 1 を決め終えたあとで、ふるう・決めるのコードも同じ。だから `g_dtm`・`g_prep` を読み書きする順は `base` と1つも変わらず、
**決める順も `found` に積む順も #39 と同じ**で、`dat/` は #39 本走とバイト一致するはず。

- 1174 行の約 6.0 秒が上限。待ちが全部消えても、読み（候補 5.57 個ぶん）と比べ・分岐の命令は残り、未定かどうかで分かれる分岐の予測ミスも残る（読みが L1 で当たれば、予測ミスを解くのは速くなる）

### 言えないこと

- `g_prep` の待ちが増えた理由（上の読みは確かめていない。`g_prep` の行の待ちを `g_dtm` の待ちと分けて数えていない）

- カーネルの区分（2.6〜2.8%）が `perf_39`（5.4%）より小さい。`perf_39` は手数ごとの計装（`depth_log.patch`）を当てていたが、それで説明できるかは確かめていない。2腕の差には効かない
- この12本は門番ではない（記録の門番の証拠には流用しない）。`numactl` で固定した値なので、本走の差を見込む値として引き算に使わない

## 推奨（決めない）

- **`ahead1` を #40 として記録の門番にかける候補として推す。** 取り決め（`U_loop` の秒の差の区間の上端が 0 より下）に当たる。区間は −2.90〜−2.57 秒、完走でも −2.89 秒（−3.19〜−2.59）。
  `dat/` は #39 とバイト一致し、変えたのは `unmoveStep` の中だけ。#40 にするなら、`impl/40_*` ＝ `impl/39_rank_lean` ＋ [`patches/ahead1.patch`](patches/ahead1.patch) を門番で測り直す
  （`old` ＝ #39。答えの検査はバイト比較のまま使える）
- **1174 行の 6.0 秒のうち、消えたのは約 5.3 秒**（その行の cycles 193.8 → 20.9）。残った約 0.6 秒は読みと比べ・分岐の命令。
  ただし `U_loop` 全体では −2.7〜−3.1 秒にとどまった。差の内訳は、決めるの `g_prep` の読みに待ちが移った ＋1.7 秒、命令の増え（＋50.5 / フロンティア）と生成器・`rankOf` などの増減で ＋0.6 秒ほど
- **先読みの距離を延ばす案（2局面先など）には、`g_dtm` の分の取り分はほとんど残っていない**（ふるいの読みの行は 20.9 cycles ≈ 0.6 秒で、読みと分岐の命令が大半）。推さない
- **`g_prep` の先読みも早める案には取り分がある**。`ahead1` で `g_prep` の読みの1行が 100.2 cycles / フロンティア（約 3.1 秒。odd の段だけ）になり、`U_loop` でいちばん重い1行になった。
  作り方の候補は、odd の段で局面 i + 1 の候補全部の `g_prep` を `g_dtm` と一緒に先読みすること（決める順・`out` は変わらない）。
  ただし残した候補は候補の 41%（238,521,168 / 578,723,910）なので、先読みの数は odd の段で約 2.4 倍になる。その費用と、取りに行っている途中の行の数が増えることの効き目は測っていない
  （作らない。推すだけ）。`ahead1` の上に作るなら、#40 を決めたあとの別の実験にする
