# 実験: 全探索 2,370 秒の内訳を計装する

⚠️ **これは記録試行ではない。** タイムを `results/` や README の記録表に載せない。
速くもしていない。**目的は「全探索のどこで時間とメモリを使っているか」を知ることだけ。**
`impl/09_*` は作っていない。

## なぜ測ったか

記録 #8 で後退解析が半分以下になり、**全探索が全体の 67.3%（2,370 秒）**を占めるようになった。
後退解析には P0〜P4 の計装があるのに、全探索には何も無い。`impl/03` 以降ずっと手つかずで、
どこで時間を使っているか誰も知らなかった。**測っていない場所を勘で選ぶ**のは、
この企画で何度も記録してきた失敗の型なので、レバーを選ぶ前に内訳を測った。
実行全体のピーク RSS（23.62 GiB）を決めているのも全探索側なので、メモリの内訳も一緒に取った。

## 何を測ったか

`searchNext()` の中を指示どおり素直に割り、区分の境界で `time.perf_counter()` と
`/proc/self/statm`（RSS）と `/proc/self/status` の `VmHWM`（高水位）を読む。

| | 範囲 |
|---|---|
| F0 | 未探索チャンクの読み込み `pickle.load(unexp_boards)` |
| F1 | 展開 `while unexp_boards:` のループ全体（pop・FFI・振り分け・`+= nbl`） |
| F2 | 未知盤面の書き出し `updateUKFile(uk_boards)` |
| F3 | 集合化 `set(new_unexp_boards)` |
| S | 初回の `buildSeenBoards()`（空の `dat/` から始めるので実質 0） |
| F4 | 重複排除 `-= seen_boards` と `\|= new_unexp_boards` |
| F5 | `list()` に戻すところ〜末尾ファイルの読み直し・結合・分割・書き込み |
| F6 | 終端の書き出し `writeWLFilesForDepth()` ×2（`searchAll()` の最後） |
| 解放 | `catch_wins = []` / `try_loses = []`（終端リスト）と `seen_boards = None`。⚠️ 指示書に無いが、全探索側に計上されている処理なので別行にした |
| 残差 | 全探索の実時間 − 上の全部。区分に入れていない処理（ファイル探索のループ・ログ出力・`catch_wins +=`・ローカル変数の解放・端数） |

計装そのものが計測を壊さないために守ったこと:

- **ホットループの内側に時計を置かない。** F1 の `while` の本体は impl/08 と1行も違わない。
  時計は区分ごとに1組で、1ラウンド 13 回（/proc の読みを含めて 1 回約 60 µs、74 ラウンドで約 0.06 秒）
- **秒未満を切り捨てない。** float のまま足し、TSV は小数6桁。`s2hms()` は通していない
- **残差を必ず出す。** ラウンドごとの `round_total − ΣF` と、全体の `実時間 − Σ全区分`
- RSS と高水位は**各区分の開始と終了の両方**で読む。VmHWM はプロセス生涯の単調な高水位なので、
  境界の間で立った一過性のピーク（集合のリサイズ等）が**どの区分に属するか**が跳ねた境界から分かる
  （⚠️ ただし「それまでの最高値を更新したラウンド」でしか見えない）

計装が答えを変えていないことは、**記録 #8 の全探索直後の状態**（`tools/rebuild_forward_fixture.py` で
#8 の完走 `dat/` から組み直したもの）と `tools/fingerprint_dat.py` で照合して確認した
（3項目 PASS、246,803,167 局面。[`logs/fingerprint.txt`](logs/fingerprint.txt)）。
TSV の件数列（`n_in` / `n_win` / `n_lose` / `n_uk` / `n_new_pre` / `n_new_post`）は
実装が元々出すサブログと **74 ラウンド × 6 列 = 444 セルすべて一致**する。

⚠️ **この実験ではオラクル174行の検証を通していない**（`tools/verify_log.py` が見る手数別局面数は
後退解析が出すもので、全探索だけを走らせるこの実験では作られない）。代わりの砦が上の指紋照合で、
**照合先はオラクル174行を通した記録 #8 の完走の成果物**から組み直したものである。
全探索の成果物（未知・キャッチ・トライ負け・未探索）が #8 と一致すれば、
そこから先の後退解析は #8 と同じ答えを出す。

## F4 が大きい理由（測ったことと、推定の区別）

**測ったこと（TSV から直接）:**

- 13〜29 ラウンド目で、生成1要素あたりの F4 が **0.282 → 1.642 µs に伸びた**。この間 `n_new_pre` は
  27.4M → 18.6M と**減って**いて、伸びに対応する量は `n_seen`（F4 開始時、11.7M → 117M）だけ。
  ⚠️ 単調ではない。下のスパイク（15・21 ラウンド目）の翌ラウンドで一度戻る
  （0.633 → 0.596、1.406 → 1.091）。**その2本を外した 15 本は単調増加**。
  F4 を F4 開始時の `n_seen` で割ると 17〜29 ラウンド目で 0.263〜0.337 µs とほぼ一定
  （⚠️ スパイクの 21 ラウンド目だけ 0.422 で、この幅には入れていない）
  ——**この区間の F4 は発見済み集合の大きさに比例している**
- **29 → 30 ラウンド目で F4 が 30.62 → 13.80 秒（−55%）に落ちた。** 入力の規模は変わっていない
- 31〜58 ラウンド目（入力が満杯の 5,000,000 のラウンド。39 を除く 27 本）は生成1要素あたり
  0.705〜1.290 µs（中央値 0.770）で、`n_seen` が 124M → 235M と倍近くになっても伸びない
  （`n_seen` への回帰の傾き 0.013 s/M、R² 0.04）。
  ⚠️ 59 ラウンド目以降は入力が減って単価が上がる（最後は 5.5 µs）が、それは分母が小さくなって
  ラウンドの固定費が目立つだけなので、この比較には入れていない
- スパイクが 13 / 15 / 21 / 39 ラウンド目にあり（前後平均に対する超過 0.54 / 3.73 / 8.78 / 21.71 秒）、
  **同じラウンドの F4 の境界で高水位が +0.546 / +1.550 / +3.329 / +7.372 GiB 跳ねている**。
  この4本に 12 ラウンド目を加えた5本は、`n_seen` が 10,066,329 / 20,132,659 / 40,265,318 /
  80,530,637 / 161,061,273 を初めて越えたラウンドと **5/5 で一致**する
- 40〜42 ラウンド目（0.92〜1.08 µs）と 54〜56 ラウンド目（1.0〜1.3 µs）も高い。⚠️ **原因はログからは分からない**

**推定（CPython の `set` の実装の読みから。計測機に CPython のソースは無い）:**

- 上の閾値は set の表が `fill*5 >= mask*3` で倍に拡張される点（表の 3/5）で、跳ね幅 7.372 GiB は
  新表 2²⁹ スロット × 16 B = 8 GiB と整合する（拡張中は新旧の表が同時に存在する）。
  **`seen_boards` の表の拡張と読むのが最も整合するが、set の内部を直接見た記録ではない**
- 29 → 30 の段差は、`set.difference_update()` が「相手集合が自分の 8 倍を超えると、
  大きい側を全走査するのをやめて小さい側だけを走査する」経路に切り替わる位置と整合する。
  この 8 倍の崖はこの計測機の Python 3.12.3 で再現した（|a| = 1M に対し |b| = 7.9M と 8.1M で
  274 ms と 37 ms）。⚠️ **切り替わりを決める「集合化後の一意な要素数」は記録していない**
  （`n_new_post` 3.5M と `n_new_pre` 17M の間）ので、29/30 が境界だという読みは推定
- F4 のうち 13〜29 ラウンド目の合計は 384.92 秒。この読みが正しければ、全走査の経路で払った
  代金がそのあたりに入っている

**追加の実験が要ること:** 集合化後の一意数の記録、F4 を `-=` と `|=` に分けること、
40〜42 と 54〜56 ラウンド目の山の原因。

## F1 の検算

F1 = 412.09 秒 ÷ 246,803,167 局面 = **入力1局面あたり 1.670 µs**。満杯チャンク（5,000,000 局面）の
46 ラウンドで 1.570〜1.800 µs と狭く、`n_seen` との相関は無い（F1 は `seen_boards` を触らない）。
`F1 = a × n_in + b × n_new_pre` で当てはめると **a = 1.385 µs / 入力、b = 75.1 ns / 生成要素**（R² 0.999）。
予想の「FFI 1.3 µs ＋ 9.4 億回の append」と矛盾しない。⚠️ a には `set.pop()`・48要素バッファの確保・
ctypes 呼び出し・C の指し手生成・分岐が全部入っていて、この計装では分けられない。

## メモリ

**実行全体のピーク RSS 23.73 GiB（`/usr/bin/time -v` の 24,878,128 kB）は、F6（終端の書き出し）の中で
更新された。** summary の `hwm_after_F6` = 25,475,203,072 B と**1バイト単位で一致**する。

```
最終ラウンド後の RSS        21.75 GiB   ← seen_boards + 終端リスト
F6 前の高水位              22.22 GiB   ← ラウンド内の最高 (58 ラウンド目の F4 で初出)
F6 中の高水位              23.73 GiB   ← 実行全体のピーク (+1.98 GiB の一過性. F6 後の RSS は 21.75 に戻る)
終端リスト解放後            18.57 GiB
seen_boards 解放後          0.05 GiB
```

**ラウンド内の高水位の最高は 58 ラウンド目の F4 で 22.22 GiB。最大の跳ねは 39 ラウンド目の F4 で
+7,549 MiB（13.74 → 21.12 GiB）。** ⚠️ この2つは別物（跳ねが最大でも水位が最高とは限らない）。

### ピークを決めているもの

**推定**（ソースの読みと 1/10 規模の再現から。本走の F6 の内側には境界を置いていない）:
`writeWLFilesForDepth()` の

```python
while wlbl:
    writeAndBackup(..., set(wlbl[:BOARD_NUM_MAX]))
    wlbl = wlbl[BOARD_NUM_MAX:]      # ← 5,000,000 個減った別のリストを毎回作る
```

で、右辺を評価する間は旧 `wlbl` も生きているので、2 回目のスライスの瞬間に
「元（`catch_wins`、1.4 億要素）+ スライス 1 + スライス 2」が同居する。
スライス 1 + 2 = 135,298,614 × 8 + 130,298,614 × 8 = 2,124,777,824 B で、
**実測の一過性 +2,124,267,520 B との差は 0.5 MB**。1/10 規模の再現では高水位の上昇が
予測値と 6 KB 差で一致し、跳ねたのも 2 周目だった。
⚠️ 29 回のスライスで写すポインタは延べ 1.9 億 × 10 ＝ 約 19 億個（15 GB の memcpy）と同数の参照増減。
F6 の 173 秒のうちどれだけがこれかは**測っていない**。

### 実寸見積もりと実測（最終ラウンド後 21.75 GiB）

| 構造 | 件数 | 見積もり | 根拠 |
|---|---|---|---|
| `seen_boards` の表 | 2²⁹ スロット | 8.000 GiB | 16 B × スロット |
| `seen_boards` の int | 246,803,167 | 7.355 GiB | 32 B（`sys.getsizeof(2**59)`） |
| `catch_wins` + `try_loses` のポインタ | 147,317,599 | 1.098 GiB | 8 B（過剰確保 0.089 GiB は別） |
| 同 int（pickle 由来で `seen` とは別オブジェクト） | 147,317,599 | 4.390 GiB | 32 B |
| **合計** | | **20.84 GiB** | |
| （リストの過剰確保を足すと） | | 20.93 GiB | 8 B × 過剰分 11,915,793 要素（`list_resize` の規則で再現） |
| **実測** | | **21.75 GiB** | 差 **+0.82 GiB（3.9%）** |

差 0.82 GiB は**推定**で pymalloc のアリーナに残る穴（走行中に約 6.9 億個の重複 int が確保・解放される）。
