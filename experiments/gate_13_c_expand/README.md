## なぜ走らせたか

記録 #13 は全探索の展開ループをC側へ移す。展開順が変わると未知・未探索チャンクの
区切りと中身が動き、採番順を通して後退解析の局所性まで動く。

⚠️ **全探索そのものを変えるので、`runs/` の全探索フィクスチャは入力に使えない**
（#10・#11 と同じ事情）。空の `dat/` から `searchAll()` だけを完走させ、

1. **答えが変わっていないこと**を指紋で確かめる（止める条件はこれだけ）
2. F1 がどれだけ落ちたかを本走の前に見る

速度では止めない（本人決定 2026-09-19）。落ちていなくても本走は走らせる。

### F1 が半分以下になった

消えたのは **246,803,167 回ぶんの往復**である。局面ごとに

- ctypes の呼び出し（1回あたり約 1.5 µs）
- 48 要素の `c_uint64` バッファの確保
- `nba[:nbn]` の list 生成（初見の後続を Python のオブジェクトにする）
- 4通りの分岐

が乗っていた。これがラウンドあたり1回の `expandRound` に変わった。
1局面あたりでは **1.841 µs → 0.838 µs**。

⚠️ **F1 には新しい仕事も1つ入っている。** `array("Q", unexp_boards)` への詰め替えで、
2.4 億要素を C の連続バッファに写している。分離していないが、下の F5 の測り方から
1件あたり 70 ns 前後と見積もれる（**推定**）ので、全体で 17 秒前後。
つまり**詰め替えを含めて −247.6 秒**であり、詰め替えを除けば下げ幅はもう少し大きい。

### F5 が 16.6 秒増えた理由は測れた

未探索チャンクの書き出しは `set(new_unexp_boards[start:start + BOARD_NUM_MAX])`。
#12 まで `new_unexp_boards` は list で、中身の `PyLong` は F1 で作り終えていた。
#13 では `array("Q")` なので、**`set()` を作る時点で `PyLong` を作り直す。**

手元で測ると、200 万件の `set()` 生成が **list 0.296 秒 / array 0.441 秒**。
2.47 億件に換算して **36.5 → 54.4 秒（+17.9 秒）**。

| | |
|---|---|
| マイクロベンチからの予測 | **+17.9 秒** |
| 実測（F5 の差） | **+16.58 秒** |

⚠️ **`PyLong` の生成は消えたのではなく、F1 から F5 へ移っただけ。** F1 の −247.6 秒には
この移動ぶんも含まれている。正味で消えたのは FFI とバッファ確保である。

### メモリが 3.9 GiB 減った

#12 の `/usr/bin/time -v` は走行全体（後退解析を含む）の 13.82 GiB なので、
ここでは比べられない。全探索側だけを見る `forward.tsv` の高水位で並べる。

| | #12 本走 | **#13 門番** |
|---|---|---|

⚠️ **これはレバーではなく副産物。** C が埋めるのは連続バッファなので、勝ち・負け・未知と

list ならポインタ 1.12 GB ＋ `PyLong` 約 4.5 GB、`array("Q")` なら 1.12 GB だけ

## 展開順を保てたことの裏づけ

⚠️ **指示書は「`unexp_boards.pop()` は末尾から取るので展開順はリストの逆順」と
していたが、これは誤りだった。** `unexp_boards` は list ではなく `set` で、
`set.pop()` の繰り返しは集合の反復順になる。`array("Q", 集合)` の並びがちょうどそれで、
C は**前から後ろへ**回している。

裏づけは3段:

| | |
|---|---|
| 打ち切った `dat/` のバイト比較 | `tests/test_impl_13_c_expand.py` が #12 と一致を固定（18 / 62 ファイルの2条件） |
| ラウンドごとの件数 | 74 ラウンド × 8 列が #12 本走と完全一致（上の表） |
| 指紋 | **PASS**（3項目、246,803,167 局面） |

本走では `dat/` のバイト比較そのものを通す。
