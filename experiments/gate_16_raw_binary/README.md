# 門番 #16: 保存形式だけを1変数にする

⚠️ **これは記録試行ではない。** 番号を取らず、タイムを `results/` にも README の記録表にも
載せない。入力を固定して後退解析だけを走らせた比較で、レギュレーションの
「空の `dat/` から完走」を満たしていない。

## なぜ要ったか

記録 #16 の**1本目**で、**成果物のチャンク分割が #15 と食い違った**。213 ファイル中 208。
集合は一致していて（オラクル174行も指紋176項目も PASS）、動いたのは**採番順**だけ。

その1本目は `impl_sha256` が汚染されていて取り下げてあり、`results/16_raw_binary/` に
載っているのは走り直した2本目（そちらの P2 は 106 秒で、下記の +23 秒は出ていない）。
経緯は[記録ノート](../../docs/records/16-raw-binary.md)にある。

原因は読む側にある。**pickle の往復は `set` の反復順を保たない。**

```
要素 1,000,000 の集合 (48bit 一様乱数、盤面番号に近い疎さ):
往復で反復順が同じ = False / 位置が動いた要素 999,807 (100.0%)
（`range(1_000_000)` のような密な連番では 0.0%。集合の疎密に依存する）
```

`#15` は `pickle.load(f)` が返す**作り直した集合の順**で番号を振っていた。
`#16` は `frombytes` で**書いたときの順**をそのまま読む。だから
**書き側の `set(...)` を残しても採番順は一致しない**。一致させるには読むたびに
`set(readBoards(...))` と作り直すしかなく、それでは形式を変えた意味が消える。

採番順は P2・P4・174段ループの局所性を決めるので、1本目の
**P2 105 → 128 秒（+23）**が「形式の効果」なのか「採番順の副作用」なのか、
その1本だけでは分けられない。ここで分ける。

## 仕掛け — 両腕に同じ採番順を渡す

`convert_fixture.py` が `.bin` のフィクスチャを **`array("Q", pickle.load(f))`** で書く。

```
#16 がファイルから読む順  =  #15 が pickle から読む順
```

⚠️ **`tools/rebuild_forward_fixture.py` は使えない。** あちらは書き出しに
`array("Q", set(boards))` を通すので、集合を作り直して順序が動く。

| | |
|---|---|
| 腕 | `old` = `impl/15_c_successors`（pickle）／ `new` = `impl/16_raw_binary`（`.bin`） |
| 並び | `old new new old` を2回、計 **8本**（対で向きを入れ替える） |
| 入力 | `runs/g1_11_fixture/dat` と、それを写した `.bin` 版 |
| 所要 | 59分。8本ともオラクル174行に一致 |

### 両腕とも片ノードに固定した

⚠️ `numactl --cpunodebind=0 --membind=0` を両腕に付けた。
[`numa_bind`](../numa_bind/) で、固定すると P2 の標準偏差が 15.69 → 0.71 秒に縮むことが
分かっている。23 秒の差を見たいので雑音を落とした。腕の扱いは対称なので偏りは入らないが、
**この帯は「固定した条件での帯」で、固定していない記録の走行には移せない。**

## 設計が成立したことの証明

走ったあとに確かめられる。`g1a`（`#15`）が書いた pickle の**ストリーム上の並び**と、
`g1b`（`#16`）の `.bin` のバイト列を突き合わせる。出力は
[`logs/order_check.txt`](logs/order_check.txt) に残してある。

「手つかず」は**ファイル名**では判定できない。`unknown*` は `loadAllUnknownBoards()`
が全部読んで消し、`writeUnknownChunks()` が番号を 0 から振り直して書くので、
同じ名前でも中身は別物になる。`old` の出力が元のフィクスチャ pickle と
**バイト同一**かどうかで判定する。

| | |
|---|---|
| 手つかず（`old` が元フィクスチャとバイト同一） | 31 ファイル（`win001te_*` 29・`lose000te_*` 2。`appendFamily()` は読むだけで書き換えない） |
| 後退解析が書いた（`unknown*` を含む） | 182 ファイル。**全部一致** |

⚠️ **手つかずのほうが食い違うのは当たり前。** 保存されているバイト列は `old` が
「元のフィクスチャが書いた順」、`new` が「`convert_fixture.py` が `pickle.load` した順」で、
そこは最初から前提が違う。大事なのは**両腕が読む順が同じ**ことで、それは
後退解析が書いた182ファイルが順序まで一致したことで示される。

### 照合の方法を間違えると逆の結論が出る

⚠️ 最初は `array("Q", pickle.load(old))` と `new` のバイト列を比べて、
「31 本が食い違う＝設計が崩れた」と読んだ。`pickle.load` が順序を崩すので、この比べ方では
**採番順が同じでも一致しない**。pickle が書いた順は `pickletools.genops` で
ストリームから直に取る。

## 答え: 1本目の P2 の +23 秒は形式ではない

| 段 | `old` 4本 | `new` 4本 | 差 | t | 自由度 | p | 95% 区間 |
|---|---|---|---|---|---|---|---|
| **P0 読み込み** | 93.50（sd 0.58） | **4.00（sd 0.00）** | **−89.50** | −310.04 | 3.00 | < 0.0001 | **−90.42 … −88.58** |
| P1 索引 | 20.00（sd 0.00） | 21.00（sd 2.00） | +1.00 | 1.00 | 3.00 | 0.39 | −2.18 … +4.18 |
| **P2 後続生成** | 104.00（sd 0.82） | 104.00（sd 0.82） | **0.00** | 0.00 | 6.00 | 1.00 | **−1.41 … +1.41** |
| P4 前任リスト | 164.00（sd 1.41） | 164.75（sd 0.96） | +0.75 | 0.88 | 5.27 | 0.42 | −1.41 … +2.91 |
| 後退解析 合計 | 490.36（sd 2.34） | 401.37（sd 0.92） | −89.00 | −70.81 | 3.90 | < 0.0001 | −92.52 … −85.47 |

**採番順を揃えると P2 の差はちょうど 0.00 秒**（区間 ±1.41 秒）。
1本目の +23 秒は形式の効果ではない。**採番順が動いたことと機械の揺れの合計**で、
この門番はそのどちらがどれだけかまでは分けていない。

後退解析合計の −89.00 秒は、ほぼ全部が P0 から来ている（−89.50）。
記録の P0 は 95 → 3 秒（−92）で、この門番の −89.50 と同じ大きさ。**形式の効果は P0 に閉じている。**

## この門番が言っていないこと

⚠️ **1本目の P2 の +23 秒の内訳。** 「採番順」と「揺れ」に分けるには、同じ実装を
2つの採番順で走らせる別の門番が要る。`numa_bind` の固定なし8本で P2 が
104〜143 秒に散ったことを思うと、揺れだけでも +23 秒は起こりうる。

固定していない条件での帯にも使えない（上記のとおり）。
