## なぜ要ったか

`#17` のレバーが最も乗っているのは全探索の書き出し3段で、`#16` の実測で
F2 111.17 / F5 159.64 / F6 54.43 秒（完走 906.37 秒の 35.9%）ある。ところが

**全探索は空の `dat/` から始まるので、両腕の入力は定義上同一。** フィクスチャを
揃える小道具（`#16` の `convert_fixture.py`）が要らず、そのまま対照群になる。

## 予測を1つ外した — F1 も動いた

事前に F1 は「⚠️ **動きうる**（展開する順が変わるので局所性が変わる）」と
登録してあった。実際 **−16.19 秒（区間 −17.18 … −15.20）**動いた。

F1 の区間に入っている `array("Q", unexp_boards)` は両腕とも `array` → `array` の
写しで、そこは変わらない。動いたのは**展開する順**で、`#16` は集合の反復順、
`#17` は前のラウンドが書いた順に展開する。C 側の発見済み表への当たり方が
変わったと読めるが、**この門番はそこまで分離していない**。

- `n_seen` は両腕とも **246,803,167**、`n_rehash` は両腕とも **0**（動かなかった）
- ラウンド数は **73 → 74**（未探索ファイルの分かれ方が動いた）

## この門番が言っていないこと

- **後退解析の段。** [`gate_17_no_set`](../gate_17_no_set/) が測る
- **F1 が下がった理由。** 「展開の順が変わった」までで、どの機構がいくら効いたかは
  分けていない。分けるには同じ実装を2つの順序で走らせる別の門番が要る
- 固定していない条件での帯（上記のとおり）
- **完走タイム。** 後退解析を走らせていないので出ない
