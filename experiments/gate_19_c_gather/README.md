# 門番 #19: 連番→パック値の翻訳を C 側へ移す

⚠️ **これは記録試行ではない。** 番号を取らず、タイムを `results/` にも README の記録表にも
載せない。入力を固定して後退解析だけを走らせた比較で、レギュレーションの
「空の `dat/` から完走」を満たしていない。

## なぜ `old` 腕が「計装だけ」なのか

記録 #19 は2つのことを同時にやっている。

1. **レバー** — 174段ループの `[packed[i] for i in found]`（96,802,868 回）と、
   引き分けの抽出 `[packed[i] for i in range(n_uk) if dtm[i] == 255]`
   （99,485,568 回走査して 2,682,700 採用）を C の `gatherPacked` / `gatherDraws` へ。
2. **計装** — 後退解析に境界を12か所置いた（記録 #18 まで `_profMark` の対象は
   `F0`〜`F5`、つまり全探索だけだった）。

②の費用は **#18 まで一度も測られていない**。`writeUnknownChunks` のタイマーは
関数の中で始まるのに、リスト内包は**引数なので呼ぶ前に終わっている**。
つまり新しい区間 `R_loop`→`R_draw` には「前の値」が存在しない。

→ **`old` 腕を「impl/18 ＋ 計装だけ」にする。** レバーは入れない。
これで新区間の before / after が両方出る。

| | |
|---|---|
| 腕 | `old` = `impl/18_optimized` の C・ヘッダ・`Makefile` ＋ [`old/animal_shogi.py`](old/animal_shogi.py)（計装だけ）／ `new` = `impl/19_c_gather` |
| ビルド | 両腕とも実装の `Makefile`（`gcc -O2 ... -Wall -fPIC -shared`）。門番側でフラグを書かない |
| 入力 | 両腕とも `runs/g1_11_fixture_bin/dat`（51ファイル・1.9 GB、**同一のバイト列**） |
| 並び | `old new new old` を2回、計 **8本**（対で向きを入れ替える） |
| 所要 | 39分。8本ともオラクル174行に一致（手数別局面数の合計 96,802,868） |

`runs/` は git 管理外なので、フィクスチャが無い環境では
`tools/rebuild_forward_fixture.py <元の dat/> <その run の main.log> <出力先 dat/>`
で組み直す（出力は必ず `.bin`）。⚠️ **組み直すと採番順は元と変わる。**
両腕に同じものを渡すぶんには影響しない。

両腕とも `numactl --cpunodebind=0 --membind=0` で片ノードに固定した
（CLAUDE.md の「門番は固定し、本走は固定しない」）。

## 計装そのものの検算

### `ru_minflt` は `/usr/bin/time -v` と合う

最後の境界の `min_R_uk` と、親が受け取る `Minor (reclaiming a frame) page faults` は
同じ rusage から来るので近い値になるはず。ずれていたら計装のほうが間違っている。

| | `min_R_uk`（計装） | `time -v` | 差 |
|---|---|---|---|
| `r1a_old` | 7,254,415 | 7,254,420 | 5 |
| `r1b_new` | 6,525,720 | 6,525,724 | 4 |
| `r2d_old` | 7,254,537 | 7,254,541 | 4 |
| `r2c_new` | 6,525,719 | 6,525,724 | 5 |

差は最後の境界のあとの仕事（TSV の書き出しとプロセスの後片付け）ぶん。

### minor fault が 72.9 万ページ減った

`old` 7,254,415 前後 → `new` 6,525,720 前後 で **−728,695 ページ ＝ 2.78 GiB**。
96,802,868 個の `PyLong`（1個 32 B で約 3.0 GB）を起こさなくなったぶんと桁が合う。

### ピーク RSS は動かない

両腕とも **13.83 GiB**（`Maximum resident set size` 14,498,852〜14,499,632 KiB）。
`hwm_` の列を見ると、**`P2` の末尾で 13.83 GiB に達してそれ以降1バイトも動いていない**。
`list` が消えても全体のピークは P2 が決めている、という読みが計装で直に見えた形。

| 境界 | `R_start` | `P0` | `P1` | `P2_alloc` | `P2` | 以降 |
|---|---|---|---|---|---|---|
| `hwm`（`r1a_old`） | 0.01 GiB | 1.87 | 9.85 | 10.32 | **13.83** | 13.83 のまま |

## この門番が言っていないこと

- **全探索。** `retreatAnalysis()` だけを走らせているので出ない。#19 が C に足した
  関数は全探索から呼ばれず、全探索側で変わったのは `_profMark` の `getrusage` だけ
  なので、そちらは本走で見る
- **固定していない条件での帯。** 両腕とも `numactl` で片ノードに固定してある
- **完走タイムがどれだけ縮むか。** 門番と本走の値は直接引き算しない
  （CLAUDE.md。#17 の採番順の見積もりで踏んだ）
- **比較は1対1**（`old` 対 `new`）なので多重比較の補正は要らない。
  ただし段ごとに14本引いているので、**段ごとの p 値は単一比較のものではない**。
  判断に使ったのは `loop174` と `R_draw` で、どちらも区間が 0 から遠い
