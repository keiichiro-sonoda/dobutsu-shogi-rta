# 門番 #30: 発見済み表をランクで引く到達済みビット表にする（記録試行ではない）

`impl/30_rank_seen` は、`impl/28_march_native` の全探索の発見済み表（オープンアドレス法のハッシュ表。キー 8 B、2^20 スロットから
占有率 0.5 を超えるたびに倍にして詰め直し、最終 4 GiB）を、**盤面から番号を計算で直接出す関数（ランク）を添字にした 1 ビットの表**
（106.9 MB、最初に1回だけ確保）に替えた版。#29 は欠番。初めて見た局面だけを返す意味と返す順序は変えていないので、`dat/` は #28 と
バイト一致するはず。`.py` と `Makefile` は #28 とバイト同一（ctypes から見える口は名前も型も同じ）。

## ランクの作り方と大きさ

定義域は、`normalBoard` で正規化した盤面（ライオンは盤上に1頭ずつ）。

1. **ライオンの組**: 手番側と相手の置き方 12 × 11 = 132 通りを、左右の鏡像どうしでまとめて **72 組**にする（2頭とも中央の列にある
   12 通りは鏡像が自分自身なのでそのまま）。まとめた側は盤を左右反転してから数える（分岐は使わない）
2. **残り 10 マス**: ライオンの2マスを抜いて詰め、5マスずつ 9 進数（空き・きりん・ぞう・ひよこ・にわとり × 持ち主）にして
   前計算の表（59,049 項目、236 KB）を引き、「駒の数の組（きりん・ぞう・ひよこ各 0〜2）」と「組の中の順位」を得る。前後の組を合わせ、
   種類ごとに 2 以下になる組み合わせだけを数える（27 × 27 の小さな表）
3. **持ち駒**: 盤上の数で持ち駒の合計が決まるので、下位の持ち駒の数だけを数える

| | |
|---|---|
| 値域 | 72 × 11,878,227 = **855,232,344**（到達局面 246,803,167 の **3.47 倍**）。駒の数と盤の形だけから数え、到達局面の数は使わない |
| 到達済みビット表 | 106,904,043 B（**106.9 MB**、2 MiB ページ 51 枚 = 104,448 kB）。#28 の発見済み表（4 GiB）の約 1/40。L3（35 MB）には収まらない |
| 前計算の表 | 約 0.25 MB。`seenInit` の最初の1回だけ作る |
| #31 で持つ「ランク → 連番」の対応表（見込み） | 855,232,344 × 4 B ≈ 3.4 GB（いまの索引は 8 GiB） |

**#28 の成果物の全 246,803,167 局面で単射**（不正な盤 0、値域の外 0、重なり 0）であることを、回す前に [`rank_check.c`](rank_check.c) で
確かめた（[`logs/rank_check.txt`](logs/rank_check.txt)。`impl/30` の `animal_shogi.c` をそのまま取り込んで `rankBoard` を全局面に通す）。
C の前計算の表のランクが素朴な実装（Python で同じ定義を数え上げる）と一致することは `tests/test_impl_30_rank_seen.py` が固定している。

### 止める条件3の調べ: F6 +0.61 秒・F5 +0.16 秒は malloc の mmap のしきい値による

段ごとの全表は [`logs/stats_forward.txt`](logs/stats_forward.txt) と [`logs/stats_spans.txt`](logs/stats_spans.txt)。
**F6 が +0.61 秒（区間 +0.59 … +0.63）、P2 が −0.24 秒（区間 −0.47 … −0.02）**で、0.2 秒のしきい値を超えた。F5 も +0.16 秒（しきい値の下）。

F6 のほうは、minor fault が F6 で 283,214 → 568,464 回（2倍）、F5 で +67,520 回、F1 で +67,043 回に増え、F6 のカーネル時間が +0.45 秒だった。
後退解析の段の minor fault は変わらない。仮説は glibc の malloc の **mmap のしきい値の動的な引き上げ**:

- glibc は、mmap で確保した塊を `free` すると、mmap のしきい値をその大きさ（最大 32 MiB）まで引き上げる
- `old`（#28）は発見済み表を 8 MiB から倍々に作り直すたびに古い表を `free` するので、しきい値が 32 MiB まで上がる。そのあとの
  F5・F6 の中くらいの配列はヒープから取られ、既にページの付いた領域を使い回していた
- `new`（#30）はビット表を `free` しないので、しきい値が既定（128 KiB）のままで、F5・F6 の配列が毎回新しく `mmap` され、ページのフォルトをやり直す

確かめるため、しきい値を 32 MiB に固定して（`GLIBC_TUNABLES=glibc.malloc.mmap_threshold=33554432`。固定すると動的な引き上げも止まる）
2腕を1本ずつ回した（[`diag_mmap.sh`](diag_mmap.sh)、生ログは [`logs/diag/`](logs/diag/)。**判定には使わない診断**）。

| | F1 | F5 | F6 | F6 の minor fault | F1 の minor fault |
|---|---|---|---|---|---|
| 門番 `old`（動的、6本の平均） | 62.18 | 1.47 | 1.82 | 283,214 | 321,422 |
| 門番 `new`（動的、6本の平均） | 50.65 | 1.62 | **2.43** | **568,464** | 388,466 |
| 診断 `old`（32 MiB に固定、1本） | 62.79 | 1.95 | 3.11 | 863,158 | 495,760 |

**しきい値を固定すると、F5・F6 は2腕で時間もフォルトの数もそろい（F6 のフォルトは同じ 863,158 回）、F1 の差（約 −12 秒）は残った。**
F6 の +0.61 秒はランクの効果ではなく、`old` が発見済み表の作り直しから偶然受けていた恩恵（しきい値の引き上げ）を `new` が受けなくなった
ことによる。固定すると両腕とも F5・F6 が遅くなるので、しきい値の値そのものの最適化は別の話（下の「範囲の外で見えたこと」）。

P2 の −0.24 秒（速くなる側、区間の端がほぼ 0）の原因は分けていない。診断の1本ずつでも `new` が 0.49 秒速かった（39.40 → 38.91）。
発見済み表の作り直しの履歴が無いぶん、後退解析が始まるときのヒープの状態が違うことが関わっている可能性があるが、確かめていない。

- **malloc の mmap のしきい値**: `old` が偶然得ていた恩恵から見て、F5・F6（と F1 の配列の確保）は、しきい値の扱いで 0.5 秒以上動く。
  固定の 32 MiB では両腕とも遅くなったので、値の選び方を測る価値がある（`mallopt` か、大きな配列を使い回す形）
- **`rankOf()` のインライン展開**: いまは後続ごとに `call` になっている（回す前に確かめた）
