# 門番 #30: 発見済み表をランクで引く到達済みビット表にする（記録試行ではない）

`impl/30_rank_seen` は、`impl/28_march_native` の全探索の発見済み表（オープンアドレス法のハッシュ表。キー 8 B、2^20 スロットから
占有率 0.5 を超えるたびに倍にして詰め直し、最終 4 GiB）を、**盤面から番号を計算で直接出す関数（ランク）を添字にした 1 ビットの表**
（106.9 MB、最初に1回だけ確保）に替えた版。#29 は欠番。初めて見た局面だけを返す意味と返す順序は変えていないので、`dat/` は #28 と
バイト一致するはず。`.py` と `Makefile` は #28 とバイト同一（ctypes から見える口は名前も型も同じ）。

## ランクの作り方と大きさ

定義域は、`normalBoard` で正規化した盤面（ライオンは盤上に1頭ずつ）。

1. **ライオンの組**: 手番側と相手の置き方 12 × 11 = 132 通りを、左右の鏡像どうしでまとめて **72 組**にする（2頭とも中央の列にある
   12 通りは鏡像が自分自身なのでそのまま）。まとめた側は盤を左右反転してから数える（分岐は使わない）
2. **残り 10 マス**: ライオンの2マスを抜いて詰め、5マスずつ 9 進数（空き・きりん・ぞう・ひよこ・にわとり × 持ち主）にして
   前計算の表（59,049 項目、236 KB）を引き、「駒の数の組（きりん・ぞう・ひよこ各 0〜2）」と「組の中の順位」を得る。前後の組を合わせ、
   種類ごとに 2 以下になる組み合わせだけを数える（27 × 27 の小さな表）
3. **持ち駒**: 盤上の数で持ち駒の合計が決まるので、下位の持ち駒の数だけを数える

| | |
|---|---|
| 値域 | 72 × 11,878,227 = **855,232,344**（到達局面 246,803,167 の **3.47 倍**）。駒の数と盤の形だけから数え、到達局面の数は使わない |
| 到達済みビット表 | 106,904,043 B（**106.9 MB**、2 MiB ページ 51 枚 = 104,448 kB）。#28 の発見済み表（4 GiB）の約 1/40。L3（35 MB）には収まらない |
| 前計算の表 | 約 0.25 MB。`seenInit` の最初の1回だけ作る |
| #31 で持つ「ランク → 連番」の対応表（見込み） | 855,232,344 × 4 B ≈ 3.4 GB（いまの索引は 8 GiB） |

**#28 の成果物の全 246,803,167 局面で単射**（不正な盤 0、値域の外 0、重なり 0）であることを、回す前に [`rank_check.c`](rank_check.c) で
確かめた（[`logs/rank_check.txt`](logs/rank_check.txt)。`impl/30` の `animal_shogi.c` をそのまま取り込んで `rankBoard` を全局面に通す）。
C の前計算の表のランクが素朴な実装（Python で同じ定義を数え上げる）と一致することは `tests/test_impl_30_rank_seen.py` が固定している。

### 回す前に見積もった1局面あたりの手間

実装の前に scratch で試作し、#28 の全局面を同じ順で入れて測った（コミットしていない試作。値は設計の参考）。

| | 初めて見る局面 | もう見た局面 |
|---|---|---|
| #28 のハッシュ表（倍々に作り直す） | 44.7 ns | 19.4 ns |
| ランク ＋ ビット表 | 19.9 ns | 19.8 ns |

ランクだけで約 16 ns。F1 の挿入は 938,671,869 回で、うち初めて見る局面が 246,803,167 回。もう見た局面ではランクの計算と DRAM の待ちが
ほぼ同じ重さなので、差は初めて見る局面の側（作り直しが無くなるぶん）から出る見込み。
⚠️ 実装では `rankOf()` が `nextBoardSeenNormal()` にインライン展開されず、後続1つごとに直接の `call` になった
（[`calls.py`](calls.py) で確かめた）。試作はインライン展開されていた。速さの追求は今後の課題とし、この形のまま測る。

## 腕と配置

| 腕 | 中身 |
|---|---|
| `old` | `impl/28_march_native` |
| `new` | `impl/30_rank_seen` |

差分の範囲（`.c` は発見済み集合の節だけ、`.h` はその宣言の節だけ、`.py` と `Makefile` はバイト同一）は `tests/test_impl_30_rank_seen.py` が
固定している。[`build_arm.sh`](build_arm.sh) はその実装の `Makefile` でビルドし、毎本 `.so` の sha256 の先頭を進行ログに出す
（回す前にビルドして読んだ値は `old` が `5128798ef4a5`（#28 本走と同じ）、`new` が `1948f6c159f2`）。
2腕とも `-march=native` でビルドするので、何に解決されたかを [`march.sh`](march.sh) で `logs/march.txt` に残す。

単位は完走（空の `dat/` から `python3 ./animal_shogi.py` を1本）。`old new new old` を3ブロック、計12本（各腕6本）。
どの本も `numactl --cpunodebind=0 --membind=0` でノード0に固定する（[`run_all.sh`](run_all.sh)）。
各本の前に、ノード0の 2 MiB 以上の空きブロックが 16 GiB 以上あるかを見る（[`run_one.sh`](run_one.sh)）。足りなければ自分で回避せず、
止めて人にキャッシュを落としてもらう。起動する前やキャッシュを落とす前後の値は [`free_snapshot.sh`](free_snapshot.sh) で `logs/` に残す。

## 判定に使う量

**主な判定の量は F1 のユーザー時間 ＋ カーネル時間**（`forward_summary.tsv` の `utime_F1` と `stime_F1` の和。[`f1p2_split.py`](f1p2_split.py)）。
発見済み表は F1 の中で引かれ、作り直しのときのページの用意はカーネル時間にも出るので、2つを足す。主な量は1つなので補正は要らない。
内訳としてユーザー時間・カーネル時間・F1 の minor fault・解放（`release_seen`）・全探索のピーク RSS（`hwm_F6`）も並べる。

**同点の扱い**: 主な量の区間の上端が 0 以上なら（下がったと言えない）同点か遅くなったとみなし、記録にせず欠番にする（CLAUDE.md）。

## 止める条件（[`stop_rule.py`](stop_rule.py)）

どれかに掛かったら、本走の前に止めて報告する。

1. どれかの本の `dat/` が #28 本走とバイト一致しない（md5 一覧の sha256 を `results/28_march_native/bytecompare.txt` の値と照合）、
   件数の列（`n_in`・`n_win`・`n_lose`・`n_uk`・`n_new_post`）が `results/28_march_native/forward.tsv` と違う、またはオラクル174行で落ちた
2. F1 のユーザー時間 ＋ カーネル時間の `new − old` の 95% 区間の上端が 0 以上（同点か遅くなった）
3. 動かないはずの段（F0・F2・F5・F6・P0・P1・P2・P4・`R_dtm`・`loop174`）のどれかが、区間が 0 をまたがず、かつ差の大きさが **0.2 秒以上**
   （向きは問わない）。発見済み表を触らない段なので、動いたら本走の前に原因を調べる（関数の配置など）。段の数だけ比べるので
   多重比較は未補正（安全側の条件）
4. どれかの本で `thp_fault_fallback` の前後差が 0 でない、または巨大ページが表と配列の全部に付かない。発見済み表は腕ごとに大きさが違うので、
   `anonhuge_seen_kB` のしきい値は `old` 4,194,304・`new` 104,448 kB（ビット表 51 枚）。索引 8,388,608・後退解析の配列 4,972,544 kB は両腕同じ

ほかに、落ちた本が無いことも見る。1・4 は `run_one.sh` が毎本その場で見る。
`forward.tsv` の `n_rehash` の列は `new` では常に 0 になる（作り直しが無い）ので、件数の照合には入れていない（#28 までと同じ5列）。

## 予測（門番を回す前に書いた）

| | 予測（`new − old`） | 根拠 |
|---|---|---|
| **F1 のユーザー時間 ＋ カーネル時間** | 下がる。区間が 0 をまたがない。**−2〜−8 秒**（中心 −5 秒前後） | 試作の見積りでは、初めて見る局面 246,803,167 回で 1回 約 25 ns 減り（作り直しが無くなる）、もう見た局面 691,868,702 回はほぼ同じ → 約 −6 秒。本番の挿入の順（ラウンドごとの待ち行列の順）は試作と違い、`rankOf()` の呼び出しの手間も足されるので、幅を広く取る |
| F1 のユーザー時間 | 下がる | 作り直し（延べで件数の約2倍の挿入）と 0xff 埋め（延べ 8 GiB）が無くなる |
| F1 のカーネル時間（#28 で約 2.9 秒） | 下がる。−0.3〜−2 秒 | 倍々に確保していた表（延べ約 8 GiB）のページの用意が、ビット表 107 MB の1回だけになる |
| F1 の minor fault | 数千回減る | 2 MiB ページ1枚で1回のフォルト。延べ約 8 GiB（約 4,000 枚）が 51 枚になる |
| 解放（`release_seen`、#28 で約 0.05 秒） | 小さくなる | 4 GiB の解放が 107 MB の解放になる |
| 全探索のピーク RSS（`hwm_F6`、#28 で 7.8 GB） | **約 4 GB 下がる** | 発見済み表 4 GiB がビット表 107 MB に替わる |
| 発見済み表の巨大ページ（`anonhuge_seen_kB`） | `old` 4,194,304 kB、`new` 104,448 kB | |
| F0・F2・F5・F6・後退解析の全段 | 動かない（止める条件3に掛からない） | 発見済み表を触らない。採番順も変わらない |
| 全体のピーク RSS（P2、#28 で 13.84 GiB） | 変わらない | 索引 8 GiB が残る。下がるのは #31 から |
| `dat/` | 12本とも #28 本走とバイト一致 | 初めて見た局面と順序が同じ |
| 完走タイム | 幅を出さない（参考の見込みは −2〜−8 秒） | |
