# 門番 #33: 熱い関数の置き場所を固定する（記録試行ではない）

#32 の門番で、**実行する命令が同じ P2 が、関数の番地がずれただけで +0.63 秒（区間 +0.35 … +0.90）動いた。**
#25 の門番の P2 −0.84 秒、#30 の門番の P2 −0.24 秒にも、置き場所の効果が混ざっていた可能性がある。
残っているレバーは1つあたり1秒前後かそれ以下が多い。C を1か所変えるたびに後ろの関数がずれて段が動くと、
レバーの効果と置き場所のぶんを分けられない。

`impl/33_hot_layout` は、熱い関数を `.text` の前の専用の区画に並べ、ほかの関数を変えても動かないようにした版。
**この記録の目的は速さではなく、以後の門番が「変えたコードの効果」だけを測れるようにすること**（#9 が「目的はピーク RSS」だったのと同じ扱い）。

## 何を変えたか

`.c` / `.h` / `.py` は #32 とバイト同一。変えたのは2つ:

- `Makefile` の `gcc` 行に `-ffunction-sections`（関数ごとに `.text.<名前>` の区画を作る）と `-Wl,-T,hot_layout.ld` を足した。最適化の指定は変えていない
- [`hot_layout.ld`](../../impl/33_hot_layout/hot_layout.ld)（新規）: 既定のリンカースクリプトに `INSERT BEFORE .text` で区画 `.text.hot_layout` を足し、
  熱い関数12個を #32 の `.so` と同じ順に並べる。**区画の先頭は 4 KiB、関数の先頭は 64 バイトの区切り**

熱い関数は、F1・P1・P2・P4・174段ループで実行される C の関数:
`invBoard`・`nextBoardInvNormal`・`indexBuild`・`nextBoardIndexNormal`・`nextBoardSeenNormal`・
`predCount`・`predScatter`・`expandRound`・`retreatStep`・`buildSuccRange`・`gatherPacked`・`gatherDraws`。
#32 の `.so` で、これらがインライン展開せずに呼ぶ自前の関数は、この中の関数と `seenInit`（最初の1回だけ）しか無い
（`expandReserve` は展開されている）。libc の `memcpy`・`memset`・`memmove`（`.plt` 経由）は固定の外。

**一覧は `perf` で確かめて、`normalBoard` を外した**（[`logs/perf_top.txt`](logs/perf_top.txt)）。初めの読みには `normalBoard` も入れていたが、
呼び出し元の `nextBoardInvNormal` に全部インライン展開されていて、外にある実体は解析の中で実行されない（Python から `ctypes` で引けるだけ）。
`old`（#32）を門番と同じくノード0に固定して1本、`perf record -F 499` で標本 68,370 個（オラクル174行 PASS）:
`animal_shogi.so` が 85.93%（上の12個がすべて標本を持ち、`normalBoard` は 0）、カーネル 10.36%、libc 3.27%、Python 0.41%。
`perf` は計測機の `perf_event_paranoid` を一時的に 4 → 1 にして使った（終わったら 4 に戻す）。

`__attribute__((hot))` と `section` 属性は使わなかった。`hot` は最適化を強め、`section` 属性は gcc の関数の分割を止めるので、
どちらも命令が変わりうる。`-ffunction-sections` とリンカースクリプトなら C を触らずに済む。

### 固定できる範囲

- **熱くない関数を変えても、熱い関数は1バイトも動かない。** 熱くない関数は後ろの `.text` に入る。区画の先頭を 4 KiB に揃えたので、
  前の `.plt` が伸びても（新しい libc の関数を呼ぶなど）区画は動かない（いまは `.plt.sec` の終わりが `0x11c0`、区画の先頭が `0x2000`）。
  前の区画が 4 KiB の区切りを越えるほど伸びたときは、区画は 4 KiB の倍数で動き、ページの中の位置は変わらない
- **熱い関数そのものを変えたら、後ろの熱い関数はずれる。** ずれは 64 バイト単位になり、命令の読み込みの区切りに対する位置は保たれる。
  解読済み命令の置き場（uop キャッシュ）や分岐予測の表の当たり方までは保証できない
- 熱い関数ごとに 4 KiB に揃える案は採らなかった。全部の先頭が L1 命令キャッシュの同じ組に集まって取り合うため
- 実行時の番地は、読み込む位置（4 KiB の倍数）だけずれる。ページの中の位置と、熱い関数どうしの相対の位置は変わらない

## 回す前に確かめたこと（番地で。時間は測らない）

[`layout.py`](layout.py) の出力は [`logs/layout.txt`](logs/layout.txt)。同じことを `tests/test_impl_33_hot_layout.py` が固定している。

**詰め物の検査**: `.c` に熱くない関数（N バイトの `nop` を持つだけ。呼ばれない）を足して両腕の `Makefile` でビルドし、
熱い関数12個のうち番地が動いた数を数えた。

| 足した場所 | 腕 | 8・24・40・100・1000 バイト |
|---|---|---|
| ファイルの頭 | `old`（#32 の作り方） | 12個全部が動く（末尾の関数は +16・+32・+48・+112・+1008） |
| ファイルの頭 | `new` | 0 |
| `nextBoardSeenNormal` の前 | `old` | 後ろの8個が動く |
| `nextBoardSeenNormal` の前 | `new` | 0 |
| 末尾 | 両腕 | 0 |
| 新しい libc の関数（`getpid`）を呼ぶ関数を末尾に | `old` / `new` | 12 / 0 |

**命令の比較**: 両腕の全32関数で、命令の並びと命令ごとのバイト数が同じ（番地の数値を除く。関数の後ろの詰め物は関数の大きさの外なので比べない）。
全32関数で 2,932 命令、うち熱い関数12個で 1,547 命令。

## 記録にするかの取り決め

**速さの向きは予測しない。** 置き場所が変われば ±0.5 秒前後はどちらにも動きうる。判定の量は、熱い関数の段 **F1 と P2 の秒**
（`forward_summary.tsv` の `F1`、`retreat_summary.tsv` の `P2`。[`f1p2_split.py`](f1p2_split.py)）。

- F1・P2 がどちらも同点か速い（区間の下端が 0 以下）→ **本走して記録にする**（同点でも記録にする。目的は以後の測りやすさ）
- F1 か P2 の `new − old` の区間が 0 をまたがずに上（遅くなった）→ **本走の前に止めて報告する。** 続けるかは本人が決める。
  固定した配置がたまたま悪い当たりだった場合に、揃え方を変えて引き直すのは選択の偏りになるので、勝手にやらない

2つの段を別々に比べるので、多重比較は未補正（止める側に倒れやすい向きなので、そのままにする）。

## 止める条件（[`stop_rule.py`](stop_rule.py)）

どれかに掛かったら、本走の前に止めて報告する。

1. どれかの本の `dat/` が #32 本走とバイト一致しない（md5 一覧の sha256 を `results/32_inline_rank/bytecompare.txt` の値と照合）、
   件数の列（`n_in`・`n_win`・`n_lose`・`n_uk`・`n_new_post`）が `results/32_inline_rank/forward.tsv` と違う、またはオラクル174行で落ちた
2. 上の「遅くなった」
3. どれかの本で `thp_fault_fallback` の前後差が 0 でない、または巨大ページが表と配列の全部に付かない（両腕とも #30〜#32 と同じ確保:
   発見済み表 104,448・索引 8,388,608・後退解析の配列 4,972,544 kB 以上）

ほかに、落ちた本が無いことも見る。1・3 は `run_one.sh` が毎本その場で見る。
置き場所が変われば全段が動きうるので、#32 の門番にあった「動かないはずの段」の条件は置かない（段ごとの差は全部表に出す）。

## 置き場所の振れの大きさを測る本（判定には使わない）

判定の12本のあとで、[`run_pad.sh`](run_pad.sh) が `.c` の頭に 24・40・1000 バイトの詰め物の関数を足した版を、
#32 の配置（`old_pad<N>`。熱い関数が +32・+48・+1008 バイトずれる）と #33 の配置（`new_pad<N>`。ずれない）で各3本、計18本回す。
進行は `logs/pad_console.log`（判定の `console.log` と混ぜない）。並びは3ブロックで、ブロックごとに腕の位置を変える（`run_pad.sh` の先頭）。
[`pad_split.py`](pad_split.py) が、同じ配置の中で詰め物の大きさを変えたときの差（3組）と、平均の幅を段ごとに出す。

**予測**: #32 の配置では詰め物の大きさで P2（と F1）が動き、#33 の配置では動かない（差の区間が 0 をまたぐ）。
これが置き場所の振れの大きさの、初めての直接の測定になる。段ごと・組ごとに比べるので多重比較は未補正。各腕3本なので、
「#33 の配置で動かない」は「その本数では差を確定できなかった」までしか言えない。
