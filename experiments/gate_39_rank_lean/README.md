# 門番 #39: 局面の番号の計算 `rankOf` の命令を値を変えずに減らした `impl/39_rank_lean` を、#38 と完走で比べる（記録試行の門番）

`old` ＝ `impl/38_precheck`（記録 #38）、`new` ＝ `impl/39_rank_lean`。どちらもその実装の `Makefile` でビルドする（[`build_arm.sh`](build_arm.sh)）。
作りは [`gate_38_precheck`](../gate_38_precheck/) を写した。巨大ページの空きの下限だけ、既定を 16 GiB から **8 GiB** に直した（`tools/run.sh` と同じ。`.claude/rules/experiments.md`）。

## 何を比べるか

`impl/39_rank_lean` は `impl/38_precheck` に、実験 [`rank_fast`](../rank_fast/) の [`patches/lean.patch`](../rank_fast/patches/lean.patch) を当てただけの実装。
変わるのは `rankOf`（どこでもインライン展開される）と、表を作る `rankTablesBuild`（表 `g_rank_keep[144]` と `g_rank_hpart[27][64]` を足す）だけで、
`.py`・`Makefile`・`hot_layout.ld`・ヘッダ・既存の表の中身・`rankFindKoma`・`rankSqueeze`・生成器・逆向きの生成器・呼び出し側は #38 とバイト同一
（[`tests/test_impl_39_rank_lean.py`](../../tests/test_impl_39_rank_lean.py)）。

`rankOf` の3か所を、値を変えずに書き換えた:

1. **ライオンの2マス**: 4ビットの駒の値の下位3ビットが `100` なのはライオン（4 と 12）だけなので、`(b >> 2) & ~(b >> 1) & ~b & 0x111111111111` で両方の印を1回で作り、
   上のビット（持ち主）で分けて `tzcnt` する（`rankFindKoma` を2回呼ぶ代わり）
2. **詰め**: 反転したあとの盤からライオンの2マスを抜いて詰めるのを、`rankSqueeze` 2回から、2マスを抜くマスク `g_rank_keep[ライオンの組]` での `pext` 1回にする（BMI2）
3. **持ち駒の部分**: 前後の組の和 `s0 + s1` は合わせた組と同じ値（正しい盤では種類ごとに 2 以下なので3進の桁が上がらない）なので、掛け算と足し算を `g_rank_hpart[s0 + s1][h & 63]` の1回の読みにする

**番号の値は1つも変わらない**（`rank_fast` の一致の検査: 到達可能な全 246,803,167 局面・それを q にした全候補 1,159,932,122・乱数の正しい盤 1 億で不一致 0。
[`../rank_fast/logs/verify_lean.txt`](../rank_fast/logs/verify_lean.txt)）。発見済みの表・`g_prep`・`g_dtm` の添字が同じなので、全探索の待ち行列も、後退解析が局面を決める順も、
`dat/` も #38 と同じになるはず。`rankOf` は全探索の F1（後続ごと）・後退解析の `U_loop`（前任の候補ごと）・`U_draw`（未知局面ごと）のどこでも展開されているので、3つの段に効く。

`rank_fast` の推奨にある「番号の付け方そのものを変える案」（鏡像でまとめない、前後の組で区切らない）は入れていない。どれも別のレバー。

### 0.5〜0.75 の係数がこのレバーに当てはまるか

段ごとに分けて考えた。

- **F1 には当てはまると見る（ただし幅を上に広げる）。** `perf_38` で #38 の F1 は、局面1つに約 3 回の書き込みが L2 で外れ（`g_prep[rb]` と発見済みの表のビット）、
  書き込みの溜まりで 98 cycles / 局面（16%）止まっていた。#38 の先行判定で消えた仕事 45 cycles のうち 34 が、溜まりの空きを待つ時間に食われた。
  この食われ方は「消した仕事がキャッチ局面の短い仕事だったから」ではなく、「F1 の書き込みの間の仕事を縮めると、書き込みが詰まって溜まりを待つ」ことから来ている。
  `rankOf` は後続ごとに、発見済みの表のビットを立てる書き込みと `g_prep` への書き込みの間で回るので、縮めれば同じように書き込みが詰まる。
  `rank_fast` の段1で本物の `rankOf` がベンチとほぼ同じ重さ（本物 50〜54、ベンチ 47）だったのは「`rankOf` 自身が文脈で遅くなっていない」ことで、
  「消したときに隠れていた待ちが表に出ないか」は言わない。一方で、#38 では局面の 57%（キャッチ局面）の仕事がまるごと消えて書き込みのある局面どうしが詰まったのに対し、
  `rankOf` の減りは書き込みのある後続に薄く散らばる（1後続あたり −9 cycles）ので、#38 ほどは食われないかもしれない。そこで F1 は **換算の 45〜90%** と見る
- **`U_loop` には当てはまらないと見る（70〜110%）。** 係数の根拠は F1 の書き込みの溜まりで、`U_loop` では測っていない。`U_loop` のベンチの換算は過去の門番で
  #36 111%・#37 101% とほぼそのまま出ている。`benchUnmove` で増えた予測ミス ＋0.28 / 局面（＋4〜6 cycles）はベンチの差にもう入っているので、
  置き場所のずれ（逆向きの生成器が −192 バイト）で同じことが本物で起きれば換算どおり、起きなければ換算より少し大きく出る
- **`U_draw` は 50〜120%。** ベンチが無く、`rankOf` だけのベンチの差から出した。`U_draw` の 83% が `rankOf`（`rank_fast` の段1）で、まわりは手数の行を先読みして読むだけ
