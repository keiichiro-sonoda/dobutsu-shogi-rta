# 門番 #40: 後退解析 `U_loop` で `g_dtm` の先読みを1局面先にした `impl/40_dtm_ahead` を、#39 と完走で比べる（記録試行の門番）

`old` ＝ `impl/39_rank_lean`（記録 #39）、`new` ＝ `impl/40_dtm_ahead`。どちらもその実装の `Makefile` でビルドする（[`build_arm.sh`](build_arm.sh)）。
作りは [`gate_39_rank_lean`](../gate_39_rank_lean/) を写した（巨大ページの空きの下限は 8 GiB のまま）。

## 何を比べるか

`impl/40_dtm_ahead` は `impl/39_rank_lean` に、実験 [`dtm_ahead`](../dtm_ahead/) の [`patches/ahead1.patch`](../dtm_ahead/patches/ahead1.patch) を当てただけの実装。
変わるのは `unmoveStep()` の中だけで、`.py`・`Makefile`・`hot_layout.ld`・ヘッダ・ほかの関数は #39 とバイト同一（[`tests/test_impl_40_dtm_ahead.py`](../../tests/test_impl_40_dtm_ahead.py)）。

[`perf_39`](../perf_39/) で、#39 の `U_loop` の約 6.0 秒が `unmoveStep` の1行（未定の候補をふるう `g_dtm` の読み）に付いた。番号を出して `prefetchw` したすぐあとに
同じ局面の候補を読むので、先読みが間に合っていなかった。`#40` は候補と番号の配列を2組持ち、**局面 i の候補をふるう前に、局面 i + 1 の候補を作って番号を出し、先読みを頼む**
（ループの前で先頭の局面の候補を作り、最後の局面では次を作らない）。候補を作ることと番号を出すことは `g_dtm` も `g_prep` も見ず、局面 i をふるう・決めるのは局面 i − 1 を
決め終えたあとで、ふるう・決めるの中身も1文字も変えていないので、**決める順も `found` に積む順も #39 と同じ**。`dat/` は #39 とバイト一致するはず。

`g_prep` の先読みも早める案（`dtm_ahead` の推奨の4つ目）は入れていない。別のレバー。

## 記録にするかの取り決め（回す前に決めた）

速さだけのレバーなので、#35〜#39 と同じ扱い。

- 完走の `new − old` の区間の上端が 0 より下 → **本走して記録にする**
- 区間が 0 をまたぐ → **本走せずに止めて報告する**（欠番にするかは本人が決める）
- 区間の下端が 0 より上（遅くなった）→ **本走せずに止めて報告する**

## 配置と条件（回す前に決めた）

- 単位は完走（空の `dat/` から1本）。`old new new old` を3ブロック、計12本（**`old` 6本・`new` 6本**。[`run_all.sh`](run_all.sh)）
- どの本も `numactl --cpunodebind=0 --membind=0`。各本の前にノード0の 2 MiB 以上の空きを読んで `logs/<ラベル>_hugefree.txt` に残し、**8 GiB** に満たなければ走らせずに止める。
  配列は変わらない（足したのは `unmoveStep` のスタックの 16 KiB だけ）ので、空きの基準は測り直さない
- **門番の前に1本、`new` を完走させて答えの検査を通す**（[`run_trial.sh`](run_trial.sh)。`dat/` 全213ファイルを #39 本走の `dat/` と `diff -rq` でも比べる。
  計時には使わない。通らなければ `run_all.sh` は回さない）。**`new` の答えの検査は、この1本と門番の6本で計7本**
- 回す前に、CPU 使用率（全 CPU）が 3% 以下（ほかの計算が動いていない）ことを確かめ、load average と CPU 使用率だけを残す。`impl/39_rank_lean`・`impl/40_dtm_ahead` に `__pycache__` が無いこと

## 止める条件（回す前に決めた）

1. 答えの検査が1本でも外れる（**`dat/` の md5 一覧の sha256 が #39 本走と違うことも含む**。決める順が同じはずなのに一致しないなら、一致の検査が見落とした違いがある）
2. `impl/40_dtm_ahead` の `.so` が `ahead1` の `.so` とバイト一致せず、かつ一致の検査を回し直して外れる（上で一致を確かめたので、ここは掛からない）
3. 上の取り決めで「確定しない」「遅くなった」
4. どれかの本で `thp_fault_fallback` の前後差が 0 でない、または巨大ページが表と配列に付かない
5. 巨大ページに使える空きが下限（8 GiB）に満たない（走らせずに止めて本人に知らせる。キャッシュは本人が落とす）

## 予測（回す前に書いた）

手がかりは実験 `dtm_ahead` の完走の比較（同じ計測機・同じ `numactl` の固定・同じ2つの `.so`・各腕6本・`base ahead1 ahead1 base` × 3）:
**`U_loop` −2.74 秒（−2.90〜−2.57）、完走 −2.89 秒（−3.19〜−2.59）**、ほかの段は ±0.13 秒の中（F1 −0.13（−0.29〜＋0.04）、`U_draw` −0.03）。
**この比較は記録の門番ではないので、判定の証拠には使わない**（予測の根拠にだけ使う）。同じ扱いの前例は `mirror1_keep` → #37 で、比較の −9.47 秒に対して門番で −9.97 秒（105%）。
`perf` では、ふるいの `g_dtm` の読みの行が 194 → 21 cycles / フロンティア（約 5.3 秒ぶん）に下がり、決めるの `g_prep` の読みの行が 45 → 100 に増え（＋1.7 秒）、命令が ＋50 / フロンティア。
生成器だけのベンチの換算は、このレバーには無い（ベンチに `g_dtm` が無い）。
