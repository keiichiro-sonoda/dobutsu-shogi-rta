# gen_bench: 指し手生成器だけを取り出して測る（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。

## 目的

#25 の段の大きい順は **F1 展開 73.6 s（45%）、P2 後続生成 45.4 s（28%）**。どちらも中心は C の
`nextBoardInvNormal()` で、この関数は `baseline/` から実質1行（#20 の `moves = NULL`）しか変わっていない。
本走を回さずに、次にこの関数に手を入れるための材料を取る。

**最初の目的は、いまの生成器の時間を局面の種類ごとに分けること。** F1 の平均は1局面 298 ns だが、
キャッチ局面（後続を表に入れない）とそれ以外の内訳は、いまの計装では分からない。

候補は2つ。

| 候補 | 何をするか | 効く段 | パッチ |
|---|---|---|---|
| **A. キャッチの先行判定** | 反転する前の盤で「相手のライオンを取れるか」だけを先に決め、取れれば 0 を返す。外れたらいまの生成器 | F1 だけ（記録にするなら `nextBoardSeenNormal()` にだけ入れる想定） | [`catchfirst.patch`](patches/catchfirst.patch) |
| **B. ループを使わない `invBoard()`** | 盤の反転（12マスを1つずつ読み直して詰め直す）を、バイトの逆順・ニブルの入れ替え・空きでないマスのマスクで作る | F1 と P2 | [`invbits.patch`](patches/invbits.patch) |

どちらのパッチも `impl/25_huge_retreat/animal_shogi.c` に当てる。

- **A は反転前の盤で判定する**ので、キャッチ局面では `invBoard()` ごと省ける。相手のライオンのマスを探し、
  その周り8方向に「その向きにライオンのマスへ動ける手番側の駒」があるかだけを見る。
  - 反転との対応（手の向きの符号、盤の端の条件、ひよこの条件）はパッチのコメントに書いた
  - 反転後の盤で判定する書き方は測っていない
- **B は出力が同じなので、生成器の戻り値と後続の列も変わらない。** 全局面で出力を突き合わせて確かめる。

## 入力

**#25 本走の `dat/`（213ファイル、246,803,167 局面）。** 到達可能な全局面をちょうど1回ずつ含み、形式は F1 の入力と同じ
64ビットの値。`dat/` は git に入れない（`runs/` に置いたまま）。

- **局面の種類は、いまの生成器の戻り値で決める**（0 ＝ キャッチ、−1 ＝ トライ負け、正 ＝ 未知）。
  ファイル名では決めない。`win001te` には後退解析が決めた「1手で勝てる非キャッチ局面」も入っている
- **一致の検査は全局面で行う**（[`run_verify.sh`](run_verify.sh)）
- **計時は 1,000万局面で行う。** 固定シード（splitmix64、シード 20260928）で種類ごとに全体の比率で抜き出し、
  種類ごとの列（抜き出した順）と、3種類を混ぜて並べ替えた列を作る
  - 抜き出した局面も git に入れない（`runs/gen_bench/sample/`）
  - 抜き出し方と件数は `logs/sample.txt` に残す

## 条件

- **生成器は、本番と同じビルドの `.so` から呼ぶ**（[`build_so.sh`](build_so.sh)）
  - `impl/25` の `Makefile` のまま、`gcc -O2 ... -Wall -fPIC -shared` でビルドする
  - ベンチ本体（[`bench.c`](bench.c)）は `.so` を `dlopen` して関数ポインタで呼ぶ
  - `.c` ごと1つの実行ファイルにすると、同じ `.so` の中の `normalBoard()` / `invBoard()` の呼び出しが
    インライン展開されるようになり、本番より速く出る（#18 で確かめた条件）
  - `base` の `.so` は #25 本走と同じバイト列（sha256 の先頭 `ed5df6fa4b89`。門番 #25 の `new` と同じ）
- **計時**（[`run_time.sh`](run_time.sh)）
  - 1本ごとに別のプロセスで、`.so` を1つだけ開く（本番の `CDLL` と同じ `RTLD_LOCAL`）
  - `numactl --cpunodebind=0 --membind=0` で固定する
  - 4つの版を7周まわし、周ごとに順番を1つずつずらす
  - 各列を1周温めてから1周測る。計時するのは生成器の呼び出しだけで、入力の読み込みと一致の検査は計時の外
  - 周波数の標本を `logs/freq.log` に取る
- **版どうしの差は、同じ周の `base` との差を周ごとに取ってから、中央値と範囲を出す**（[`summary.py`](summary.py)）

## 止める条件（回す前に決めた）

どれかの候補で一致の検査が1局面でも外れたら、その候補は計時せずに報告する（`run_time.sh` が `logs/verify.txt` を見る）。
一致の条件は次のとおり。

- **B**: 全局面で `invBoard()` の出力が1ビットも違わないこと。生成器の戻り値と後続の列も突き合わせる
- **A と AB**: 戻り値が全局面で一致し、正のときは後続の列が順番まで一致すること。戻り値が 0 か −1 のときは後続を
  比べない（呼び出し側の `nextBoardSeenNormal()` と `nextBoardIndexNormal()` は、戻り値が 0 以下なら後続を読まない）

## 予測（回す前に書いた）

大きさは根拠のあるものだけにした。根拠の無いところは向きだけにした。

| # | 予測 | 根拠 |
|---|---|---|
| 1 | 種類ごとの時間は **キャッチ ＜ トライ負け ＜ 未知** | キャッチは取れる手に当たった時点で止まる。トライ負けは盤の駒を全部見るが、持ち駒を打つ手を作らない。未知は平均 9.4 個の後続を作る（辺 938,671,869 ÷ 未知 99,485,568） |
| 1 | 未知局面は **456 ns 未満** | #25 本走の P2 は1局面 456 ns（45.4 s ÷ 9,949万）で、生成器に索引引きが乗った値 |
| 2 | いまの `invBoard()` 単体は **10〜30 ns** | 12マスのループで、空きマスの分岐（盤上の駒は多くて8個）が読みにくい |
| 3 | ループを使わない `invBoard()` 単体は **数 ns** | 分岐の無い十数命令 |
| 4 | B を組み込んだ生成器は、3種類とも下がる。**下がり幅は 2 と 3 の差より小さい** | 生成器の中では、`invBoard()` の費用の一部がほかの計算と並んで隠れる |
| 5 | A はキャッチ局面で大きく下がる。**未知とトライ負けは、先行判定のぶん増える** | 外れる局面は、ライオンを探すループ（最大12マス）と8方向を見てから、いまの生成器をそのまま呼ぶ |
| 6 | A＋B は、未知とトライ負けではほぼ A と B の足し算。**キャッチ局面では B が効かない** | キャッチ局面は A が反転の前に 0 を返すので、`invBoard()` を呼ばない |
| 換算 | B は F1 ＋ P2 で数秒の桁（3.46億回 × 1回あたりの差） | 呼ばれる回数は F1 の 246,803,167 ＋ P2 の 99,485,568 |
| 換算 | A は F1 で「(キャッチ局面のいまの時間 − 先行判定の時間) × 1.40億 − 先行判定の時間 × 1.07億」 | キャッチ局面は 140,298,614、それ以外は 106,504,553。キャッチ局面の時間はこの実験で初めて出る |

⚠️ 換算は生成器だけの差で、F1 の発見済み表への挿入や P2 の索引引き（先読み・巨大ページ入り）との重なりは入らない。
本当の効果は、記録にするときの門番で測る。

## 結果（回したあとで書いた）

### 一致の検査: 3つの候補とも全局面で一致した

[`logs/verify.txt`](logs/verify.txt)。止める条件には掛からなかった。

- B: 246,803,167 局面で、`invBoard()` の出力の不一致 0、生成器の戻り値と後続の列の不一致 0
- A と AB: 戻り値の不一致 0、後続の列（戻り値が正のとき）の不一致 0

いまの生成器の戻り値で決めた種類は、キャッチ 140,298,614 / トライ負け 7,018,985 / 未知 99,485,568 で、
本番の F1 の件数とちょうど同じだった。抜き出しはキャッチ 5,684,636 / トライ負け 284,396 / 未知 4,030,968
（計 1,000万。[`logs/sample.txt`](logs/sample.txt)）。

**いまの生成器は、キャッチ局面でも 1局面 156 ns かかっていた。うち約 40 ns が `invBoard()`。**
キャッチ局面は取れる手に当たれば止まるが、その前に盤を反転し、先頭のマスから順に手を作り始めるので、

混ぜた列に近いので、下の換算（種類ごとの差 × 件数）は、この 5〜8 ns のぶんを含まない。

### 本走への換算

種類ごとの差の中央値 × 本番の件数。A は F1 の経路にだけ入れる想定なので、P2 には B のぶんだけを数える。

| 版 | F1 | P2 | 計 |
|---|---|---|---|
| `B` | -9.72 | -3.98 | **-13.70** |
| `A` | -12.43 | 0 | **-12.43** |
| `AB` | -16.49 | -3.98 | **-20.47** |
| `AB` − `B`（B の上に A を足したぶん） | -6.85 | 0 | -6.85 |

⚠️ 生成器だけの差で、F1 の発見済み表への挿入や P2 の索引引き（先読み・巨大ページ入り）との重なりは入らない。
C を変えるので、#23・#25 と同じく後ろの関数の番地もずれる。本当の効果は、記録にするときの門番で測る。

`invBoard()` を軽く見ていたのが、いちばん大きな外れだった。12マスを1つずつ読み、空きかどうかで分岐し、
駒のあるマス（盤上の駒は多くて8個）ごとに詰め直していて、1回 46 ns かかっていた。

### A の先行判定は、外れたときの費用が大きい

先行判定が外れる局面（未知とトライ負け）は、1局面あたり 33〜45 ns 増えた。先行判定は、相手のライオンのマスを
ループで探し（最大12マス）、周り8方向を分岐で見る書き方にした。キャッチ局面の 122 ns の節約の3分の1を、
外れた局面で払っている。未知とトライ負けは F1 の入力の43%あるので、この費用が A の換算を削っている
（B の上に足すと −6.85 秒で、単独の −12.43 秒の約半分）。先行判定を分岐の少ない形（ライオンのマスをビット演算で
探す、8方向の利きを表引きでまとめて見るなど）にすれば外れたときの費用は下がりうるが、この回では測っていない。

## この回で言えないこと

- **本走の段の値。** 生成器だけを、抜き出した1,000万局面で、温めたあとに測った値で、F1 の発見済み表への挿入や
  P2 の索引引きと重なったときの値ではない
- **関数の置き場所の効果。** 本番の `.so` と同じビルドだが、C を足した版は後ろの関数の番地がずれる。ベンチは生成器の
  関数だけを呼ぶので、F1 と P2 のほかの関数への影響は出てこない
- **並びの効果。** 種類ごとの列は抜き出した順（種類の中で無作為）、混ぜた列は3種類を無作為に並べ替えた順で、
  本番の待ち行列の順ではない

## 思いついたが混ぜなかったもの

- 先行判定を分岐の少ない形にする（上の節）
- `normalBoard()` の呼び出し（未知局面で平均 9.4 回、`-fPIC -shared` なので同じ `.so` の中でも関数呼び出しのまま）。
  `-fno-semantic-interposition` はこれをインライン展開させるレバーで、README のレバー表（いまは [`docs/levers.md`](../../docs/levers.md)）に残っている
- 手の生成の表引き化・分岐の削減

## 推奨（決めない）

| 順 | 候補 | 推奨 | 理由 |
|---|---|---|---|
| 1 | **B**（ループを使わない `invBoard()`） | **記録にする** | 換算 −13.70 秒で、3種類とも 38〜40 ns ずつ下がり、悪くなる局面が無い。F1 と P2 の両方に効く。出力が同じ関数の中身を替えるだけで、全局面で一致を確かめてある |
| 2 | **A**（キャッチの先行判定） | **B のあとに、外れたときの費用を下げてから測り直す** | B の上に足すと −6.85 秒。外れた局面が 33〜45 ns 払っていて、ここを下げる余地がある。F1 の経路（`nextBoardSeenNormal()`）にだけ入れる設計になる |

どちらも記録にするときは、記録にする版そのものを門番で測り直す。
