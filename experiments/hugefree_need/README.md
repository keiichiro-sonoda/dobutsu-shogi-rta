# hugefree_need: 走る前に確かめる「巨大ページに使える空き」の基準を、今の作りに合わせて測り直す（記録試行ではない）

番号を取らず、`impl/` を作らず、`results/` にも README の記録表にも載せない。速さは測らない（秒は参考）。

## 目的

`tools/run.sh` と門番の `run_one.sh` は、走る前に `/proc/buddyinfo` の order 9 以上（2 MiB 以上の空きブロック）を数え、**16 GiB**（`HUGEFREE_MIN_GIB`）に満たなければ走らせずに止める。
16 GiB は記録 #23 のときに「後退解析の索引 8 GiB と、発見済み表を作り直す瞬間の 2 ＋ 4 GiB に余裕を見た値」として決めた（[`docs/lessons.md`](../../docs/lessons.md)）。
ところが #34 で後退解析の作りを替えて**索引は無くなり**（ピーク RSS 14.88 → 3.69 GB）、#30 で発見済み表の作り直しも無くなった。基準だけが #23 の作りのまま残っていて、
完走を何本も回すたびにノード0の空きが 16 GiB に近づき、本人が root でキャッシュを落としている（#34・#37・#38 の門番の前）。

ここでは、**今の作り（`impl/38_precheck`）が1本の完走のあいだに 2 MiB 以上の空きブロックをどれだけ使うか**を測り、その値から新しい基準を決める。

## 何を「使う量」とするか（回す前に決めた）

基準が守りたいのは「走り始めるときに、その本が巨大ページを頼むたびに 2 MiB の塊が残っていること」。塊を減らすのは巨大ページそのものだけでなく、`dat/` の書き出しで増えるページキャッシュ
（約 2 GB）や、Python の小さな確保が大きな塊を割ることもある。だから巨大ページの量ではなく、**塊の空きそのものの減り方**を主に測る。

- **主: 消費量** ＝ 走る前の 2 MiB 以上の空き − 走っているあいだのその最小値（GiB）。`pin` はノード0、`free` はノード0・ノード1・両ノードの合計
  （合計は読みごとに2つのノードを足してから最小を取る）
- 並べて出す: プロセスの `AnonHugePages`（`/proc/<pid>/smaps_rollup`）の最大、`/proc/vmstat` の `thp_fault_alloc`・`thp_fault_fallback`・`thp_collapse_alloc`・`compact_stall` の前後差、
  走り終わった直後と `dat/` を消したあとの空き（**持ち越し** ＝ 走る前 − `dat/` を消したあと）、ピーク RSS、段ごとの秒（参考）
- 最小が起きた段: 0.2 秒おきの読みの時刻を、段の秒と突き合わせる（[`summary.py`](summary.py) の冒頭の近似。境目の前後 0.2〜0.4 秒は取り違えうる）

## 測り方

- [`run_one.sh`](run_one.sh): `impl/38_precheck` を `runs/hugefree_need/<ラベル>/` に写してその `Makefile` でビルドし（`impl/` は触らない）、空の `dat/` から完走を1本回す。
  `tools/run.sh` は使わない（`results/` に書かない）
- [`sampler.py`](sampler.py): 走っているあいだ **0.2 秒おき**に、`/proc/buddyinfo` のノード0と1の 2 MiB 以上の空きと、Python のプロセスの `smaps_rollup` の `AnonHugePages`・`Rss` を
  `logs/<ラベル>_samples.tsv` に書く。**読むだけで、計測される側には手を入れない**（`.so` も `.py` も記録のまま）。道具の動作は、回す前にダミーのプロセスで確かめた（数は使っていない）
- 走る前（`logs/<ラベル>_before.txt`）と、走り終わった直後・`dat/` を消したあと（`logs/<ラベル>_after.txt`）の `/proc/buddyinfo`、`vmstat` の前後（`logs/<ラベル>_vmstat.tsv`）も残す
- **取りこぼしの見込み**: 0.2 秒より短い山は読めない。大きな確保（準備の配列・手数の配列はどちらも 0.86 GB）はページを付けながら 0 で埋めるので、1 GiB 進むのに 0.2 秒以上かかる
  （#38 の `U_init` は 1.8 秒で 0.86 GB を作る）。だから、1回の読みの間に減る量は多くて 0.5 GiB ほどと見る。読みが拾った `AnonHugePages` の最大と、
  `thp_fault_alloc` の前後差 × 2 MiB（延べで、同時ではない）を並べて、読みが巨大ページの山を見落としていないかを見る

## 新しい基準の決め方（回す前に決めた）

- **新しい基準 ＝ `pin` 3本のノード0の消費量の最大 × 1.5 を、GiB の整数に切り上げたもの**。ただし `free` 2本で、どちらかのノードの消費量がそれ（`pin` の最大）を超えたら、
  そちらの最大で同じ計算をする
- **1.5 の理由**: 3本しか見ていない（本ごとの振れと、ノードの断片化の具合で消費量は動く）ことと、0.2 秒おきの取りこぼし（上の見込みで1回の読みの間に 0.5 GiB ほど）。
  係数は 1.5 に決めた（回す前に）。消費量が 5 GiB なら余裕は 2.5 GiB で、取りこぼしの見込みの5倍ある
- 新しい基準は、門番（ノード0で比べる）と `tools/run.sh`（両ノードの合計で比べる）の両方の既定値にする。合計で比べる側には厳しめに働く
- 止める（基準を決めない）:
  - **新しい基準が 16 GiB 以上** → 基準は変えずに止めて報告する（今の 16 GiB が古いという見立てが外れた）
  - **消費量が本ごとに大きく違う**: 5本の「その本の消費量」（`pin` はノード0、`free` は両ノードの合計）の最大が最小の2倍を超える → 基準を決めずに止めて報告する

## 止める条件（回す前に決めた）

1. どれかの本で答えの検査が外れる
2. どれかの本で `thp_fault_fallback` の前後差が 0 でない（今の 16 GiB で回すので、ここで付かないなら別の問題がある）
3. 上の「新しい基準が 16 GiB 以上」「消費量が本ごとに大きく違う」
4. 1本目の前の空きが 16 GiB に満たない（キャッシュは本人が落とす）

### 回したあとで見たこと（基準の決め方には使っていない）

走る前の `/proc/buddyinfo` から、**2 MiB 未満の空きブロック**（order 0〜8）も足した（`logs/<ラベル>_before.txt` の写しから。`summary.py` の最後の表で、止める条件に掛かったあとで足した）。

| 本 | 走ったノード | そのノードの 2 MiB 未満の空き（走る前） | そのノードの 2 MiB 以上の消費量 | 和 |
|---|---|---|---|---|
| `p1_pin` | 0 | 0.89 GiB | 4.51 | 5.40 |
| `f2_free` | 0 | 1.31 | 4.10 | 5.40 |
| `p3_pin` | 0 | 1.60 | 3.73 | 5.33 |
| `f4_free` | 1 | 3.79 | 2.04 | 5.83 |
| `p5_pin` | 0 | 1.62 | 3.76 | 5.38 |

小さな確保は、まず 2 MiB 未満の空きから取られ、それが尽きると 2 MiB 以上の塊が割られる（見込みに書いた仕組み）。どの本も和がほぼ同じ 5.33〜5.83 GiB なので、
**2 MiB 以上の塊の消費量は、走るノードに 2 MiB 未満の空きがどれだけ残っていたかで動く**と読める（`f4_free` はノード1で走り、ノード1には 2 MiB 未満の空きが 3.79 GiB あった）。
`pin` の3本の消費量が 4.51 → 3.73 → 3.76 と下がったのも、ノード0の 2 MiB 未満の空きが本を重ねて 0.89 → 1.60 GiB に増えたのと合う。
この読みが正しければ、1本の完走が要る量は「2 MiB 未満の空きが無いときの消費量」に近い約 5.4〜5.8 GiB で、決めた式の「消費量」はそれを下から見積もる。
ただし和が一定になる理由は確かめていない（5本だけの、回したあとの読み）。

### 言えないこと

- 0.2 秒より短い山は読めていない（`AnonHugePages` の最大は延べの `thp_fault_alloc` と矛盾しないが、ページキャッシュや小さな確保の短い山は見えない）
- `free` で、どちらのノードで走るかは本ごとに違った。5本では、本走でどちらのノードが使われやすいかは言えない
- 上の「和がほぼ一定」は回したあとで見た読みで、決めた式を置き換える根拠にはしていない

## 判断を本人に返す

決めた手順どおり、基準は 16 GiB のまま変えていない。進め方の候補（決めるのは本人）:
- 「消費量」の定義を「2 MiB 以上の消費量 ＋ 走る前にあった 2 MiB 未満の空き」のような、ノードの状態に左右されにくい量に替えて、測り直す（定義の変更なので、登録からやり直す）
- 走るノードを `pin` に揃えた本だけで決め直す（`free` の本は、どちらのノードで走るかで量が動く）
