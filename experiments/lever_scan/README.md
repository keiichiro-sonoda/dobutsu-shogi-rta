# 実験 lever_scan: 出力を変えないレバーのふるい分け

⚠️ **これは記録試行ではない。** 番号を取らず、`impl/` を作らず、タイムを `results/` にも
README の記録表にも載せない。入力を固定して片方の段だけを走らせる門番で、
レギュレーションの「空の `dat/` から完走」を満たしていない。

## 何をしたか

`#19` で Python 側に億単位のループが無くなり、残りの段はどれも C の中にある。
候補はどれも1〜5% 級に見えていて、1本ずつ記録にすると固定費が割に合わない。
そこで5つのレバーと、それを全部入れた腕を、**全探索と後退解析の2つの門番で同時にふるい、
順位を付けるところまで**やった。束ねて記録にするのは次の回で、その回に測り直す。

対象は「出力をバイト単位で変えないレバー」だけ。7腕とも `impl/19_c_gather` が出発点で、
`.py` は計装ごとバイト同一。動かすのは下の表の差分だけ（[`make_arm.sh`](make_arm.sh) が組む）。

| 腕 | 変えるもの | 効いたことの確認（[`logs/warnings.txt`](logs/warnings.txt)） |
|---|---|---|
| `base` | 何も変えない（`-O2`） | — |
| `fnsi` | `gcc` に `-fno-semantic-interposition` | `normalBoard@plt` への `call` が 3 → 0 |
| `const` | [`patches/const.patch`](patches/const.patch): 移動表4本を `static const int`、`.h` の `extern` を削除 | 移動表の `GLOB_DAT` 再配置が 4 → 0 |
| `native` | `gcc` に `-march=native` | AVX・BMI 系の命令が 0 → 48 |
| `huge` | [`patches/huge.patch`](patches/huge.patch): 索引と発見済み表を 2 MiB 境界で確保し、`memset` の前に `MADV_HUGEPAGE` | `madvise` の呼び出しが 0 → 3 |
| `pf` | [`patches/pf.patch`](patches/pf.patch): 先読み4か所（距離 16。`predScatter` だけ 16 / 32 の2段） | `prefetch` 命令が 0 → 5 |
| `all` | 上の5つを全部（パッチは const → huge → pf の順） | 上の全部 |

7腕とも `-Wall -Wextra` で警告ゼロ。門番の前に、小さいフィクスチャ（全探索7ラウンド → 後退解析）で
7腕の出力が `base` とバイト一致することを確かめた。

| 門番 | 走らせるもの | 本数 | 所要 |
|---|---|---|---|
| 全探索 | 空の `dat/` から `searchAll()` だけ | 7腕 × 3ブロック = 21本 | 44分 |
| 後退解析 | 下の入力から `retreatAnalysis()` だけ | 7腕 × 3ブロック = 21本 | 56分 |

機械時間は門番2つで1時間40分、マイクロベンチを足して約2時間18分（測る前に決めた上限は4時間）。
途中で腕を足したり、結果を見て本数を増やしたりはしていない。

ブロック `b` の位置 `p` に `ARMS[(b + p) % 7]` を置く巡回の配置（`ARMS = base fnsi const native huge pf all`）。
各腕は3つの異なる位置に来る。各腕に一度も来ない位置が4つあるので、ラテン方陣ではない。
両門番とも `numactl --cpunodebind=0 --membind=0` で片ノードに固定した（CLAUDE.md の取り決め）。

## 後退解析の入力 — 組み直さずに、全探索の出力をそのまま使った

`tools/rebuild_forward_fixture.py` で #18 / #19 の完走 `dat/` から組み直しても、
**今の採番順は戻らない。** あのツールは未知の集合を「深さ1の残り → 深さ2以上 → 引き分け」の
順に詰め直すので、集合は戻るが並びは戻らない（CLAUDE.md。小さく回すと 99.2% の位置が変わる）。

そこで、**全探索の門番の1本目（`b1_base`）が書いた `dat/` をそのまま入力にした**
（`runs/g19_fixture_bin/dat`、51ファイル）。全探索は決定的で、21本とも同じバイト列を書いた。
本走の `searchAll()` が書いて `retreatAnalysis()` が読むものと同じになる。

こうすると、並びが本走と同じことをバイト単位で確かめられる。後退解析の `base` の出力が **#19 本走の `dat/` と全213ファイルで
バイト一致した**（md5 一覧の sha256 `f18f3075…`、`results/19_c_gather/bytecompare.txt` と同じ値）。
段の秒も本走とほぼ重なる（`r1_base` の P4 63.39 / 174段 26.62 秒、本走は 64.35 / 26.66 秒。
古い `g1_11_fixture_bin` の門番では P4 が 157 秒だった）。

`runs/` は git 管理外だが、この入力は `impl/19_c_gather` の `searchAll()` を1回走らせれば
同じバイト列で作り直せる。

## マイクロベンチ

[`microbench/scatter_bench.c`](microbench/scatter_bench.c)（`gcc -O2 -Wall` で警告ゼロ）を、
本番規模（辺 2^30、約 10 GB）で `numactl --cpunodebind=0 --membind=0` に固定して回した。
各条件3周の中央値（ns/辺）。表は [`microbench/table.py`](microbench/table.py) が
[`microbench/logs/`](microbench/logs/) から組む。4条件で約38分。
`logs/*_time.txt` の「Command being timed」はユーザ名を含む絶対パスだったので、その部分だけ `<ROOT>/` に置き換えた
（[`microbench/run.sh`](microbench/run.sh) の冒頭に経緯）。

**判定の規則（測る前に決めたもの）: 1条件目の `scatter ÷ count` が 5 倍を超えたら残り3条件を回す。**
1条件目は **7.13 倍**で、別の機械（Ryzen 7 8840U、辺 2^26。`scatter_bench.c` の冒頭のコメント）の
2.3 倍と違って本番の症状
（#19 本走で 9.2 倍。[`results/19_c_gather/retreat_summary.tsv`](../../results/19_c_gather/retreat_summary.tsv) の
`P4_scatter` ÷ `P4_count`）を再現したので、4条件とも回した。

| 条件 | `AnonHugePages` | count | scatter | scatter ÷ count | store_indep | pf2_32 | pf2_32 ÷ scatter |
|---|---|---|---|---|---|---|---|
| `uniform 30 plain` | 0.00 GiB | 23.93 | 170.65 | 7.13 倍 | 17.72 | 36.61 | 0.21 |
| `uniform 30 hp` | 9.48 GiB | 12.63 | 116.21 | 9.20 倍 | 12.71 | 24.79 | 0.21 |
| `local 30 plain` | 0.00 GiB | 5.35 | 94.06 | 17.58 倍 | 17.13 | 17.36 | 0.18 |
| `local 30 hp` | 9.48 GiB | 4.82 | 87.65 | 18.18 倍 | 12.78 | 14.67 | 0.17 |

- **先読み（`pf2_32`）は4条件とも scatter を 0.17〜0.21 倍にした。** 門番の P4_scatter
  （57.31 → 12.92 秒 ＝ 0.23 倍）と同じ桁で、模型と本番が合っている
- **依存の無い乱択書き込み（`store_indep`）は scatter の 1/10**（一様で 17.72 対 170.65）。
  書き込み先が読み込みの結果で決まるせいで DRAM 待ちが直列に並ぶ、という仮説と合う
- **巨大ページは、一様な行き先で scatter −32%（170.65 → 116.21）、局所的な行き先で −7%**
  （94.06 → 87.65）。先読みと重ねても一様 −32%（36.61 → 24.79）、局所 −15%（17.36 → 14.67）残る。
  ⚠️ **本番の P4 の配列（`succ` / `pred` / `pred_off`）は Python 側で確保していて、`huge` の腕の
  対象外。** 門番でも `huge` は P4 を動かしていない（−0.22、区間が 0 をまたぐ）。
  この効き目を本番で取るには確保を C に移す必要があり、構造の変更なのでこの回の範囲の外にした

なお #19 本走の scatter（61.8 ns。`P4_scatter` を辺の総数 938,671,869 で割った値）は、模型のどの条件（一様 170.65、局所 94.06）よりも速い。模型の「局所」は出発ごとに幅 1/64 の窓に落とす
粗い形で、本番の採番順の局所性はそれより強いと読める。**模型の ns を本番の見込みに換算しない。**

| 順 | 腕 | 推奨 | 理由 |
|---|---|---|---|
| 1 | `pf` | **束ねる** | 後退解析 −48.07、全探索 −13.47。単独で最大。P4_scatter が −77% |
| 2 | `huge` | **束ねる** | 後退解析 −22.75、全探索 −10.29。付いたことを全本で確かめてある |
| 3 | `fnsi` | 束ねる | F1 −3.92 で、gate_18 に続いて2回目の再現。フラグ1つで出力は変わらない |
| 4 | `native` | 束ねるなら測り直しで確かめる | 後退解析 −4.35 で向きは下。ただし向きを測る前に登録していなかった。バイナリはこの計測機専用になる |
| 5 | `const` | 速さのレバーとしては推奨しない | 狙う段で区間が 0 をまたいだ |
| — | P4 の配列の巨大ページ化 | この次の回以降 | マイクロベンチで先読みと重ねても −15〜−32%。確保を C に移す構造の変更なので、束ねる回には入れない |

束ねた版はこの回の数字を証拠に使わず、もう一度門番で測る。

## この回で言えないこと

- **多重比較。** `base` に対して6本、段ごとに引いている。選んだ腕の効果は上に偏っている
  （偶然よく見えた腕を選ぶため）。束ねた版の門番で確かめ直す
- **本走の値。** 入力は本走と同じ並びで、`base` の段の秒も本走に近いが、`numactl` で
  固定していて本走そのものではない。門番と本走の値を直接引き算しない（CLAUDE.md）
- **持ち越し。** 巡回の配置では直前の腕が固定される（`huge` の次は毎回 `pf`、`pf` の次は `all`）。
  `compact_stall` は全42本で 0 で、`huge` がコンパクションを後に残した兆候は無いが、
  3ブロックでは腕の効果と分けきれない
- **`r1_fnsi` の P2 の外れ値の原因。** fault の数も NUMA の移動回数も他の本と同じだった
- **`huge`・`all` の後退解析だけ `pgmigrate_fail` が約190**（他は約2）。巨大ページが NUMA の
  自動移動に乗らなかったのだと思われるが、調べていない。片ノード固定の門番では時間に効いていない
- **各腕3本。** 区間が 0 をまたいだ段（`const` 全般、`fnsi` と `pf` の P2）は
  「効かない」ではなく「この本数では確定できなかった」
