# 実験: 片ノードに固定すると後退解析のページフォルトは消えるか

⚠️ **これは記録試行ではない。** 番号を取らず、タイムを `results/` にも README の記録表にも
載せない。入力を固定して後退解析だけを走らせた比較で、レギュレーションの
「空の `dat/` から完走」を満たしていない。

## 何を確かめたかったか

[`retreat_profile`](../retreat_profile/) で、後退解析の余分な minor page fault が
どの段で起きているかまでは分かったが、**機序は候補どまりだった**。自動 NUMA バランシングが
疑わしいと書いて、そこで止めてある。

`numactl` はプロセス単位で、`sysctl` も root も要らない。ピーク RSS 13.9 GiB に対し
node0 は 31.3 GiB あるので、片ノードに固定して走らせられる。

```
plain  python3 driver.py
numa   numactl --cpunodebind=0 --membind=0 python3 driver.py
```

同じフィクスチャ・同じコードで **16本**、`plain numa numa plain` を4回。
⚠️ **`retreat_profile` の8本とは比べない。** 別の日の走行で機械の状態が違う。
比べるのはこの16本の中だけ。全16本がオラクル174行に一致した（2時間15分）。

## 答え: NUMA で確定

**高フォルト側は `plain` にだけ出て、`numa` には1本も出なかった。**

| | 総 minor fault | 本数 |
|---|---|---|
| `numa` 8本 | **12,610,088 〜 12,611,913** | 8 / 8 が低群 |
| `plain` 低群 | 12,614,024 / 13,069,018 / 13,763,384 | 3 |
| `plain` 高群 | 14,924,361 〜 14,980,166 | **5** |

⚠️ **`numa` 側の幅は 1,825 フォルト（0.014%）しかない。** `plain` 側の幅は 2,366,142 で、
1,296 倍ある。`plain` の高群は [`gate_15`](../gate_15_c_successors/) の高群
（14,739,664〜17,324,158）と同じ帯に入る。

段で割ると、超過ぶんは**索引を引くループ**に集中している。

| 区間 | `numa` 8本 | `plain` 高5本 | 差 |
|---|---|---|---|
| `R_start`→`P0` | 5,753,017 | 5,752,918 | −99 |
| `P0`→`P1` | 2,097,153 | 2,139,448 | +42,295 |
| **`P2_alloc`→`P2`** | 916,676 | **3,157,158** | **+2,240,482** |
| `P4_count`→`P4` | 916,672 | 920,013 | +3,341 |
| `R_dtm`→`R_loop` | 2,251,567 | 2,296,940 | +45,374 |

## 機序: ヒンティングフォルトが1対1で minor fault になる

`/proc/vmstat` の差分（解析の直前と直後）。

| | `numa` 8本 | `plain` 低3本 | `plain` 高5本 |
|---|---|---|---|
| `numa_hint_faults` | 38,444 | 574,117 | **2,375,924** |
| `numa_pages_migrated` | 1,466 | 164,515 | **2,267,140** |
| `numa_other`（遠いノードからの確保） | **256** | 231,317 | 277,936 |

自動 NUMA バランシングは、ページを定期的に一時的な保護状態にして、次のアクセスで
**NUMA ヒンティングフォルト**を起こす。これは major ではないので minor fault に計上される。

**16本を通した相関は r = 0.9999、回帰の傾きは 1.003。**
つまり**ヒンティングフォルト1回が minor fault 1回**として、そのまま出ている。
段で測った超過 2,240,482 と、`vmstat` で測ったヒンティングフォルト 2,375,924 の比は **1.06**。
`numa_other` が 256 まで落ちているので、固定した側では遠いノードのページが
そもそも無く、移動も起きない。

⚠️ **`/proc/vmstat` はマシン全体の累積値で、プロセス単位ではない。** 走行中に
他の計算を回していないので差分はほぼこの走行のもの、と言えるだけで、
「この 2,375,924 がこのプロセスのものだ」と直接示す計数ではない。
結び付けているのは**大きさの一致と 16本ぶんの相関**であって、帰属の証明ではない。

## `retreat_profile` の 2.41 倍は再現しなかった

正直に書く。[`retreat_profile`](../retreat_profile/) で見つけた
「`P0`→`P1` が索引のページ数の **2.41 倍**」という形は、**16本のどれにも出ていない**。
最大でも 1.02 倍（`plain` の4本が 2,133,857〜2,143,523）。

つまりこの16本は、**あの飛びそのものを試せていない**。再現したのは
`gate_15` の高群／低群の分かれ方のほうで、そちらは `plain` に出て `numa` に出なかった。
同じ自動 NUMA バランシングが両方の裏にいると読むのが自然だが、
**`P0`→`P1` に 2.41 倍が乗る条件は分かっていない。**

## 平均の差 — 固定そのものがレバーになる

飛びが消えるかとは別に、**片ノードに固定すると毎回速い**。
Welch 検定（自由度まで計算、両側）:

| 段 | `plain` 8本 | `numa` 8本 | 差 | t | 自由度 | p | 95% 区間 |
|---|---|---|---|---|---|---|---|
| **後退解析 合計** | 514.59（sd 16.25） | **489.89（sd 2.56）** | **+24.71** | 4.25 | 7.35 | 0.0034 | **+11.09 … +38.33** |
| **P2 後続生成** | 125.72（sd 15.69） | **104.21（sd 0.64）** | **+21.52** | 3.87 | 7.02 | 0.0061 | **+8.39 … +34.64** |
| P1 索引 | 21.64（sd 1.31） | 20.59（sd 0.12） | +1.05 | 2.26 | 7.13 | 0.058 | −0.05 … +2.14 |
| P4 前任リスト | 143.02（sd 0.49） | 141.98（sd 1.36） | +1.04 | 2.03 | 8.79 | 0.073 | −0.12 … +2.20 |
| 174段ループ | 100.72（sd 0.71） | 100.09（sd 0.65） | +0.63 | 1.85 | 13.88 | 0.085 | −0.10 … +1.36 |
| P0 読み込み | 93.82（sd 0.63） | 93.81（sd 0.49） | +0.01 | 0.03 | 13.24 | 0.98 | −0.60 … +0.61 |

⚠️ **区間が 0 をまたがないのは合計と P2 だけ。** 他の段は「この本数では確定できなかった」
であって、効果が無いという意味ではない。効果は **P2 にほぼ全部乗っている**。

**揺れも縮む。** 合計の標準偏差が 16.25 → 2.56（変動係数 3.16% → 0.52%）。
P2 は [`docs/measurement-noise.md`](../../docs/measurement-noise.md) の表に2行として
入れてあり、そちらでは **12.43% → 0.68%** になる。レバーとしての価値は速さだけではなく、
**同じコードを測り直したときの再現性**のほうが大きいかもしれない。

この節の表は `retreat_summary.tsv`（秒未満まである）から、揺れの表は `main.log`
（`s2hms()` が秒未満を切り捨てた整数）から計算しているので、同じ段でも
小数点以下が少し違う。**出どころの違いで、どちらかが間違っているのではない。**

## 対のなかの位置は効いている

`plain` の中でも高群と低群に分かれた。並びとの対応を見ると:

| 位置 | 腕 | 直前の本 | 高群 |
|---|---|---|---|
| `a` | `plain` | `plain`（前の組の `d`）／最初 | 1 / 4 |
| `b` | `numa` | `plain` | 0 / 4 |
| `c` | `numa` | `numa` | 0 / 4 |
| `d` | `plain` | `numa` | **4 / 4** |

⚠️ **`numa` の直後の `plain` は4本とも高群。** この16本だけでは
「腕の効き」と「直前の本が残したもの」を完全には分けられない。
ただし `numa` は `plain` の直後（`b`）でも `numa` の直後（`c`）でも低群なので、
**低群であることは並びでは説明できず、腕で説明できる**。
`plain` 側の高低の分かれ方が並びに引きずられている、という読みになる。

## レギュレーション上の扱い

⚠️ **ここでは決めない。判断が要る、とだけ書く。**
`numactl` を付けると `results/*/env.txt` の `run_cmd` が変わる。これを
**実装の一部**と見るか**機械の設定**と見るかで、記録に載せてよいかが変わる。
前者なら `tools/run.sh` に入れて記録を取り直す話になり、後者なら
計測機の条件として `env.txt` に書いて全記録に遡って効く話になる。

## 次に測るなら

1. **`numactl --membind=0` だけ（CPU は固定しない）と、`--cpunodebind=0` だけを分ける。**
   いまは2つ同時に付けているので、「CPU の置き場所」と「メモリの置き場所」を分けられない
2. `P0`→`P1` に 2.41 倍が乗る条件を探す。この16本では一度も出ていない
3. `madvise(MADV_HUGEPAGE)` を並べる。索引・`seen` 表・`pred` は数 GB に
   9.39 億回のランダムアクセスをしていて、TLB の被覆率は 0.07%
