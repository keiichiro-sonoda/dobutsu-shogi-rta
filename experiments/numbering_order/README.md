# 実験: 採番順が後退解析にどれだけ効くか

⚠️ **これは記録試行ではない。** タイムを `results/` や README の記録表に載せない。
入力を固定して後退解析だけを走らせた比較であり、レギュレーションの
「空の `dat/` から完走」を満たしていない。`impl/08_*` も作っていない。

> ## ⚠️ 記録 #8 以後、この実験の見込みは成り立たない
>
> ここで出した「F なら記録実装比 −104 秒」は、**P2 が 1,035 秒あった前提の引き算**である。
> 記録 #8（`impl/08_c_index`）で照合をC側へ移した結果 **P2 は 197 秒**になり、
> F の得の半分以上を占めていた P2 のぶんが消えた。
> **測り直さないかぎり、この −104 秒を次の判断に使ってはいけない。**
>
> 下の測定そのもの（順序で 1.56 倍ひらくこと、上位ビットのバケットが安いこと）は
> **#7 の構造に対する観測として有効**で、そこは変わらない。

## なぜ測ったか

記録 #7 の時点で、後退解析 2,156 秒のうち **1,843 秒（85.5%）が「辺を使える形にする
下ごしらえ」**（P0〜P4）で、本来の仕事である174段のループは 264〜313 秒しかない
（⚠️ 下限はログの表示値の合計、上限は「後退解析 − 測った4段」。深さごとの所要時間は
`s2hms()` が秒未満を切り捨てるので、表示値の合計は下限にしかならない）。
下ごしらえの中身は 9.4 億回の辞書引き（P2）と 9.4 億本の辺の詰め替え（P4）で、
どちらも 10〜24 GiB の構造をランダムに叩く。**叩く順番を変えれば効くはず**だが、
効果量も、並べ替え自体の代金も分かっていなかった。

## 何を変えたか

`packed[]` に詰める順（＝通し番号の振り方）だけを変える。盤面の集合も、辺も、
答えも変わらない。`ORDER` 環境変数で切り替える。

| | 並べ方 |
|---|---|
| **A** | 現状（未知チャンクを逆順 → キャッチ → トライ負け）。impl/07 と同じ採番 |
| **B** | 未知チャンクを正順にするだけ |
| **C** | 全件を固定シード (20260917) でシャッフル。局所性を壊す対照 |
| **D** | パック値で完全ソート |
| **E** | パック値の上位20ビットで計数ソート（D の近似、全件まとめて） |
| **F** | E を3群（未知・キャッチ・トライ負け）の中だけで行う |

E / F のバケット幅は `BUCKET_SHIFT`（既定 40 ＝ 2²⁰ バケット、1バケット平均 235 局面）。
⚠️ **この値は調整していない。**

### 比較を成立させるための作り

- **A にも同じ改修を入れてある。** 並べ替えを可能にすると3群の連続配置が崩れるので、
  `buildSuccessors` を「未知は先頭 `n_uk` 件」前提から `kind[]` を見る形に書き換えた。
  この改修自体に代金があるため、A も同じコードで走らせている（差は `ORDER` だけ）
- `kind[]`（不変の3群ラベル）と `dtm[]`（手数）は**別の配列**にしてある。
  同じものを使うと深さ1のフロンティアを作るときに、前向き探索のキャッチと
  後退解析が今まさに 1 を入れた局面とを区別できず、`cnt` を二重に減らす
- `del idx` の位置は impl/07 のまま動かしていない（ピークを決める一行）

## どう測ったか

```bash
experiments/numbering_order/run.sh A B C D E F > exp.out 2>&1
```

- 入力は `runs/g1_07_batch_forward_write/dat`（全探索が終わった直後の状態、2.1 GB）を
  変種ごとにコピー。⚠️ **git 管理外。** 無ければ完走した `dat/` から
  `tools/rebuild_forward_fixture.py` で作り直す
- CPython 3.12 / gcc `-O0` / 同一マシンで連続実行。他の計算は流していない
- **毎回 `tools/verify_log.py` でオラクル174行を確認**（[`logs/console.log`](logs/console.log)
  に6回ぶんの `PASS: 174 行すべて一致`）
- 検証が済んだら `dat/` は捨てる

変種どうしの比較には使えるが、絶対値としては下限。

| | 並べ替え | P0 | P1 | P2 | P4 | 174段（下限） | 後退解析計 | ピーク RSS |
|---|---|---|---|---|---|---|---|---|
| impl/07（記録・参考） | — | 95 | 167 | 1,035 | 546 | 264 | 2,156 | 30.65 GiB |
| **A** 現状 | 0 | 95 | 167 | 1,094 | 569 | 295 | 2,279 | 31.75 GiB |
| **B** 未知正順 | 0 | 95 | 167 | 1,062 | 563 | 283 | 2,226 | 31.76 GiB |
| **C** シャッフル | 159 | 95 | 186 | 1,352 | 637 | 345 | 2,827 | 31.75 GiB |
| **D** パック値ソート | 401 | 95 | 165 | **831** | **405** | 258 | 2,210 | 31.73 GiB |
| **E** バケット全件 | 126 | 96 | 167 | 989 | 479 | 268 | **2,177** | 31.75 GiB |

### 言えること

**① 順番で大きく変わる。差はこれまで観測したばらつきの幅より桁で大きい。**
順序に反応する3段（P2・P4・174段ループ）の合計は **C 2,334 秒 対 D 1,494 秒で 1.56倍**
（⚠️ 174段ぶんは表示値の下限を使っているので、合計も下限どうしの比較）
（P2・P4 だけなら 1,989 対 1,236 で 1.61倍）。同一コードの後退解析でこれまでに観測した
幅は 3.3%（2,087 / 2,144 / 2,156 秒の3本）で、840 秒の差はその 12 倍にあたる。
⚠️ **3.3% は3本の観測の幅であって、ばらつきの上限ではない。**
「この差はばらつきでは説明できない」と言い切るには本数が足りない。
言えるのは「これまで見た幅よりはるかに大きい差が出た」まで。

**② 動いた段と動かない段の内訳は、メモリの局所性という説明と整合する。**
ファイルを頭から読むだけの **P0 は全変種で 95〜96 秒**。飛び回る段だけが揃って動いた。
⚠️ ただし**キャッシュミスの回数もTLBミスも測っていない。** 整合するというだけで、
局所性が原因だと確かめたわけではない。ほかの説明（分岐予測の当たり方など）も
このデータでは否定できない。

**③ 完全に並べる必要はない。上位ビットだけで足りる。**
A を基準に、並べ替え代を差し引いた正味：

| | 並べ替え代 | P2+P4+ループ | A との差引 |
|---|---|---|---|
| B | 0 | 1,908 | **−50** |
| C | 159 | 2,334 | **+535** |
| D | 401 | 1,494 | **−63** |
| E | 126 | 1,736 | **−96** |
| F | 141 | 1,713 | **−104** |

D（完全ソート）は 464 秒ぶん稼ぐのに 401 秒払うので、ほぼ相殺される。
**必要なのは「完璧な順序」ではなく「似た盤面が近くにいること」**で、
上位20ビットを揃えるだけの計数ソートならその条件を 126〜141 秒で満たせる。

**④ ピーク RSS は順番で動かない。** 6変種すべて 31.73〜31.76 GiB。
D が作る 10 GB 級の一時リストもピークを上げなかった（ピークは P2 の終わりにあるため）。

### 言えないこと

⚠️ **各変種 n=1。** 上の差引はどれも1本ずつの観測で、雑音帯（後退解析で約 ±70 秒）を
考えると **F の −104 秒は雑音の 1.5 倍程度**しかない。①の 840 秒差とは確からしさが違う。

⚠️ **`BUCKET_SHIFT` は未調整。** 40 以外を試していないので、E / F の値は最良ではない。

⚠️ **記録実装にしたときの見込みは引き算であって実測ではない。**
順序非依存への書き換え代は A − impl/07 ＝ **+113 秒**（P2 +59 / P4 +23 / ループ +31）と
**+1.10 GiB**（impl/07 の 30.65 GiB は実行全体のピークだが、そのピークは後退解析 P2 の
終わりにあるので、後退解析だけを測ったこの実験の 31.75 GiB と比較できる）。F を impl/07 の構造（3群が連続なのでこの書き換えが要らない）に載せれば
`1,713 − 113 + 141 ＝ 1,741` 秒で、impl/07 の 1,845 秒に対して **−104 秒**。
⚠️ P2・P4 だけを信用するなら **−79 秒**。**引く側の +113 秒自体が n=1 同士の差**で、
雑音帯の 1.6 倍しかない。

⚠️ **記録全体（4,471 秒）に対して 2% 前後。** 全探索は同一コードでも 5.3% の幅
（6本）で振れているので、**完走1本の壁時計でこの差を見分けるのは難しい。**
記録試行にするならフェーズ単独を複数回測る門番が要る。

## F が本命な理由

E とタイムは同じ（2,177 秒）だが、**F は3群の連続配置を壊さない**。
impl/07 は「未知は先頭 `n_uk` 件」「キャッチは `[n_uk, n_uk+n_win)`」という前提で
`cnt[]` と `succ_off[]` を未知のぶんだけに切り詰め、深さ0と深さ1の初期フロンティアを
`range()` にしている。F ならその構造をそのまま使えるので、上の +113 秒と +1.10 GiB を
払わずに済む。

判定、`ROOT` を絶対パスからスクリプト位置基準に。**いずれも失敗時と不正入力時の
振る舞いだけで、正常系の手順は変わっていない。**
