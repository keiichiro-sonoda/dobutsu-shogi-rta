# perf_38: #38 の F1 で何が律速しているかを perf で測る — 先行判定の得がベンチの換算の 56% しか出なかった理由を探す（記録試行ではない）

番号を取らず、`impl/` を作らず、`results/` にも README の記録表にも載せない。速くする工夫は入れない。測るだけ。

## 目的

#38 は全探索の生成器にキャッチの先行判定を入れた。生成器だけのベンチ（[`f1_select_catch`](../f1_select_catch/)）では F1 の換算 −7.49 秒だったが、
[門番 #38](../gate_38_precheck/) の F1 は −4.16 秒で、**換算の 56%** しか出なかった（これまでの記録は 75〜111%）。記録ノート
[`docs/records/38-precheck.md`](../../docs/records/38-precheck.md) は候補を2つ挙げて、どちらも確かめていない。

- **H1**: ベンチでは外れる局面（other）が −18.4 cycles 軽くなった（換算で約 −0.58 秒）が、本物の F1 では出ていない
- **H2**: 本物の F1 では、キャッチ局面の生成器の時間の一部が、生成器の外の仕事（準備の配列 `g_prep` への書き込み・発見済みの表・待ち行列・Python 側）と重なって隠れていた。
  生成器が 230 → 33 cycles に縮んだので、その仕事が表に出てきた

H1 だけでは差（約 3.3 秒）の一部しか説明できない。#37 と #38 の本物の F1 を同じ道具で測って、縮んだもの・縮まなかったもの・増えたものを分け、どちらの候補（または別の理由）が効いているかを推す。

| 組 | イベント（`cycles`・`instructions` に足すもの） |

### 2. どこで時間を使っているか（`perf record`）

`perf record -e cycles:pp -c 2000003 -e mem_load_uops_retired.l3_miss:pp -c 211`（周期はどちらも素数）。F1 の区間だけ。
- 周期の選び方: F1 は約 1.5 × 10^11 サイクルなので cycles は 7 万個ほど（毎秒 1,700 個で、カーネルの上限 25,000 / 秒の下）。LLC のロードミスは #34 で局面 100 個に1個
  （F1 全体で約 250 万回）なので 1 万個ほど
- 書き込みの外れを指せる PEBS のイベントはこの CPU に無い（書き込みは `mem_uops_retired.all_stores` の数しか取れない）ので、record は読み込みの LLC ミスだけ
- 標本は [`attribute.py`](attribute.py) で、`-g` なしの `.so` の逆アセンブルで番地に直し（`perf_branch_34` の `branches.py` の `resolve`）、`-g` の `.so` の
  `addr2line -i` で外側の関数・一番内側の関数・ソースの行に寄せる（`perf_branch_34` の `aggregate.py` の `lines_of`）。分岐には寄せない
- [`summary.py`](summary.py) の `bucket()` が区分に分ける（一番内側の関数の名前と行の文で。インライン展開されたものも分ける）:
  生成器: 先行判定（`komaSet` と先行判定の区画の行）／生成器: 本体／生成器: `invBoard`／`rankOf`（`rank` で始まる下請け）／`seenTestAndSet`／
  `nextBoardSeenNormal` の `g_prep[rb]` の書き込み・`g_prep` の先読み・`g_seen` の先読み・`zeroPush`・ほか／`expandRound`／`.so` のほかの関数／Python／libc／カーネル
- `perf.data` は `runs/` に置いたままでコミットしない。テキストの集計（`logs/<ラベル>_record.tsv`）と間引きの記録（`_record_stats.txt`）だけを残す

## 式（回す前に決めた）

`perf_34` の README の「式」と同じ（`summary.py` の `derived()` は `perf_34` の写し）。組ごとに別の本で数えるので、どの量もその本の `cycles` で割ってから組み合わせる。
加えて `resource_stalls.sb` / `cycles` を S1 からも出す（M1 にも同じイベントがあり、memory bound の式は M1 の値を使う）。

- 局面1つあたりの分母は、F1 で展開した局面（`forward.tsv` の `n_in` の合計）。2腕・全本で同じことを確かめる（246,803,167 のはず）
- 回ごと・腕ごとに8組から値を出し、3回の中央値と範囲。**腕どうしの差（`r38` − `r37`）は同じ回の2本の差を取ってから**中央値と範囲
- topdown の区分の差はサイクルにも直す（区分の割合 × 1局面あたり cycles の差）
- `perf record` の区分の1局面あたり ＝ 標本の割合 × その回・その腕の T1 の1局面あたり cycles（LLC のロードミスは C1 の `l3_miss`）
- 消えた cycles ＝ ベンチの差（−103.4）− 本物の差。F1 の秒には 246,803,167 局面 ÷ 3.408 GHz で直す
- F1 の秒（`forward_summary.tsv`）を門番 #38 の F1（`old` 48.31 / `new` 44.15 秒、perf なし）と並べ、perf を付けた分の重さを出す
