# perf_39: #39 の後退解析 `U_loop`（30.6 秒）が何に時間を使っているかを perf で測る（記録試行ではない）

番号を取らず、`impl/` を作らず、`results/` にも README の記録表にも載せない。速くする工夫は入れない。測るだけ。

## 目的

#39 の本走で、段の大きい順は F1 42.0 秒（51%）、`U_loop` 30.6 秒（37%）。F1 は [`perf_38`](../perf_38/) で中身まで測った（生成器・`rankOf`・発見済みの表と `g_prep`・
書き込みの溜まり）が、**`U_loop` は #37 で逆向きの生成器の仕事を半分にしてから、中身を一度も測っていない**。[`rank_fast`](../rank_fast/) の段1で `rankOf` の分
（#38 で 9.35 秒）だけは分かっていて、#39 で `U_loop` は門番で −1.80 秒縮んだ。残りの 20 秒あまり（逆向きの生成器・手数の配列 `g_dtm` と準備の配列 `g_prep` の読み書き・
Python 側の段ごとの仕事・カーネル）の内訳が分からない。

残っている後退解析のレバー（到達しない候補を減らす、逆向きの生成器に残った分岐、`g_dtm` の読みの局所性など）の取り分は、この内訳が無いと見積もれない。
`U_loop` の内訳を出し、どのレバーに取り分がありそうかを推す。F1 も同じ本で数えられるので並べて出す（`perf_38` の `r38` から #39 で何が変わったかの確認。主題は `U_loop`）。

## 回す前に数えたもの

`-g` の `.so` の逆アセンブルと `addr2line -i` で見た（標本は使っていない）。

- **`unmoveCandidates`（逆向きの生成器）は `unmoveStep` に展開されず、`call` で呼ばれる**（`.text.hot_layout` の自分の区画にある）。だから逆向きの生成器は関数の名前で分けられる。
  `unmoveRaw`・`unmovePiece`・`unmoveCaptures`・`unmoveEmit`・`unmoveMirror`・`normalBoard` などはその中に展開されている。`invBoard` も展開されるか、関数の `invBoard` が呼ばれる
- `unmoveStep` は 276 命令。`rankOf` を展開した部分（`rankHalf`・`_pext_u64` を含む）が 102 命令
- `g_dtm`・`g_prep` は巨大ページに取った配列で、`.so` にはポインタ（記号 `g_dtm`・`g_prep`）だけがある。`unmoveStep` の頭で `mov g_dtm(%rip),%r12` とポインタを読み、
  ふるい（1174 行）は `cmpb $0xff,(%r12,%rdi,1)` で引く。rank_fast の `tables.py`（静的な表の記号に寄せる）ではこの読みが「?」になるので、[`tables39.py`](tables39.py) で広げた（下）
- `U_loop` の分母（#39 本走の `main.log` と `rank_fast` の段1のログ）: 展開した局面（フロンティア）の延べ数 **103,821,853**、前任の候補 **578,723,910**（5.574 / 局面）、
  未定で残した候補 238,521,168（41.2%）。到達しない局面で捨てる候補は **82,992,958（候補の 14.3%）**（[`unmove_prune`](../unmove_prune/) が数えた。候補の多重集合は #37 から変わらない）

## 測るもの

### 1. カウンタ（`perf stat`）

`perf_38` の8組（T1・T2・M1・M2・M3・C1・C2・S1）をそのまま使う（[`run_one.sh`](run_one.sh) の `EVENTS`）。1本の完走で1つの組を、F1 と `U_loop` の両方で数える

### 2. どこで時間を使っているか（`perf record`）

1本につきイベントは1つ（`rank_fast` の試しの本で、PEBS のイベントを2つ以上並べるとロードの標本の数が揺れた）。周期は素数で、イベントごとに `cpu/…,period=…/pp` で書く。

| 種類 | イベント | 周期 | 標本の見込み |
|---|---|---|---|
| `record:cyc` | `cycles:pp` | 2,000,003 | `U_loop` 約 5 万個（毎秒 1,700 個）、F1 約 7 万個 |
| `record:l2m` | `mem_load_uops_retired.l2_miss:pp` | 10,007 | `U_loop` 約 1 万個（`perf_34` で L2 のロードミスは局面 0.97 個）、F1 約 8 千個 |

- L1 ではなく L2 の外れを取る（`g_dtm`・`g_prep` の散らばった読みを見る。LLC の外れは `perf_34` で局面 13 個に1個で、標本が少ない。LLC の外れの数は C1 で数える）
- `-d`（データの番地）は付けない（この CPU では使えなかった。`rank_fast`）
- 標本は [`attribute.py`](attribute.py)（`rank_fast` の写し）で、`-g` なしの `.so` の逆アセンブルで番地に直し、`-g` の `.so` の `addr2line -i` で**インライン展開の鎖を全部**と
  一番内側のソースの行に寄せる。ロードの標本は、その命令が読む配列に寄せる（[`tables39.py`](tables39.py)）:
  1. `rank_fast` の `table_of_load`（静的な表の記号）
  2. 決まらなければ、ベースのレジスタをたどって `mov <記号>(%rip),%reg`（ポインタの読み）に当たれば `*<記号>`（ポインタの指す配列）。ベースが `%rsp` なら「スタック」
  3. それでも決まらなければ、一番内側の行の文で添字を引いている配列（`g_xxx[` と `frontier[`）がちょうど1つなら「<名前>（行から）」。ほかは「?」
- `.so` の外の標本は dso の名前ごと（Python・libc）、カーネルは「[kernel]」にまとめる。**この計測機では `kernel.kptr_restrict` が 1 で、カーネルの標本の関数名は取れない**。
  カーネル時間の中身（ページフォルトか書き出しか）は、`depth_log.patch` の手数ごとのカーネル時間と minor fault を、`unmoveStep` の呼び出しの中とそれ以外に分けて見る
- `perf.data` は `runs/` に置いたままでコミットしない。テキストの集計（`logs/<ラベル>_record_<区間>.tsv`）と間引きの記録（`_record_stats_<区間>.txt`）だけを残す

## 結果の読み方（回す前に決めた）

`U_loop` の区分（`cycles:pp`）の割合と、カウンタで読む。「大きい」は `U_loop` の 20% 以上（約 6 秒以上）とする。

| 見え方 | 取り分がありそうなレバー |
|---|---|
| 逆向きの生成器の区分が大きく、`U_loop` の予測ミスが多い（フロンティア1局面あたり 6 以上） | 逆向きの生成器に残った分岐（打てるか・持ち駒・正規形） |
| 未定の候補をふるう区分・決める区分が合わせて大きく、L2 のロードミスの標本の半分以上が `*g_dtm`・`*g_prep` | `g_dtm` の読みの局所性（候補の順を並べ替える、先読みを早めるなど）、到達しない候補を作る前に落とす |
| `rankOf` の区分がまだ大きい | 番号の付け方を変える2案（`rank_fast` の推奨） |
| `resource_stalls.sb` / `cycles` が 10% 以上 | `g_dtm`・`g_prep` への書き込みのまとめ方 |
| Python・libc・カーネルの区分と、手数ごとの「それ以外」の秒が合わせて 10% 以上（約 3 秒） | 手数のループを C に寄せる、書き出しの作り |

- 律速が計算か待ちかは topdown で読む: retiring ＋ bad speculation ＋ core bound と、memory bound の大きさ。区分ごとには、ふるう・決めるの区分の標本が
  ロードの命令の直後（待っている命令）に寄るかで読む
- #34 からの変化（生成器が軽くなって待ちが表に出たか）は、`perf_34` の `U_loop` の1局面あたりの `stalls_mem_any` のサイクル・memory bound のサイクルと比べる。
  サイクルがほぼ同じ（±30%）で割合が増えていれば「隠れていた待ちが表に出た」、サイクルが減っていれば「待ちも減った」と読む

## 見込み（回す前に書いた）

手がかりは `perf_34`（#34 の `U_loop`）・`perf_38`（#38 の F1）・`rank_fast`・門番 #39 だけ。

- 門番 #39 の `new` の `U_loop` は 30.51 秒（ユーザー 29.09、カーネル 1.41）。3.408 GHz とフロンティア 103,821,853 で **約 1,000 cycles / 局面**（候補1つあたり約 180）
- `perf_34`（#34）の `U_loop` は 1,820 cycles / 局面、命令 2,991、予測ミス 26.5、memory bound 8.1%、`stalls_mem_any` 299 cycles、L2 のロードミス 0.97、LLC 0.075。
  そのとき本物 − ベンチ（生成器と `rankOf` の外）は 428 cycles・232 命令だった
- そのあと #36（ビットボード型、門番で −14.93 秒）と #37（鏡像の側から戻さない、−9.76 秒）で生成器が軽くなり、ベンチの `benchUnmove` は 1,391 → 586 cycles / 局面（`lean`）になった。
  生成器の外の仕事（`g_dtm`・`g_prep`・`found`・Python・カーネル）は #34 から変わっていないので、**外の 400 cycles 前後はそのまま残り、`U_loop` の 4 割を占める**と見る。
  その中の待ちが、生成器が重かったときは重なって隠れていた分だけ表に出ている、と見る（#38 の F1 と同じ形。ただし F1 の待ちは書き込みの溜まりだったので、`U_loop` でも
  読みの待ちと決めつけない）
- `rank_fast` の段1: #38 の `U_loop` の `rankOf` は 53.7 cycles / 呼び出し（9.35 秒）。#39 で 1呼び出しあたり約 −9.6（`rankOf` だけのベンチ）

詳しくは [`results.md`](results.md)（集計は [`logs/summary.txt`](logs/summary.txt)）。2026-10-19 に 30 本を回し、止める条件には掛からなかった（答えの検査 30 本とも PASS、

## 推奨（決めない）

- **`U_loop` の 30.6 秒の内訳**（perf を付けた本の 30.8 秒に割合を掛けた値）: 逆向きの生成器 10.5 秒（34%）、`rankOf` 7.6 秒（25%）、未定の候補をふるう 7.0 秒（23%。うち `g_dtm` の
  読みの1行で約 6.0 秒）、決める 1.9 秒（6%）、カーネル 1.7 秒（5%）、`g_dtm` の先読み 0.9 秒、`unmoveStep` のそのほか 0.6 秒、libc 0.6 秒、Python 0.02 秒。
  **律速は計算が約6割（生成器と `rankOf` の命令）、待ちが約2割**（`g_dtm` の読みの待ちと `g_rank_half` の L2 外れ）
- **#34 からの変化**: 生成器は 1,391 → 586 cycles（ベンチ）と軽くなったが、生成器と `rankOf` の外の 408 cycles（#34 は 428）はそのまま残り、`U_loop` の 41% になった。
  待ちのサイクルはほぼ同じ（`stalls_mem_any` 299 → 238）で、割合が 16% → 24% に増えた。**生成器が軽くなって、隠れていた待ちが表に出た**
- **残っている後退解析のレバーの取り分（どれも上限）**:
  1. **`g_dtm` の先読みを早める（新しい候補）**: 1174 行の約 6.0 秒が上限（待ちが全部消えても、読みと分岐の命令は残る）。いまは候補の番号を出した直後に同じ局面の候補を読むので、
     先読みから読みまでが短い。1局面先（i ＋ 1）の候補を作って番号を出し先読みしてから、i の候補をふるう形にすれば、局面1つ分の仕事（約 1,000 cycles）が間に入る。
     決める順は変わらないので `dat/` は変わらないはず
  2. **到達しない候補を減らす**: **3.76 秒**（#34 の頃の 3.4 秒から少し増えた。ふるいが重いぶん）。作る前に見分ける手がかりはまだ無い。1 の形が入ると、ふるいの分が減ってこの上限も下がる
  3. **`rankOf`（番号の付け方を変える2案）**: `rankOf` の区分は 7.6 秒で、そのうち `g_rank_half` の L2 外れ（0.12 / 候補）の待ちがある。鏡像でまとめない案は反転の部分（約 2〜4 cycles / 呼び出し、
     0.3〜0.7 秒）、前後の組で区切らない案は組み合わせの段。`g_rank_half` を L2 に収まる表に分ける案（`rank_fast` の段2で作らなかった「L2 の待ち」の案）は、F1 と合わせて L2 外れが
     F1 0.22・`U_loop` 0.67 / 局面あるので、`rank_fast` の段1（5%）より取り分が大きいかもしれない（この実験では待ちの cycles に直していない）
  4. **逆向きの生成器に残った分岐**: 生成器の予測ミスは約 4.9 / フロンティア（ベンチ）。1回 15〜20 cycles で 74〜98 cycles / フロンティア、**2.3〜3.0 秒が分岐を全部消したときの上限**。
     打てるか・持ち駒・正規形の3つはその一部
  5. **Python 側・書き出し**: 手数ごとの「それ以外」は 2.10 秒（カーネル 1.42 秒）。決まった局面を3回写している分を1回にすれば、カーネル時間と libc の一部（1〜1.5 秒）
  6. 書き込みの溜まり（`resource_stalls.sb` 3.1%、31 cycles / フロンティア）は小さい。F1（17.0%）とは違う
- **次に試作するなら 1（`g_dtm` の先読みを1局面先に）を推す**。上限が一番大きく（約 6 秒）、値も決める順も変えずに書けるので、答え合わせは `dat/` のバイト比較で済む。
  生成器だけのベンチには `g_dtm` が無いので、`unmove_bench` のように `g_dtm` を持つベンチか、門番で測る
- F1（主題でない）: #39 の F1 は 564.5 cycles / 局面で、`perf_38` の `r38`（599.6）から −35。`rankOf` の区分は 188 → 155、書き込みの溜まりは 98 → 96 cycles で変わらない
