# perf_branch_34: 分岐の予測ミスがどこで起きているかを測る（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。生成器は書き換えない。場所を特定するところまで。

## 目的

[`perf_34`](../perf_34/) で、記録 #34（`impl/34_unmove`）の F1 と `U_loop` はメモリの待ちが小さく、残っている一番大きな損が分岐の予測ミスだと分かった
（3回の中央値。`perf_34` の README の「結果」）。

| | F1 | `U_loop` |
|---|---|---|
| bad speculation | 21.2% | 21.9% |
| memory bound | 4.4% | 8.1% |
| cycles / 局面 | 798.1 | 1,819.8 |
| 分岐 / 局面 | 166.3 | 343.1 |
| 分岐の予測ミス / 局面 | 12.15 | 26.49 |

ただし、どの分岐で外れているかは測っていない。直し方は分岐の種類で違う（盤の端の判定なら表引きやビット演算、駒の種類の `switch` なら分け方、
キャッチ局面の途中の `return 0` なら先行判定、など）。そこで、**F1 と `U_loop` の予測ミスが、どの関数の、どの分岐（C のどの条件）に
集まっているか**を表にする。何を作り込むかは決めず、根拠を添えて推す。

## 段の分け方と腕

`perf_34` と同じ。`impl/34_unmove` の写しに [`perf_34` の `patches/perf_ctl.patch`](../perf_34/patches/perf_ctl.patch) を写さずに当て
（Python 側だけ。段の境界で perf に `enable` / `disable` を送る）、F1 は起動した perf、`U_loop` は python に `-p` で付けた perf が取る。
`impl/34_unmove` そのものは触らない。

**C のソース行まで落とすため、`.so` は `Makefile` の gcc 行に `-g` を足してビルドする**（[`build_arm.sh`](build_arm.sh)。`Makefile` は書き換えず、
行を取り出して置き換える）。同じ場所に `-g` なしの `.so` も作り、毎本次を確かめる（合わなければ止める）:

- `-g` なしの `.so` が #34 本走と同じバイト列（sha256 の先頭 `572517006344`）
- `.text.hot_layout` と `.text` の中身（`objcopy -O binary --only-section`）がバイト一致し、番地と大きさ（`readelf -S`）も同じ

回す前に一度組んで確かめた: 一致した（`-g` の `.so` は `f0ab204963d6`。違うのは `.debug_*` の区画と build-id だけ）。

## 回す前に確かめたこと（[`probe/`](probe/)。本物のデータは使わない）

登録の時点で `logs/` にあるのは、この節の2つのファイルだけ（どちらも回す前に数えたもの。本物の解析は回していない）。

### 標本の帰属（[`logs/probe_attr.txt`](logs/probe_attr.txt)）

[`probe/attr.c`](probe/attr.c) は、乱数で転ぶ条件分岐（`test` と融合した `jz`）を1つだけ持つループ。これを perf の下で回し、標本の番地が
どこに付くかを見た（[`probe/run_probe.sh`](probe/run_probe.sh)、[`probe/check_attr.py`](probe/check_attr.py)）。perf 6.8.12、`perf_event_paranoid` 1、
`max_precise` 3、LBR の深さ 16。

| 事象 | 標本の番地 |
|---|---|
| `br_misp_retired.all_branches_pebs:up`（precise 1） | 分岐の**次に実行した命令**: 次の命令 53.2%、飛び先 46.8% |
| `br_misp_retired.all_branches_pebs:upp`（precise 2） | **分岐そのもの 47.6%、融合した直前の `test` 52.4%**（飛び先・次の命令には 0） |
| `br_inst_retired.all_branches_pebs:upp` | 同じ回数だけ実行される2つの分岐に 13.0% と 87.0%（**偏る**） |
| LBR（`-j any,u`） | 取られた記録に外れの印。区間から組み立てた実行回数は、同じ回数のはずの2つの分岐で比 0.971 |

ここから決めたこと:

- **予測ミスは `br_misp_retired.all_branches_pebs:pp` で取る。** 標本の番地が条件分岐ならその分岐、そうでなく次の命令が条件分岐ならその分岐
  （融合した比較）に寄せる（[`branches.py`](branches.py) の `branch_of()`）。どちらでもない番地は「分岐に対応づけられない番地」として割合を出す
- **分岐ごとの実行回数（率の分母）は PEBS では取らない。** `br_inst_retired` の PEBS は、分岐が数命令おきに続くと直後の分岐に標本が寄る
  （シャドーイングと見る）。予測ミスは1回ごとにパイプラインが流れ直して間隔が開くので、この偏りは出にくい（probe では外れる分岐が1つなので、
  ミスどうしの偏りは確かめられていない。LBR の外れの印との照合で見る）
- **実行回数は LBR から組み立てる**（`branches.py` の `lbr_counts()`。AutoFDO と同じ形）。隣り合う2つの記録の間（古いほうの飛び先から
  新しいほうの分岐まで）はまっすぐ実行された区間なので、その中の条件分岐は「取られなかった」と数える。区間は同じ関数の中だけ使う。
  **LBR は取られた分岐しか記録しないので、取られずに外れたミスは LBR では見えない**（照合は「取られて外れた」側で行う）
- 計画では `br_inst_retired` の PEBS を予測ミスと同じ本で取るつもりだったが、上の偏りで、実行回数は LBR の本（3回）で取ることに替えた

### 分岐のある行（[`logs/branch_lines.txt`](logs/branch_lines.txt)）

`-g` の `.so` で、熱い関数（`invBoard`・`nextBoardInvNormalNC`・`nextBoardSeenNormal`・`expandRound`・`unmoveCandidates`・`unmoveStep`）の条件分岐 222 個を
`addr2line -i` の一番内側の行で引くと、91 行に分かれた（[`list_branches.py`](list_branches.py)）。インライン展開された `normalBoard`（100 行）や
`seenTestAndSet`（470 行）、`unmoveRaw`・`unmovePiece`・`unmoveEmit` の行もここで分かれる。`invBoard` には条件分岐が無い。

完走を [`run_one.sh`](run_one.sh) で回す（[`run_all.sh`](run_all.sh) が順に呼ぶ）:

| 種類 | 何を取るか | 本数 |

- 標本は `perf script` を [`aggregate.py`](aggregate.py) に通して、分岐の番地ごとに数えた表（番地・関数・インライン展開された関数・ソース行・標本数）にしてから
  `logs/` に写す。`perf.data` は `runs/` に置いたままでコミットしない。カーネルの標本は `[kernel]` にまとめ、番地を残さない
- [`summary.py`](summary.py) が表を作る（手で書かない）:
  - 分岐ごと: 関数・行・番地・束・説明・段の中の割合（3回の中央値と範囲）・1局面あたり・率（予測ミスの推定 ÷ 実行の推定）・
    LBR の「取られた側の外れの率」・累積。段の予測ミスの 8 割に届くまで（届かなければ上位 30 個で止め、届いた割合を書く）
  - 実行の推定 ＝ LBR の（取られた ＋ 取られなかった）の割合 × 段の分岐の総数（`perf_34` の `br_inst_retired.all_branches` の中央値）
  - 束ごと: 割合・1局面あたり・「1回 15〜20 サイクルとしたときの上限の秒」（周波数 ＝ `perf_34` の段のサイクル ÷ この実験の `base` の段の秒）。
    **全部消せた場合の上限で、見込みではない**
  - 上位5個の分岐の顔ぶれと順位の3回の一致、LBR の「取られて外れた」上位5個との照合

  生成器の戻り値で**キャッチ局面だけ／それ以外だけ**に分けたファイル（[`split.py`](split.py)。並びは保つ）でも数え、キャッチの先行判定が消しうる量を見積もる

## 条件

- 解析は `numactl --cpunodebind=0 --membind=0` で固定。perf 自身は固定しない
- 各本の前にノード0の 2 MiB 以上の空きが 16 GiB 以上あるか確かめて `logs/<ラベル>_hugefree.txt` に残す。足りなければ走らせずに止めて本人に知らせる
- 各本の前に `kernel.perf_event_paranoid` が 1 か確かめる。違えば走らせずに止めて本人に知らせる（設定は本人が変える）
- 回す前に、`impl/34_unmove` に `__pycache__` が無いこと、CPU 使用率（全 CPU）が 3% 以下であること（ほかの計算が動いていないこと。
  1 CPU ぶんは約 1.8%）を確かめ、load average と CPU 使用率だけを残す（プロセスの名前は残さない）
- **perf を付けた本の秒は、記録とも門番とも比べない**
- 進行は `logs/console.log`（開始の行は `date --iso-8601=seconds`）。ログの絶対パスは `<repo>` に、カーネルの番地は伏せてからコミットする

## 止める条件（回す前に決めた）

どれかに掛かったら、そこで止めて報告する（結果の解釈に進まない）。

1. どれかの本で、答えの検査（オラクル174行・全探索の側のバイト一致・名前と件数・指紋）が落ちる。参考に `dat/` の md5 一覧の sha256 も見る
   （`perf_34` の 27 本と #34 本走は `851de9569efc…`）
2. `-g` の腕の `.text` が `impl/34_unmove` の `.so` とバイト一致しない（`build_arm.sh` が毎本見る）
3. 標本の帰属（分岐か飛び先か）が確かめられない（上の probe で確かめた。本番で「分岐に対応づけられない番地」が段の標本の 5% を超えたら、
   probe と本番で付き方が違うとみて止める）
4. 3回で上位5個の分岐の顔ぶれが揃わない

## 推奨（決めない）

**予測ミスは F1 も `U_loop` も「マスを1つずつ見て、空きか・誰の駒か・行き先に何があるか・盤の外か」を分岐で判定するところに集まっている。**
