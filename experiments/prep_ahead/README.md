# prep_ahead: 後退解析 `U_loop` で、`g_prep` の先読みも1局面先にする試作を、完走で比べる（記録試行ではない）

番号を取らず、`impl/41_*` を作らず、タイムを `results/` にも README の記録表にも載せない。記録の門番・本走はしない（推すところまで）。
ここでの12本の比較は、記録の門番の証拠には流用しない（#41 にするなら門番を改めて回す）。作りは [`dtm_ahead`](../dtm_ahead/) の写し。

## 何を確かめるか

#40 は `unmoveStep()` で、局面 i をふるう前に局面 i + 1 の前任の候補を作って `g_dtm` を先読みする形にした（[記録ノート](../../docs/records/40-dtm-ahead.md)）。
`dtm_ahead` の `perf` で、ふるいの `g_dtm` の読みの待ちは消えたが、**消えた待ちの一部が、決めるの `g_prep` の読み**（#40 の 1205 行 `if (g_prep[rr] == 0) return -4;`。
負けを決める段（`odd`）だけ）**に移った**（44.9 → 100.2 cycles / フロンティア、約 ＋1.7 秒。#40 の `U_loop` でいちばん重い1行で、約 3.1 秒）。

`g_prep` の先読みは、今もふるうループの中（#40 の 1197 行 `if (odd) __builtin_prefetch(&g_prep[r[j]], 1, 3);`）で頼み、すぐあとの決めるループで読んでいる。
#40 の前の `g_dtm` と同じ「頼んですぐ読む」形。試作 `prep1` では、**`g_prep` の先読みを、局面 i + 1 の候補を作るとき（`g_dtm` の先読みと同じところ）に移す**。
先読みから読みまでのあいだに、局面1つ分の仕事が入る。

### この試作の費用（`g_dtm` のときと違うところ）

- ふるうループの中では、ふるって残った候補だけを先読みしていた。候補を作るときにはまだふるっていないので、**全部の候補**の `g_prep` を先読みする。
  残る候補は全体の約 41%（238,521,168 / 578,723,910）なので、負けを決める段の `g_prep` の先読みはおよそ 2.4 倍に増える
- 取りに行っている途中の行を CPU が同時に持てる数には上限がある（L1 のフィルバッファ。Broadwell は 10 本）。`odd` の段では局面1つにつき候補の数（平均 5.6）の2倍の行を頼むので、
  上限に当たって先読みが待たされる可能性がある
- だから `g_dtm` のときほど素直に効くとは限らない。効くかどうかを測るのがこの実験

### `prep1` の作り

変えるのは `unmoveStep()` の中だけ（関数の頭のコメントに1行足し、コードは3行）。

- `g_dtm` を先読みする2か所（ループの前で先頭の局面の候補を作るところと、ループの中で局面 i + 1 の候補を作るところ）のすぐあとに、
  `if (odd) __builtin_prefetch(&g_prep[<同じ番号>], 1, 3);` を足した。引数は今の `g_prep` の先読みと同じ（`1, 3`）
- ふるうループの中の `if (odd) __builtin_prefetch(&g_prep[r[j]], 1, 3);` を消した（移した）。ふるう・決めるの中身（読み・比べ・減らす・書く・`found` に積む）はほかに1文字も変えていない
- `odd` でない段（勝ちを決める段）では、今と同じく `g_prep` を先読みしない。`g_dtm` の先読みの位置と引数は変えていない
- 書き方はこの1通りだけ作った

**答えが変わらない理由**: 先読みはヒントで、メモリの中身を変えない。`g_prep` を読み書きする命令（決めるループの読み・減らす）はそのままで、`g_dtm` も含めて読み書きの順は #40 と1つも変わらない。
だから決める順も `found` に積む順も #40 と同じで、`dat/` は #40 本走とバイト一致するはず。

**置き場所のずれ（`nm`）**: `unmoveStep` が **0x836 → 0x7dc バイト（−90）**（先頭 0x4480 は動かない。先読みを足したのに縮んだのは、コンパイラがループの組み方を変えたため。中は読んでいない）。
後ろに並ぶ熱い関数 `unmoveDraws`（`U_draw`）は 0x4cc0 → 0x4c80（**−64 バイト**）、熱くない `.text` の関数も全部 −64 バイト。前に並ぶ全探索の関数・`unmoveCandidates`・`unmoveInit` は動かない。
`.text.hot_layout` は 0x31ba → 0x317a。**`.bss` は 0xa0e0 → 0x90e0（−4096 バイト）**で、#39 と同じ番地に戻る（`.text` がページの境目の手前に戻ったため。大きさと中の並びは同じ）。

## 見込み（回す前に書いた）

手がかりは `dtm_ahead` の `perf`（`ahead1` ＝ #40 と同じ `.so`。`U_loop` 873.0 cycles / フロンティア、決めるの `g_prep` の読みの1行 100.2、ふるいの `g_dtm` の読みの1行 20.9、
`g_dtm` の先読みの区分 31.6、`stalls_mem_any` 143.9、命令 1,651.9、`resource_stalls.sb` が cycles の 2.9%）と、門番 #40（`U_loop` 27.86 秒）。
秒への換算は 1 秒 ≈ 32.8 cycles / フロンティア（3.408 GHz × 1 秒 ÷ フロンティアの延べ 103,821,853）。

考えたこと:
- **上限**: `g_prep` の読みの1行の 100.2 cycles（約 3.1 秒）。待ちが全部消えても、読みと比べ・分岐（残りが 0 か）の命令は残る。`g_dtm` の行では待ちが消えて 194 → 21 になった（約 1 割が残った）
- **効き方が `g_dtm` より弱くなりうる理由**: (1) `odd` の段では、局面1つにつき `g_dtm` と `g_prep` で平均 11 本ほどの行を、`rankOf` のループ（`rankOf` 1回 約 44 cycles）の中で続けて頼む。
  メモリの待ちを約 300 cycles とすると、頼んでから届くまでに次の局面の行も重なり、取りに行っている途中の行が 10 本の上限に近づく。上限に当たると先読みの命令そのものが待たされ、
  `rankOf` のループが遅れる。(2) 残らない候補の行（59%）も取りに行くので、メモリの読みが増える（`odd` の段の `g_prep` の行で約 2.4 倍）
- **費用**: 先読みの命令は、`odd` の段で候補ごとに1つ（今は残った候補ごとに1つ）。フロンティア1局面あたりで ＋1〜＋4 命令ほど。`unmoveStep` の機械語は静的には 7 命令減ったが、
  ループの組み方の違いで実行される命令の数がどう動くかは読んでいない
- **次に表に出うる待ち**: `dtm_ahead` では `g_dtm` の待ちを消すと `g_prep` の待ちが表に出た。今度 `g_prep` の待ちが消えると、残る読みの待ちは `rankOf` の表 `g_rank_half` の L2 の外れ
  （`perf_39` で L2 のロードミスの 7 割）と、決めるの `g_dtm` への書き込み・`g_prep` を減らす書き込み（`resource_stalls.sb` が #40 で 2.9% に上がっている）。
  先読みが詰まれば、`g_dtm` の先読みの区分と `rankOf` の区分に出る
- 置き場所のずれ（`unmoveDraws` −64 バイト、`.bss` −4096 バイト）では、これまで段は ±0.1 秒以内しか動かなかった
