## 本番の前の試しで直したこと

登録のコミットのあと、本番の前に登録どおりの形で試しの完走を1本回した（ラベル `trial/t1`、ログは [`logs/trial/`](logs/trial/)。進行は `console_trial.log`）。
`logs/trial/` の `*_record_*.tsv` は直す前の `attribute.py` が作ったもので、表の列は全部「-」になっている（下の2）。
答え・オラクル・件数の列・巨大ページはどれも通った。**試しの本の数は、集計にも見込みにも使わない。** 直したことは2つで、どちらも測る量（区間・事象・式・決め方）は変えていない。

### 1. 1本で取る事象を2つにし、ロードの周期を 20,011 にした

試しの本で、cycles の標本の数 × 周期 ÷ 区間の秒が F1 3.0・`U_loop` 3.15・`U_draw` 2.17 GHz で、登録の範囲（3.2〜3.5）より下だった。
`rankOf` だけのベンチ（`rank_bench` の fwd・thr、1 億呼び出し）で、perf stat の数（4本で cycles 5.04〜5.06 × 10^9、L1 の外れ 1.50〜1.52 × 10^7、L2 で当たり 1.24〜1.28 × 10^7）を基準に
perf record の標本の数を比べた（ログは残していない。どの数も集計に使わない）:

| 取り方 | 標本の数（本ごと） | perf stat から見込む数 |
|---|---|---|
| L1 の外れだけ（周期 2,003） | 8,184・8,329・8,233 | 7,479〜7,600 |
| cycles ＋ L1 の外れ（2,003） | L1 4,166〜8,529（10本。cycles の `pp` と `-d` の有無を変えたものを含む） | 7,479〜7,600 |
| 3つ（ロード 2,003） | L1 2,296〜5,590・L2 2,466〜6,570（3本） | 7,479〜7,600・6,212〜6,392 |
| 3つ（ロード 20,011） | L1 647〜843（4本） | 749〜761 |
| cycles ＋ L1 の外れ（20,011） | L1 782〜796（4本）、cycles 2,569〜2,572 | 749〜761・2,522〜2,530 |
| cycles ＋ L2 で当たり（20,011） | L2 656〜662（4本） | 622〜640 |
| cycles（周期 400,009）＋ L1 の外れ（20,011） | L1 726〜849（3本） | 749〜761 |

PEBS の事象を2つ以上並べてロードの周期を短くすると、ロードの標本の数が本ごとに大きく揺れ、perf stat の数と合わなかった（理由は確かめていない）。
2つまでにしてロードの周期を 20,011 にすると、標本の数 × 周期は perf stat の数より 2〜6% 多いところで揃い（多い理由は確かめていない）、本ごとの揺れも 2% 以内だった。そこで:

- **1本で取るのは2つ**: 種類 `l1` は cycles（2,000,003）と `mem_load_uops_retired.l1_miss`（20,011）、種類 `l2` は cycles（2,000,003）と
  `mem_load_uops_retired.l2_hit`（20,011）。周期は3区間とも同じ（`U_draw` の cycles の周期を縮めた組も揺れたので、`U_draw` も同じ周期にした）
- **完走は 3回 × 2種類 ＝ 6本**（r1 と r3 は `l1` → `l2`、r2 は `l2` → `l1`。ラベルは `r<回>_<種類>`）。cycles の量（割合・秒・区分）は6本の中央値と範囲、
  ロードの量は種類ごとの3本の中央値と範囲
- `U_draw` の cycles の標本は1本あたり 3,000 個ほど（6本で 1.8 万個ほど）になる
- 実効の周波数（cycles の標本の数 × 周期 ÷ 区間の秒）は本ごとに出すが、試しの本では多重化のほかにも下がる理由がありうる（perf の後始末・区間の境界の待ち）ので、
  判定には使わず参考に並べる

### 2. ロードの読む表を、データの番地ではなく命令から決める

この CPU と perf 6.8 では、`mem_load_uops_retired.*` の標本のデータの番地（`-d`）が `0xfeb800xx` のような値ばかりで、`.so` の表のどこにも当たらなかった。
標本の命令の番地は `pp` で正しいので、**その命令がどの表を読むかを逆アセンブルから決める**（[`tables.py`](tables.py)。メモリの引数のベースのレジスタを、
同じ関数の中で前にさかのぼって `lea 表(%rip)` まで辿る）。

- 決め方が正しいかを、データの番地が取れる読み込み遅延の事象（`perf mem` の `mem-loads,ldlat=8`）で `rankOf` だけのベンチを回して照らした
  （[`run_check_tables.sh`](run_check_tables.sh)、[`check_tables.py`](check_tables.py)、[`logs/check_tables.txt`](logs/check_tables.txt)）。
  `.so` の表を読む 15 命令（`g_rank_lion` 4・`g_rank_pair` 4・`g_rank_code` 2・`g_rank_half` 2・組の表 3）とも、本物の番地の表と一致した。
  `mem-loads` でも標本の半分ほどの番地は `0xfeb800xx` だったので、`.so` の表に当たった標本だけで比べた
- 同じ決め方で、`nextBoardSeenNormal`・`unmoveStep`・`unmoveDraws` の `rankOf` の 15 回の読みもそれぞれの表に決まることを、回す前に見た
- 表に決まらない読み（入力の盤の列・スタック）は「?」
- `-d` は試しで揺れを見たときと同じ形にするために残す（番地は使わない）

### 待ちと計算の分け方（`rankOf` だけのベンチ。7周の中央値と範囲）

| 入力 | thr | chain | small | thr の命令 | thr の IPC | thr の L1 の外れ |
|---|---|---|---|---|---|---|
| fwd | 49.2（49.1〜49.5） | 72.2（72.1〜72.4） | 47.4（47.4〜47.7） | 137.0 | 2.78 | 0.147 |

「主因の決め方」で本物の cycles / 呼び出し（R）を分ける:

| | F1（R ＝ 49.8） | `U_loop`（R ＝ 53.7） | 呼び出しの数で重みを付けて合わせたもの |
|---|---|---|---|
| 計算（small） | 47.4（95%） | 47.4（88%） | 47.4（92%） |
| L2 の待ち（thr − small） | 1.9（4%） | 3.2（6%） | 2.4（5%） |
| 重ねきれない分（R − thr） | 0.6（1%） | 3.1（6%） | 1.6（3%） |

- **主因は計算そのもの（R の 92%）。** 2番目（L2 の待ち 5%）は 20% に届かないので、**段2の試作は1本**（命令を減らす）
- 本物の `rankOf` は、表が L1 に残る小さい集合を独立に回したとき（small）とほぼ同じ重さだった。まわりの生成器や発見済みの表の仕事と重なって軽くなることも、
  待ちが表に出て重くなることもほとんどない
- small でも IPC は 2.9 で、4 には届かない。1呼び出しの鎖の長さ（chain − 鎖に足した2命令 ≈ 70 サイクル）と命令の数（137）から見ると、ROB（192 命令）に入る呼び出しは
  1.4 個ほどで、**独立に回しても鎖の待ちを重ねきれていない**と読める。命令を減らすと、同じ ROB に入る呼び出しが増え、鎖そのものも短くなる
- L2 の待ちは小さい: `g_rank_half` の L1 の外れは 0.25〜0.39 / 呼び出しあるが、L2 で当たる読みは独立なので鎖の上で隠れている
