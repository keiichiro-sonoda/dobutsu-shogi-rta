# 実験: 後退解析のどの段でページフォルトが増えているか

⚠️ **これは記録試行ではない。** 番号を取らず、タイムを `results/` にも README の記録表にも
載せない。入力を固定して後退解析だけを走らせた計装で、レギュレーションの
「空の `dat/` から完走」を満たしていない。

## 何を確かめたかったか

[`gate_15`](../gate_15_c_successors/) の16本で、**minor page fault の多い走行と P2 の遅い
走行が完全に一致した。**

| | minor faults | 本数 |
|---|---|---|
| 低群 | 12,624,147 〜 13,511,169 | 11 |
| 高群 | 14,739,664 〜 17,324,158 | 5 |

旧の低群 P2 の最大 197 < 高群の最小 204、新の低群 104 < 高群 129 で分離する。
段ごとの差（高群平均 − 低群平均、秒）は **P1 +4.71 / P2 +31.05** に対し
P0 −0.58 / P4 +2.85 / 174段+残差 +1.62 で、**遅れは索引を作る段と引く段に集中**していた。
増分の最小は 2,115,517 で、索引 2^29 × 16 B ÷ 4 KiB = **2,097,152** に近い。

`/usr/bin/time -v` は走行全体の合計しか出さないので、**どの段で起きているかが分からない**。
後退解析には境界が1つも無かった（`_profMark` の対象は `F0`〜`F5`、つまり全探索だけ）。
**安定している側が厚く計装され、振れている側が素**という状態だった。

## 答え: 索引を作る段（`P0`→`P1`）

計装した8本の、隣り合う境界の間の minor fault の増分。**minor の少ない順**に並べてある。

| **`P0`→`P1`** | 2396837 | 2097153 | 2098177 | 2097153 | 2097153 | 2097153 | 2097154 | **5044682** | **2,947,529** |

| `P2_free`→`P4_count` | 241023 | 392305 | 787684 | 789014 | 909666 | 985431 | 1032740 | 241050 | 791,717 |

**`P0`→`P1` が索引のページ数とちょうど 1 対 1 になる。**

| | `P0`→`P1` | 索引のページ数との比 | P1 の秒 |
|---|---|---|---|
| 6本（p2 p3 p4 p5 p6 p8） | **2,097,153〜2,098,177** | **1.00** | 20.6〜20.9 |
| p7 | 2,396,837 | 1.14 | 22.9 |
| **p1** | **5,044,682** | **2.41** | **34.3** |

索引は `aligned_alloc(64, 2^29 * 16)` ＋ `memset`（`impl/15_c_successors/animal_shogi.c:216,221`）で
8.59 GB ＝ 2,097,152 ページ。**正常な走行ではその全部をちょうど1回ずつ踏む。**
p1 は 2.41 倍踏んでいて、P1 が 20.7 → 34.3 秒に伸びた。

⚠️ **P2 の遅れは P2 自身のフォルトでは説明できない。** p1 の `P2_alloc`→`P2` は
+194,772 フォルトで +11.5 秒。フォルト1回を 1 µs としても 0.2 秒にしかならない。
索引の置かれ方が変わった結果、9.39 億回のランダム引きの局所性が落ちた、と読むのが自然だが
**測っていない**。

## メモリ圧ではない

走行中の `mem_available` は9本ともほぼ同じだった（開始時 59.7〜59.8 GB、最小 45.4〜46.8 GB）。
p1 の最小が 45.4 GB でいちばん低いが、**45 GB 空いている状態はメモリ圧ではない**。

`P2_free`→`P4_count` と `P4_count`→`P4` と `R_dtm`→`R_loop` は走行の順に単調に増えていて
（p7 が最初、p6 が最後ではないので厳密な順ではない）、合計で 1.3M ほど動く。
⚠️ **ただしこちらは時間が動いていない**（`P4_count`→`P4` は 142.8〜147.2 秒）。
p1 の異常とは別の現象で、こちらは追っていない。

## 機序の候補: 自動 NUMA バランシング

**確かめた事実**:

| | |
|---|---|
| `/proc/sys/kernel/numa_balancing` | **1**（有効） |
| NUMA ノード | **2**（node0 32.8 GB / node1 33.0 GB） |
| `/proc/vmstat` `numa_hint_faults` | 432,257,328 |
| 同 `numa_hint_faults_local` | 69,019,395（**16%**） |
| 同 `numa_pages_migrated` | 246,318,428 |

自動 NUMA バランシングは、ページを定期的に一時的な保護状態にして、次のアクセスで
**NUMA ヒンティングフォルト**を起こす。これは major ではないので **minor fault に計上される**。
遠いノードにあれば移動も起きる。

⚠️ **これは候補であって、確かめていない。** 上の `vmstat` の値はマシン全体の累積で、
p1 の超過分がそこから来た証拠にはならない。**言えるのは「その機序がこの機械で活発に
動いている」までで、p1 と結び付けてはいない。**

透過的 huge page は候補から外れている。`enabled=[madvise]` / `defrag=[madvise]` で、
索引は `madvise` を呼んでいないので huge page は一度も付かない。付いたり付かなかったりは
起こりえない。

## 次に測るなら

1. **`/proc/vmstat` の `numa_hint_faults` / `numa_pages_migrated` を走行ごとに差分で取る。**
   `run.sh` の採取ループに足すだけで、今回の8本と同じ形で比べられる
2. `numa_balancing=0` で走らせる、または `numactl --membind=0` で片ノードに固定する。
   ⚠️ どちらも機械の設定を変えるので、この実験の範囲では触っていない
3. `P0`→`P1` の中をさらに割る（`aligned_alloc` の直後と `memset` の直後）

## 計装そのもののコスト

**直接測ったもの**（`timeit`、20,000 回の最小値）:

| | µs/回 |
|---|---|
| `_rssBytes()`（`/proc/self/statm`） | 21.53 |
| `_hwmBytes()`（`/proc/self/status` を `VmHWM:` まで走査） | **32.02** |
| `resource.getrusage()`（今回足したぶん） | **0.90** |
| `_profMark()` 合計 | 59.20 |

境界は11か所なので、**後退解析1本あたり 0.651 ミリ秒**。今回足した `getrusage` のぶんは
**0.010 ミリ秒**。全探索側は 74 ラウンド × 14 か所 = 1,036 回で +0.9 ミリ秒。

**走行レベルの比較**（参考。⚠️ どれも揺れのほうが大きく、上限しか言えない）:

| | 後退解析 合計 |
|---|---|
| 計装あり8本 | 平均 500.25 / sd 9.02 |
| 計装なし `base` 1本 | 501.58 |
| [`gate_15`](../gate_15_c_successors/) の計装なし新版8本 | 平均 497.73 / sd 14.36 |

差は +2.52 秒（8本 vs 8本）だが、**sd が 9〜14 秒なので直接計測の 0.651 ミリ秒と矛盾しない**。
日が違うので機械の状態も別。**計装コストは「揺れに埋もれる」が正しい言い方。**

### console.log の2行だけ書き換えてある

⚠️ **絶対パスをリポジトリ相対に直した。**
`run.sh` が `dat/ は残した (バイト比較用): ...` を絶対パスで出していて、
ユーザ名が入ってしまったため（`make publish-check` の「ユーザ名を含む絶対パス」）。
`run.sh` 側も相対で出すよう直した。書き換えたのはこの2行のパスだけで、計測の値は触っていない。

### 検算の窓

最後の境界の `min_R_uk` と `time.txt` の `Minor page faults` は同じ rusage から来る。
`p1` で **15,769,759 対 15,771,818、差 2,059**。最後の境界より後（要約の書き出しと
インタプリタの終了）のぶんだけ `time.txt` が多い。向きも大きさも合っている。

## 8本にした理由

`gate_15` では16本中5本（31%）が高フォルト側だった。
**8本で1本も出ない確率は (11/16)^8 = 5.0%。** 実際には p1 が 2.41 倍、p7 が 1.14 倍で出た。

⚠️ **計装した8本の総フォルトは 12.93M〜15.77M で、`gate_15` の低群（12.62M〜13.51M）より
全体に高い。** `base`（計装なし、この9本の1本目）は 12.62M で低群と同じ。
順番の効きか計装の効きかは分けていない。
