# 記録 #15 でピーク RSS が上がった理由を探した（見つからなかった）

⚠️ **これは記録試行ではない。** タイムを `results/` や README の記録表に載せない。
効果量ではなく、**外れた予測の原因**を探すために測ったもの。

## 何が起きたか

記録 #15 は「ピーク RSS は 13.82 GiB のまま」を事前登録して外した。

| | ピーク RSS | 差 |
|---|---|---|
| 門番（[`gate_15_c_successors`](../gate_15_c_successors/)、旧新8本ずつ） | 13.8268 → 13.8430 GiB | **+16.6 MiB** |
| 本走（[`results/15_c_successors`](../../results/15_c_successors/)） | 13.8170 → 13.8776 GiB | **+61.8 MiB** |

門番では**旧8本と新8本が完全に分離**した（旧の最大 14,499,136 KiB < 新の最小
14,514,988 KiB）ので、揺れではない。

新版が P2 で余分に持つのは中継バッファ **256 KiB** だけで、桁が合わない。

## 測ったもの

```bash
for m in succ_small succ_big off_grow off_prealloc p2_old p2_new full_old full_new; do
    python3 experiments/rss_array_growth/probe.py "$m"
done
```

`probe.py` は1回の起動で1つだけ測る（`ru_maxrss` は取り消せない高水位なので混ぜられない）。
結果は [`log.txt`](log.txt)。

| 測ったもの | 旧（#14 相当） | 新（#15 相当） | 差 |
|---|---|---|---|
| `succ` の積み方（9 要素ずつ / 65,536 要素ずつ） | 3591.0 MiB | 3591.0 MiB | **0** |
| `succ_off` と `cnt`（`append` / 先に確保） | 484.3 MiB | 484.3 MiB | **0** |
| P2 の3本を同じ順序で作る（`p2_old` / `p2_new`） | 4065.7 MiB | 4065.7 MiB | **0** |
| それに索引 8.59 GB と `packed` 1.97 GB を先に置く | 14140.4 MiB | 14140.9 MiB | **+0.5** |

⚠️ **どれも +16.6 MiB を再現しない。** 最後の +0.5 MiB は中継バッファ 256 KiB と
ほぼ同じで、残りは説明できていない。

## 言えること / 言えないこと

- **言える**: Python 側の割り付け（配列の伸ばし方・確保の順序・先に置いた 10.5 GB）だけでは
  この差は出ない。4通りの組み合わせで 0〜0.5 MiB しか動かなかった
- **言えない**: 何が原因か。残っている違いは C の呼び出し方（`nextBoardIndexNormal` を
  99,485,568 回 → `buildSuccRange` を約 14,300 回）だが、**そこは測っていない**
- 最後の `full_*` が出した 14,140 MiB は本走の実測 14,551,676 KiB（13.88 GiB）と
  同じ桁で、**P2 の末尾がピークを決めているという見立て自体は裏が取れている**
