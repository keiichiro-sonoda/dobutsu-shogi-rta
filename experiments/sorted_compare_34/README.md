# sorted_compare_34: #34 の後退解析の `dat/` が、#33 と集合として同じかを確かめる（記録試行ではない）

番号を取らず、`impl/` を作らず、`results/` にも README の記録表にも何も載せない。速くする工夫も入れない。確かめるだけ。

## 目的

記録 #34（`impl/34_unmove`）は後退解析を作り替え、後退解析の採番順（局面が決まる順）が変わった。だから後退解析の側の
182 ファイルは、中身の並びが #33 と違い、バイト一致しない（1 個だけ一致）。記録では、ファイルの名前と件数、手数別174行、
指紋で答えを見た（[`results/34_unmove/bytecompare.txt`](../../results/34_unmove/bytecompare.txt)）。

ただ、指紋（深さごとの件数・総和・XOR）は異なる集合でも同じ値になりうるので、集合が完全に一致することの証明にはならない。
各ファイルの中身を並べ替えてから比べれば、**ファイルごとに中身が集合として同じ**ことを、バイト一致で確かめられる。

## やり方

比べるのは、#33 本走と #34 本走の作業ディレクトリ（`tools/run.sh` が git 管理外の `runs/` の下に作ったもの）の `dat/`。
どちらも読むだけで、中へ `cd` しない（パスを外から渡す）。

1. **本走のものかを照らす**（[`identify.py`](identify.py) → `logs/identify.txt`）
   - 作業ディレクトリの生ログ（`env.txt`・`time.txt`・`vmstat.tsv`・`hugefree.txt`・`freq.log`・`kaiseki_log/` の tsv 3つ）が、
     `results/33_hot_layout/` と `results/34_unmove/` の同じファイルとバイト一致する（#33 の `env.txt` は本走のあとで
     `finished` の2行を足してあるので、その2行を除く）
   - `dat/` のファイル数と合計バイト数が `sizecheck.txt` と同じ
   - #33 は、`dat/` の md5 一覧の sha256 が `results/33_hot_layout/bytecompare.txt` の #33 の値と同じ
   - #34 は、`results/34_unmove/` に並びに依る `dat/` の値（md5 一覧）が残っていない。そこで、`dat/` の更新時刻が
     本走の開始（`env.txt`）から開始 ＋ 経過時間（`time.txt`）の間に収まる（本走のあとで書き換わっていない）ことを見る
   - 照らせなければ止める
2. **ファイルごとに並べ替えて比べる**（[`compare.py`](compare.py) → `logs/compare.tsv`）
   - ファイルは 8 バイトの符号なし整数（リトルエンディアン）を並べただけでヘッダが無い。局面の列として読み、昇順に並べ替えて
     sha256 を取り、#33 と #34 で比べる
   - 並べ替えた列は重複を残すので、重複の数が違っても検出できる。重複の数も数える
   - 元の並びのままのバイト一致も並べる
3. `summary.py` が `logs/compare.tsv` を集計する（`logs/summary.txt`）

## 回す前に書いた見込みと止める条件

見込み:

- 213 ファイルすべてで、並べ替えた sha256 が一致する
- どのファイルにも重複が無い（両方とも 0 個）
- 元の並びでのバイト一致は、全探索の側の 31 ファイル（`lose000te_*` と `win001te_000`〜`028`）すべてと、
  後退解析の側の 182 ファイルのうち1個（`results/34_unmove/bytecompare.txt` の参考の値）

止める条件:

- 本走の `dat/` と照らせなければ止めて報告する
- 1 ファイルでも並べ替えた sha256 が一致しなければ、そのファイルの差（片方にだけある局面の数、そのファイルの手数）を出して
  報告する。perf の計測（`experiments/perf_34/`）には進まない

## 結果（回したあとで書いた）

**止める条件に掛かった。** ファイルごとに並べ替えて比べると、213 ファイルのうち 11 ファイルで sha256 が一致しなかった。
ただし、手数ごとにファイルを束ねて比べると、すべての手数で一致した（下の 2）。食い違いは、同じ手数の中でファイルの切れ目を
またいで局面が入れ替わったものだった。答えが変わったものは見つかっていない。

### 1. 本走の `dat/` との照合（`logs/identify.txt`）

- #33: 生ログ8つが `results/33_hot_layout/` と一致した。`dat/` は 213 ファイル / 1,974,425,336 バイトで `sizecheck.txt` と同じ。
  md5 一覧の sha256 は `bytecompare.txt` の #33 の値（`f18f3075ba25…`）と一致した
- #34: 生ログ8つが `results/34_unmove/` と一致した。`dat/` の数と大きさも `sizecheck.txt` と同じ。
  `dat/` の更新時刻（05:04:47.98〜05:05:50.71 UTC）は、計時の間（05:03:46.16〜05:05:50.83）に収まる。
  md5 一覧の sha256 は `851de9569efc…`（全桁は `logs/identify.txt`）
- ⚠️ `identify.py` は1回目の照合のあとで直した。1回目は計時の始まりを `env.txt` の `started` にしていた。
  `tools/run.sh` は `started` を書いてからビルドし、そのあとで計時を始めるので、終わりがビルドの分（約 1 秒）早く出て、
  最後のファイルの更新時刻がはみ出した（「収まらない」）。始まりを、計時の直前に開かれる `stdout.txt` の更新時刻に替えた。
  1回目の出力は残していない。計時の終わりは `time.txt` の更新時刻（05:05:50.835）と 0.005 秒で合う

### 2. ファイルごと（`logs/compare.tsv`）と、手数ごと（`logs/depth_compare.tsv`）

`python3 summary.py`（`logs/summary.txt`）:

| | ファイル | 件数（#33 / #34） | 並べ替えて一致 | 元の並びでバイト一致 | 重複 |
|---|---|---|---|---|---|
| 全探索の側 | 31 | 147,317,599 / 147,317,599 | 31 | 31 | 0 / 0 |
| 後退解析の側 | 182 | 99,485,568 / 99,485,568 | **171** | 1（`lose174te_000`） | 0 / 0 |

並べ替えて一致しなかった 11 ファイル。どれも「#33 だけにある局面」と「#34 だけにある局面」の数が同じ:

| 手数 | ファイル（件数） | 片方にだけある局面（ファイルごと。#33 だけと #34 だけは同じ数） |
|---|---|---|
| 2手負け | `lose002te_000`（5,000,000）・`_001`（4,343,557） | 3,088,572（両ファイルとも） |
| 4手負け | `lose004te_000`（5,000,000）・`_001`（625,607） | 600,066（両ファイルとも） |
| 3手勝ち | `win003te_000`・`_001`（各 5,000,000）・`_002`（1,574,858） | 順に 2,404,557・2,400,870・1,574,858 |
| 5手勝ち | `win005te_000`（5,000,000）・`_001`（2,758,524） | 1,164,778（両ファイルとも） |
| 7手勝ち | `win007te_000`（5,000,000）・`_001`（806,000） | 728,521（両ファイルとも） |

この 11 ファイルは、後退解析の側で1つの手数が2ファイル以上に分かれているところ（`win001te` の後退解析の側の2つを除く）と重なる。
成果物は手数ごとに 5,000,000 件ずつに区切って書くので、決まった順が変わると、同じ手数の中で局面が切れ目の前後を行き来する。
後退解析の側の残り 171 ファイル（1ファイルの手数と、`win001te` の後退解析の側の2つ）は、すべて並べ替えて一致した。

そこで、名前の接頭辞（`lose002te` など）が同じファイルを番号順に連結して並べ替え、手数ごとに比べた（[`depth_compare.py`](depth_compare.py)）。
`win001te` は全探索の側（000〜028）と後退解析の側（029〜030）を分けた。全探索の側の `win001te` は、ファイルごとに元の並びのまま
バイト一致しているので束ねずに省いた。**束ねた 176 個（手数 0〜174 の 175 個と引き分け。`win001te` は後退解析の側だけ）すべてで、
並べ替えた sha256 が一致し、件数も同じで、重複は両方とも 0 だった。** 2ファイル以上の手数は7つ（`lose000te`・`lose002te`・`lose004te`・
`win001te` の後退解析の側・`win003te`・`win005te`・`win007te`）。

### 見込みと実測

| 見込み | 実測 |
|---|---|
| 213 ファイルすべてで並べ替えた sha256 が一致 | **外れた。** 202 ファイル。11 ファイルは手数の中の切れ目をまたいだ入れ替え。手数ごとには全部一致 |
| どのファイルにも重複が無い | 当たった（213 ファイルとも両方 0） |
| 元の並びでのバイト一致は全探索の側 31 と後退解析の側 1 | 当たった（後退解析の側は `lose174te_000`） |

見込みを外したのは、成果物が手数ごとに一定の件数で区切られていることを見落とし、「ファイルごとに集合が同じ」と置いたため。
採番順が変わればファイルの切れ目も動きうる。区切り（ファイルの名前と件数）が同じでも、中身の集合が同じとは限らない。

### 言えること・言えないこと

- 言える: #34 本走の `dat/` は、手数（と引き分け）ごとに、#33 本走の `dat/` と同じ局面の集合で、重複も無い。
  答え（局面ごとの勝ち負け引き分けと手数）は #33 と同じ
- 言える: ファイル単位では 11 ファイルで中身の集合が違う。手数をまたいではいないが、ファイルを1つずつ取り出して #33 と
  比べる使い方では一致しない
- 言えない: #34 の各ファイルの切れ目がどう決まったかは追っていない（決まった順に5,000,000 件ずつ、という書き出しの作りから
  読んだだけ）
