# unmove_bench: 一手前の局面を直接作る生成器を、試験台で作って測る（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。記録にするかどうかは、この実験の数字を見て決める。

## 目的

#33 の後退解析は 79.0 秒（完走の 58.7%）で、そのうち次の4段、**約 77 秒**が「前任（一手前の局面）の一覧を作って、たどる」ための工程。

| 段 | 秒（#33 本走） | していること |
|---|---|---|
| P1 索引 | 7.2 | パック値 → 連番のハッシュ表（8 GiB）を作る |
| P2 後続生成 | 39.2 | 未知局面 99,485,568 個の後続を作り、索引で連番に直す（辺 938,671,869 本） |
| P4 前任リスト | 15.8 | 辺の向きを逆にして、前任の一覧（CSR）に詰め直す |
| 174段ループ | 14.5 | 前任の一覧をたどって勝ち負けを広げる |

いまの作りは前任を直接は計算せず、全部の後続を作ってから逆向きに並べ替えている。**局面 q を受け取って、q の一手前にありえた局面を
その場で全部作る生成器**（以下「逆向きの生成器」）があれば、P2 と P4 は要らなくなり、後退解析の状態を #30 のランクを添字にした配列で
持てば P1 も要らなくなる。

この実験では後退解析は作り替えない。**逆向きの生成器だけを作り、正しさを全局面で確かめ、1局面あたりの費用を測って、置き換えられる秒を見積もる。**
gen_bench が「いまある部品を速くする」実験だったのに対し、今回は「いま存在しない部品を作る」実験で、**正しさの確認が主で、計時は従**。

## 正解の定義

**正解は、いまの後退解析が作っている前任の多重集合（公式ルールではない）。** いまの生成器（`nextBoardInvNormal`）の規則とずれが無いこと。

- 全到達局面 q について、**pred(q) ＝ { 未知局面 p : p の後続の列に q が現れる }**。p が q を何回生むかの**重複も数える**
  （いまの `cnt[p]` は重複込みの出次数で、174段ループは辺1本につき1回減らしている）
- 前任 p は**未知局面だけ**（キャッチ局面・トライ負け局面は後続を持たない。到達しない局面も前任にならない）
- 盤の向きと左右の正規化（`normalBoard`）は、いまの規約のまま。逆向きの生成器が出す p も、`normalBoard` を通した形（正規形）で比べる

## 逆向きの生成器の作り（[`unmove.c`](unmove.c)）

いまの生成器は、局面 p を `invBoard()` で反転した盤 b' の上で手番側の駒（9〜13。所有者ビット `0b1000`）を動かし、動かした直後の盤 nb を
`normalBoard()` に通したものを後続 q にしている。nb ではもう反転しないので、**q では「直前に指した側」の駒が 9〜13、その持ち駒が bit 54〜59 にある。**
だから前任は、q の上で 9〜13 の駒の手を1つ戻した盤 b' を作り、p ＝ `invBoard(b')` とすればよい。

戻す手は、いまの生成器の手の規則をそのまま逆にした（規則の正本は `impl/33_hot_layout/animal_shogi.c` の `nextBoardInvNormal`）。

| 直前の手 | 戻し方（q の上で、直前に指した側の駒 k がマス d にあるとき） |
|---|---|
| 駒を動かした（取らない） | 元のマス s ＝ d − 移動量（移動表 `GIRAFFE_MOVE` などのとおり）。s が盤の中で、端から端へ回り込む手（`src_mod16` の2つの条件）でなく、空いていること |
| 駒を取った | 上の手に加えて、取られた駒 c を d に戻し、持ち駒から1枚減らす。c はひよこ・にわとり（どちらも持ち駒の bit 54 に入る）・きりん・ぞう。ライオンは取る手が無い（取れる局面はキャッチで後続を持たない） |
| 持ち駒を打った | k がひよこ・きりん・ぞうなら、d から盤の駒を外して持ち駒に1枚足す。打てるマスに制限は無い（いまの生成器は空きマスならどこでも打つ。端の行のひよこも） |
| ひよこが成った | k がにわとりで d が端の行（`d % 16 == 0`）なら、ひよことして d ＋ 4 から進んで成った手もある（取ったかどうかで枝分かれ） |

ひよこ（成っていない）が端の行にいれば、それは打った駒（進んできたなら成っている）。持ち駒の数の増減は、いまの生成器の XOR の式
（0 → 1、1 → 2 が取ったとき、2 → 1、1 → 0 が打ったとき）をそのまま逆にした。

作った候補は、(a) 正規形か、(b) 到達しているか、(c) 未知局面か、でふるう。(b) と (c) は、ランクを添字にした 1 バイトの種類の表
（`cls`。0 到達しない / 1 未知 / 2 キャッチ / 3 トライ負け。855,232,344 バイト）を1回引くだけでまとめて決まる。
`cls` は全到達局面をいまの生成器に通して作る（[`bench.c`](bench.c) の `prep`）。作るときに、正規形の到達局面どうしでランクが重ならないことも確かめる。

### 正規化と重複の扱い

**q ＝ `normalBoard(nb)` なので、手を指した直後の盤 nb は q か、q の左右の鏡像のどちらか**（q が左右対称なら q だけ）。
その両方（対称なら1つ）から手を戻し、**戻した p が正規形（`normalBoard(p) == p`）のものだけを残す。** これで、残る（nb, 戻した手）の組と、
いまの生成器の（p, 手）の組がちょうど1対1になる。

- いまの生成器の（p, 手）の組は、p が正規形で、手を指した直後の盤 nb は q か鏡像のどちらか。その nb から手を戻すと b' ＝ `invBoard(p)` に戻り、
  p は正規形なので残る。だから、いまの組はどれも1回ずつ数えられる
- 戻した p が正規形でない組は、鏡像の側（鏡像の nb から鏡像の手を戻した組）と重なる。鏡像の側の p は正規形なので、そちらで数えられる。
  正規形でない側を捨てるので、二重に数えない
- p が左右対称なら、手とその鏡像の手は別の手として両方数える（いまの生成器も両方作って、どちらも q になる）。手そのものが左右対称
  （まん中の列の駒）なら nb も左右対称になり、q も対称なので、nb は1つしか作らない。どちらもいまの数え方と同じになる
- ランクだけでふるうと二重に数えうる: #30 のランクは鏡像どうしを同じ値にまとめる（ライオンがどちらもまん中の列のときを除く）ので、
  正規形でない p も到達していると判定されてしまう。**正規形の検査を先にする**

## 正解との突き合わせ（[`bench.c`](bench.c) の `verify`）

q ごとに（前任の件数、前任のパック値の 64 ビットのハッシュの和、別のハッシュの XOR）を、前向き（未知局面 p の後続を全部作り、後続 q ごとに p を足す）と
逆向き（全到達局面 q から前任を作る）の両方で集めて比べる（`oracle/fingerprint.tsv` と同じ考え方）。ハッシュは splitmix64 の混ぜ方。
食い違った q は、逆向きの前任の中身と戻した手の種類を出す。前任の総数と辺の総数（938,671,869）も比べる。

## 入力

（ファイル名では決めない）。`dat/`・`cls.bin`・抜き出した局面は git に入れない（`runs/unmove_bench/`）。

- **一致の検査は全局面で行う**（[`run_verify.sh`](run_verify.sh)。`logs/prep.txt` と `logs/verify.txt`）
- **計時は 1,000万局面で行う。** 種類ごとに全体の比率（未知 4,030,968 / キャッチ 5,684,636 / トライ負け 284,396）で、`dat/` の名前順の並びの上で
  部分的な Fisher-Yates（splitmix64、シード 20261005）で抜き出す。種類ごとの列（抜き出した順）と、3種類を合わせて同じ乱数で並べ替えた列（mixed）を作る

## 条件（[`build_so.sh`](build_so.sh) / [`run_time.sh`](run_time.sh)）

計時の条件は gen_bench と揃えた。

- **本番と同じ `gcc` 行で作った `.so` から呼ぶ。** `impl/33_hot_layout` の `animal_shogi.c` / `.h` / `hot_layout.ld` を写し、`unmove.c`（`animal_shogi.c` を
  `#include` する）を、`impl/33` の `Makefile` の `gcc` 行のまま（入力と出力の名前だけ替えて）`.so` にする。ランクの表と `rankOf()` は `static` なので、
  同じ翻訳単位に置くしかない。ベンチ本体は `.so` を `dlopen` して関数ポインタで呼ぶ（本番の `CDLL` と同じ `RTLD_LOCAL`）
- 1本ごとに別のプロセス。`numactl --cpunodebind=0 --membind=0` で固定。5つの版を5周まわし、周ごとに順番を1つずつずらす
- 各列を1周温めてから1周測る。計時するのは呼び出しのループだけ（入力の読み込みは外）。周波数の標本を `logs/freq.log` に取る
- **`cls` と状態の配列は 2 MiB の区切りで確保して `madvise(MADV_HUGEPAGE)` を頼む**（本番の表と同じ）。計時の前後の `thp_fault_fallback` を残す
- **先読みを入れた。** 候補のランクを全部先に出して `cls` の行を取り寄せてから順に見る。3 では、残った前任のランクを出して状態の配列の行を取り寄せてから
  書く（#20 / #30 と同じ形）。先読みしない版は測っていない

| 版 | 測るもの | 出す値 |
|---|---|---|
| `cand` | 1. 逆向きの生成器（候補を作って正規形の検査まで） | q の種類ごとの ns/局面、候補の平均数 |
| `sieve` | 2. 1 ＋ ふるい（ランクを出して `cls` を引く） | 同上、残った前任の平均数 |
| `visit` | 3. 2 ＋ 状態の配列（ランクを添字にした 1 バイト）を前任ごとに1回読んで1回書く | 同上 |
| `degw` | 換算用: 局面ごとにランクを出して 1 バイト書く（出次数を全探索で数えて持ち越す案の、足す費用） | ns/局面 |
| `gen` | 比べる相手: いまの前向きの生成器（`nextBoardInvNormal`） | ns/局面、後続の平均数 |

作る前に候補を絞る版（前任の局面で手番側がライオンを取れる形を作らない、など）は作っていない（任意）。

⚠️ **手順を1つ外した。** 見込みと止める条件は回す前にコミットすることになっていたが、一致の検査を先に回してしまった（下の結果はそのときのもの。
コミットしたコードで回し直したものを `logs/` に置いた）。止める条件は回す前から上のとおりに決めていて、それで判定した。
候補の数とふるいに残る数は、見込みを書く前に結果を見てしまったので、**下の見込みの表には載せない**（載せると事前の見込みに見える）。
計時（ns/局面）と換算の見込みは、計時の前に書いてコミットした。

## 本走への換算

作り替えたあとの後退解析を3つの和として見積もった（[`summary.py`](summary.py)。周ごとに計算して中央値と範囲）。比べる相手は #33 本走の
P1 ＋ P2 ＋ P4 ＋ 174段ループ ＝ **76.70 秒**。

| | 秒 | 中身 |
|---|---|---|
| 1. 前任をたどる | **219.7**（218.4〜220.6） | `visit` の種類ごとの値 × 展開する局面（キャッチ 140,298,614 ＋ トライ負け 7,018,985 ＋ 決まる未知 96,802,868 ＝ 244,120,467） |
| 2A. 出次数を全探索で数えて持ち越す | 9.0（8.9〜9.1） | 種類と出次数を 1 バイトにまとめ（未知は出次数 1〜48、ほかは別の値）、F1 で全局面に1回ずつ書く（`degw` × 246,803,167） |
| 2B. 後退解析の初めに数える | 31.2（30.9〜31.4） | 2A ＋ 前向きの生成器を未知局面でもう一度回す（`gen` × 99,485,568） |
| 3. 成果物の形に戻す | 測っていない | 決まった局面の値はたどる時点で手元にあるので、手数ごとの列に足して書くだけ（並べ替えも引き直しも要らない）。数秒の桁と見るが、未計測 |
| **1 ＋ 2A**（3 を除く） | **228.6**（227.3〜229.6） | いまより **+151.9 秒**（+150.6〜+152.9） |

**素朴な逆向きの生成器では、作り替えると後退解析は約 3 倍に遅くなる見積もり。** 前任1本あたりで比べると、いまの4段は辺1本あたり約 82 ns
（76.70 秒 ÷ 938,671,869）、逆向きは前任1本あたり約 234 ns（219.7 秒 ÷ 938,671,869）。

遅い理由は構造にある。

- **いまの作りは、未知局面 99,485,568 個からだけ生成器を回す**（後続 9.4 本）。**逆向きは、決まる局面 244,120,467 個（2.45 倍）から回す**。
  そのうち 57% はキャッチ局面で、前向きでは 110 ns で打ち切れる局面が、逆向きでは 533 ns の候補作りになる
- **候補は前任の 2.6 倍**（9.77 対 3.80）作ってから捨てる。候補作りとふるいの費用の大半が、捨てる候補に使われている
- いまの4段のうち、P2 は後続1本あたり索引引きが約 18 ns（P2 の 394 ns/局面 − `gen` の 223 ns、を 9.4 で割る）、P4 と174段ループは
  DRAM を順に近く舐める。逆向きは「生成 ＋ ランク ＋ ランダムな読み」を前任ごとではなく候補ごとに払う

**ふるいと状態の読み書きだけでも（生成器の費用を 0 としても）**、(`sieve` − `cand` ＋ `visit` − `sieve`) × 展開する局面 ≈ 85 秒で、いまの 76.7 秒を超える。
作り替えが速くなるには、**候補をふるう前に減らす**（作る前に絞る版。たとえば前任の局面で手番側がライオンを取れる形を作らない）ことと、
**生成器そのものを数倍軽くする**（候補ごとの `invBoard()` をやめ、反転した盤の上で戻して最後にまとめて反転する、など）ことの両方が要る。
どちらもこの実験では作っていない。
