# unmove_catch: キャッチ局面への手を、残りの後続の数から最初に外す（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。

**工夫は1つだけ入れる。** 逆向きの生成器は [`unmove_bench`](../unmove_bench/) の素朴な版（`unmove.c`）をそのまま使う
（書き換えずにビルドのときに写す）。`unmove_bench` が挙げた「作る前に候補を絞る」「反転を1回にする」は入れない。効いた・効かないを、
この工夫ひとつに帰せるようにするため。

## 目的

`unmove_bench` の換算では、作り替えた後退解析の「前任をたどる」費用が 219.7 秒だった。展開する局面 244,120,467 個のうち
57%（140,298,614 個）がキャッチ局面で、そこからも逆向きの生成器を回している。

**未知局面 p の「残りの後続の数」を、最初からキャッチ局面への手を除いて数えておけば、キャッチ局面から前任をたどらずに済む**、
という見立てを確かめる。

1. 答えが変わらないか（全局面の勝敗と手数が `dat/` と一致するか）
2. 外したぶん、後退解析がどれだけ速くなるか（同じ素朴な生成器で、外す版と外さない版を丸ごと回して比べる）
3. キャッチ抜きの数を、いくらで数えられるか（B1・B2）

## キャッチ局面への手を外しても答えが変わらない理由

いまの後退解析（`impl/33_hot_layout` の `retreatAnalysis` と `retreatStep`）の規則を読むと、手数は次のように決まる。

- 手数 0 の負け = トライ負けの局面、手数 1 の勝ち = キャッチ局面（と、トライ負けの局面へ指せる局面）
- 手数 d（奇数）の段: 手数 d − 1 で負けに決まった局面 q の前任で未定のものは、勝ち（手数 d）
- 手数 d（偶数）の段: 手数 d − 1 で勝ちに決まった局面 q の前任ごとに、残りの後続の数を辺1本につき1つ減らし、0 になって未定なら負け（手数 d）
- 段は手数の小さい順に進む

だから、**負けに決まる局面 p の手数は「1 ＋ 後続の勝ちの手数の最大」**になる（最後に残った後続が勝ちに決まった段の次で 0 になる）。
勝ちに決まる局面と引き分けは、後続に負けがあるか・最後まで 0 にならない後続があるかで決まる。

キャッチ局面は手数 1 の勝ちで、勝ちの手数の最小（手数 1 より小さい勝ちは無い）。

- **後続にキャッチ局面でないものが1つでもある p:** キャッチ局面を除いても、後続の勝ちの手数の最大は変わらない（ほかの後続の勝ちは手数 1 以上）。
  後続に負けがあるかどうかも変わらない（キャッチ局面は勝ち）。最後まで勝ちに決まらない後続（引き分け）があるかどうかも変わらない。
  だから、負けなら手数は同じ、勝ち・引き分けもそのまま
- **後続がキャッチ局面だけの p:** いまの規則では、手数 1 の勝ち（キャッチ局面）を処理する手数 2 の段で 0 になり、**手数 2 の負け**。
  外す版では残りの数が最初から 0 なので、たどってくる前任が無い。だから**最初に手数 2 の負けとして決め、手数 2 で決まった局面に足す**
  （手数 3 の段で、その前任を勝ちにするため）。この局面は手数 1 の段で勝ちに決まることも無い（後続に負けが無い）

キャッチ局面そのものは手数 1 の勝ちのまま（初めから決まっている）。外すのは「キャッチ局面から前任をたどること」と「キャッチ局面への辺を数えること」だけ。

## 試作の後退解析（A。[`catch.c`](catch.c) の `catchStep`、[`bench.c`](bench.c) の `retreat`）

`unmove_bench` の部品（逆向きの生成器、ランクを添字にした種類の表 `cls`）で、後退解析を試験台の上で1本回す。記録にする設計ではない。

- 状態はランクを添字にした 1 バイトの配列2本: 手数 `dtm`（255 が未定。奇数が勝ち、偶数が負け）と、残りの後続の数 `cnt`
- 手数ごとのフロンティア（その手数で決まった局面の値）から、逆向きの生成器で前任をたどる。候補は `cls` でふるい（未知局面だけ残す）、
  いまの `retreatStep` と同じ規則で `dtm` と `cnt` を書く。`cnt` を 0 から減らそうとしたら止める（数え方の誤り）
- 先読みあり: 候補のランクを全部出して `cls` の行を取り寄せ、残った前任の `dtm`（と `cnt`）の行を取り寄せてから書く（`unmove_bench` の `visit` と同じ形）
- `dtm`・`cnt`・`cls` は 2 MiB の区切りで確保して `madvise(MADV_HUGEPAGE)` を頼む

| 版 | 残りの後続の数（初期化） | キャッチ局面 | 手数 2 の段 |
|---|---|---|---|
| `keep`（外さない） | 重複込みの出次数（いまの生成器の戻り値。いまの `cnt` と同じ） | 手数 1 の勝ち。手数 2 の段のフロンティアに入れる | フロンティアはキャッチ局面 ＋ 手数 1 で決まった局面 |
| `drop`（外す） | キャッチ抜きの数（B2 と同じ数え方: 後続のランクで `cls` を引く） | 手数 1 の勝ち。たどらない | フロンティアは手数 1 で決まった局面だけ。キャッチ抜きの数が 0 の局面を手数 2 の負けとして足す |

**一致の検査:** 終わったら全局面の手数を、`dat/` のファイル名（`win<手数>te_*`・`lose<手数>te_*`・`unknown*` は引き分け）から決めた正解と比べる。
食い違ったら、正解と試作の勝敗の組（負け・勝ち・引き分け）ごとに数え、例を20個出す。`keep` が一致することが、試作そのものが正しいことの確かめになる。

時間は、初期化（残りの後続の数を数えて、キャッチ局面・トライ負け局面を置く）とループ（手数ごとの段）を分けて測る。段ごとに、フロンティアの大きさ・
候補・残った前任・決まった局面・秒を出す。ふるいで捨てた候補を理由ごと（到達しない / キャッチ局面 / トライ負け局面）に数える。

## キャッチ抜きの数の数え方（B）

- **B1（[`catch.c`](catch.c) の `nextBoardCountNonCatch`）: 全探索で、後続を作るその場で見分ける。** いまの生成器の本体を写し、後続を積むところで
  「手を指した直後の盤で、相手が指した側のライオンを取れるか」（`catchAfterMove`）を足した。後続の列はいまの生成器と同じ順で同じもの
  - 判定はいまの生成器のキャッチの規則（反転した盤で、手番側の駒が `LION1` のマスへ動けるか）を、反転する前の盤に移したもの。
    反転はマス a を 44 − a へ移すので、「元のマス s から移動量 m」が「ライオンのマス L ＝ s − m」になる。回り込みを捨てる2つの条件は反転しても
    同じ組み合わせ。ひよこは L ＝ s ＋ 4 で、s が反転前の盤の端の行（`s % 16 == 12`）でないこと。表は移動表から作る（`catchAttackBuild`）
- **B2（`countNonCatchB2`）: 全探索のあとで数え直す。** 未知局面ごとにいまの生成器を回し、後続のランクで `cls` を引いてキャッチ局面を除く
- **一致の検査（[`run_count.sh`](run_count.sh)）:** 全未知局面で、B1 の数と B2 の数が一致すること、B1 の後続の列がいまの生成器と同じであることを確かめる

## 入力と条件

- 入力は #33 本走の `dat/`（213 ファイル、246,803,167 局面）。`cls.bin` と計時用の抜き出しは `unmove_bench` と同じ作り方・同じシード（20261005）で
  `runs/unmove_catch/` に作り直す（git に入れない）
- `.so` は `impl/33_hot_layout` の `Makefile` の `gcc` 行のまま（入力と出力の名前だけ替えて）ビルドする（[`build_so.sh`](build_so.sh)）。ベンチ本体は
  `dlopen` して呼ぶ（`RTLD_LOCAL`）
- どの本も `numactl --cpunodebind=0 --membind=0` で固定し、周波数の標本を取り、前後の `thp_fault_fallback` を残す
- **A（[`run_retreat.sh`](run_retreat.sh)）:** `keep drop drop keep keep drop` の6本。1本ずつ別のプロセスで、終わるたびに一致の検査をする
- **B（[`run_time.sh`](run_time.sh)）:** `gen`（いまの生成器）・`b1`・`b2` を5周、周ごとに順番をずらす。1,000万局面の抜き出しで、各列を1周温めてから1周測る
- 回す順: `run_count.sh`（準備と B の一致）→ `run_retreat.sh`（A）→ `run_time.sh`（B の計時）

## 止める条件（回す前に決めた）

1. **`keep` が全局面で一致しなかったら**、試作の後退解析の不具合として、`drop` に進まずに止めて報告する（`run_retreat.sh` は1本目が `keep`）
2. **`drop` が一致しなかったら**、そこで止めて計時に使わない。食い違った局面を勝敗の組ごとに分けて報告する
3. **B1 の数が B2 と1局面でも合わなかったら**（または B1 の後続の列がいまの生成器と違ったら）、B1 は計時しない（`run_time.sh` が `logs/count.txt` を見る）

## 言えないこと

- 試作は記録にする設計ではない。Python からの呼び方・`dat/` への書き出し・採番順は入っていない。本当の効果は、記録にするときの門番で測る

## 次の工夫の推奨（決めない）

**「作る前に絞る」を先に試す。** `drop` で展開した局面の候補 1,094,348,081 個のうち、31.2%（341,669,361 個）は「前任の候補が、手番側が
ライオンを取れる局面（キャッチ局面）」で捨てられ、23.5% は到達しない局面で捨てられている。キャッチ局面の候補を作る前に落とせれば、候補作り
（`unmove_bench` で候補1個あたり約 57 ns）とふるい（約 30 ns）の両方が、候補の約3割について要らなくなる。粗く見積もると、
341,669,361 × 約 87 ns ≈ 30 秒の桁。ただし、判定の費用が B1 と同じ作り（1回約 42 ns）だと得の半分が消える。手を戻す前の盤で一度だけ
「どのマスへ戻すと手番側の駒がライオンに利くか」を求め、候補ごとの判定を表引きにする形が要る。

「反転を1回にする」は、候補全部（1,094,348,081 個）について `invBoard()` 1回ぶん（約 4 ns）と、その前後の詰め直しが減る。粗く 5〜10 秒の桁で、
「作る前に絞る」より小さい。

どちらも入れたとしても、`drop` のループ 80.21 秒からこの見積もりを引いた 40〜45 秒に、残りの後続の数を数える費用（B2 なら 45.93 秒。B1 を
速くできればそれ以下）が乗る。いまの4段の 76.70 秒を下回れるかは、数える費用をどこまで減らせるか（全探索の F1 で後続を作るときに、
`cls` を引かずに数える B1 を、1後続あたり数 ns にできるか）で決まる。
