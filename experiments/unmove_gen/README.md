# unmove_gen: 逆向きの生成器を2通りに作り替えた試作を、生成器だけのベンチで測る（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。門番・本走はしない（推すところまで）。

## 目的

記録 #35（`impl/35_bitboard`、0:01:54）で一番大きい段は後退解析のループ `U_loop`（本走で 56.65 秒）になった。その中心は逆向きの生成器
`unmoveCandidates()`（`perf_34` で `U_loop` のサイクルの約 54%、ほかに戻した盤ごとの `invBoard` が約 7%）。これを**独立した2つのやり方**で作り替えた試作を作り、
今の生成器と同じベンチで比べる。どちらを（両方なら、どの順で）記録試行の門番にかける価値があるかを、根拠を添えて推す。

## 腕

どの腕も `impl/35_bitboard` の写しにパッチを当てて作る（[`build_arm.sh`](build_arm.sh)、[`patches/`](patches/)）。`impl/35_bitboard` そのものは触らない。
**変えるのは `unmoveCandidates()` とその下請け（`unmoveRaw`・`unmovePiece`・`unmoveEmit`）と、そのための表だけ。** 全探索の側・`unmoveStep()`・
`normalBoard()`・`invBoard()`・ランク・Python・`Makefile`・`hot_layout.ld` は変えない（関数名も同じ。新しい熱い関数は無い）。両方を入れた腕は作らない。

| 腕 | 中身 | 狙い |
|---|---|---|
| `base` | `impl/35_bitboard` のまま（`.so` は #35 本走と同じバイト列、sha256 の先頭 `3b37ebdc6230`） | 比べる元 |
| `mirror1` | q と鏡像の q の両方から手を戻すのをやめ、q だけから戻して正規化する | 作ってから捨てている半分を作らない（仕事の量） |
| `bb_unmove` | 元のマスの候補を、ビット集合と表引きで出す（q と鏡像の両方から戻すのは今のまま） | 外れの多い分岐を消す（1回あたりの速さ） |

### `mirror1` の数え方

今の作り（[`unmove_bench`](../unmove_bench/) の「正規化と重複の扱い」）は、q と鏡像の q（q が左右対称なら q だけ）から手を戻し、戻した p が正規形のものだけを残す。
[`unmove_flip`](../unmove_flip/) の全局面の数で、戻した盤の約半分（1,159,696,580 回）を正規形でないとして捨てている。`mirror1` は q だけから戻し、
戻した候補 c ごとに正規形 N(c)（`normalBoard(c)`）にして出す。辺の本数を今と同じにする規則は2つ:

1. **q が左右対称でないとき**: N(c) を出す。**c が左右対称なら N(c)（＝ c）を2回出す**（p が対称だと p → q と p → 鏡像の q は別の手だが、q からは片方しか見えない）。
   パッチでは `out[n] = out[n+1] = N(c); n += 1 + (c が対称)` と書いた
2. **q が左右対称なとき**: 今と同じく、c が正規形のものだけを残す（正規化して出すと、手と鏡像の手から同じ p が2回出て多く数えるため）

鏡像の q から戻した候補は、q から戻した候補の鏡像と1対1に対応するはず（移動量の表・盤の端・「戻した先からライオンに利く戻し方は作らない」がどれも左右対称）。
すると q ごとの候補の**多重集合**は `base` と同じになる。成り立つかは一致の検査で確かめる。候補の並びは変わる（後退解析の順と後退解析の側の `dat/` の並びも変わる。#34 と同じ）。
`unmoveRaw`・`unmovePiece`・`unmoveEmit` に「正規化して出すか」の引数を足し、`unmoveCandidates` が q の対称で2通りに呼ぶ（引数は定数で、インライン展開で畳まれる）。

### `bb_unmove` の作り

#35 の全探索の生成器と同じ考え方を、「駒を動かした手を戻す」部分に入れる。マス s はビット s（各4ビットの最下位）に置く。

- **表**（`unmoveSrcTableBuild()`、`unmoveTableBuild()` の中で1回だけ呼ぶ）: `g_usrc[駒][d]` ＝ 駒を動かした手を戻した元のマス s の集合、
  `g_upromo[駒][d]` ＝ にわとりが端の行にいるときの「ひよこが成った」を戻す元のマス d + 4、`g_uatk[駒][L]` ＝ 置くと LION1 のマス L に利くマス（今の `g_xatt` を引き直したもの）。
  **`g_usrc` と `g_upromo` は今の `unmovePiece` の判定（`s = d - moves[i]`、盤の外、端の回り込み2条件、ひよこの特別扱い）をそのまま全通り回して作る**。
  表を作る関数は `noinline, cold` にして、生成器に展開させない
- 元のマスの候補 ＝ `g_usrc` ∧ 空きマス ∧ ¬`g_uatk`（元のマスが空いているか・盤の端・戻した先から利くかの分岐が消える）。空きマスは `(nb | nb>>1 | nb>>2 | nb>>3)` から作る
- X の駒（直前に指した側。持ち主のビット 0b1000）のマスは `(nb >> 3) & 0x111111111111` を `ctz` で番号の小さい順に取り出す（X の駒かの分岐と 12 マスのループが消える）
- 打った手を戻す部分は「戻せる駒か」をビットの表（`UNMOVE_DROP_KOMA >> k`）で見る。取った駒を戻す部分（4種類）は今のまま（`unmoveCaptures` にくくり出しただけ）。
  成りを戻す候補は1つの分岐が残る。持ち駒の枚数で分かれるところは今回の主眼ではない
- q と鏡像の q の両方から戻し、正規形だけを残す作りは今のまま

**候補の並びを今と完全に同じにする仕組み。** 今の並びは (1) q、次に鏡像の q、(2) その盤の中で X の駒のマス d を番号の小さい順（A が1マスならそのマスだけ）、
(3) d ごとに「打った」→「動かした」元のマス s →（s ごとに「取っていない版 → 取った駒の4種類（`UNMOVE_CAPTURED` の順）」）、(4) 正規形でないものは捨てる。
移動量の表はどれも昇順で `s = d - moves[i]` なので、**s は番号の大きい順**に出る。そこで s は `63 - clzll` で大きい順に取り出す（`lzcnt`）。
にわとりが端の行にいるときの「ひよこが成った」候補（`s = d + 4`）は、ほかの s の**あと**に出す（にわとりの普通の戻し方にも `s = d + 4` があり、そちらが先）。
1つの駒の移動量の表に同じ s は2回出ないので、ビット集合にしても候補は落ちない。

## 選び方（回す前に決めた）

- 判定の量は **order 入力の1局面あたり `cycles`**。腕ごとに `腕 − base` の範囲（7周）が 0 をまたがずに下なら、記録試行の門番にかける候補として推す
- **両腕とも候補になったときの順番**: order の cycles の差の中央値で、`mirror1` の減りが `bb_unmove` の減りの **2 倍以上なら `mirror1` を先**、そうでなければ **`bb_unmove` を先**に推す。
  `bb_unmove` は候補の並びを変えないので、記録にするときの答え合わせを `dat/` のバイト一致のまま進められ、門番の差に並びの効果（後退解析の順が変わること）が混ざらない。
  `mirror1` は並びが変わり、答え合わせが手数ごとの集合になる。それでも差がはっきり大きければ先に取る価値がある、という線を 2 倍に置いた
- どちらも候補にならなければ、門番は推さない

## 止める条件（回す前に決めた）

1. `bb_unmove` の一致の検査で、候補の列が1局面でも `base` と違う（並びも含む）。または完走の `dat/` が #35 本走とバイト一致しない
2. `mirror1` の一致の検査で、候補の多重集合が1局面でも `base` と違う。または完走でオラクル・指紋・手数ごとの集合のどれかが外れる
3. `bb_unmove` で、候補の並びを保てない箇所が見つかる（直し方を自分で決めずに報告する）
4. 完走の前の巨大ページの空きが足りない、`perf_event_paranoid` が 1 でない（`run_all.sh` が回さずに止める）

1・2 に掛かった腕は計時しない（`run_all.sh` が見る）。両腕とも掛かったら計時に進まない。

### 言えないこと

- ベンチは生成器 ＋ 番号の計算だけで、本物の `U_loop` の手数の配列と残りの数の読み書き・書き出しを含まない。秒への換算は見込み
- `mirror1` は候補の並びを変えるので、記録にすると後退解析が局面を決める順と、`dat/` の並びが変わる。それが後退解析の段（表を引く順・先読みの当たり）に効くかは、このベンチでは見えない
- 完走は答え合わせのために回しただけで、時間は比べていない（`numactl` で固定した1本ずつで、計時の手順を踏んでいない）
- 帰属の標本の数 × 周期が `perf stat` の予測ミスと合わない理由（上）は確かめていない。割合は3回でほぼ揃った
- 2つを両方入れた腕は作っていないので、下の足し算の見込みは測っていない

## 推奨（決めない）

- **どちらも記録試行の門番にかける価値がある。順番は `bb_unmove` が先、`mirror1` があと**（回す前に決めた規則: 減りの比 1.22 が 2 倍に届かない）。
  `bb_unmove` は候補の並びまで同じなので、門番の答えは `dat/` のバイト一致（#35 本走の md5 一覧）で見られ、差に並びの効果が混ざらない。換算は −13.5 秒。
  `mirror1` は単独ならもっと大きい（−16.4 秒）が、並びが変わり、答え合わせは手数ごとの集合（#34 と同じ形）になる
- **2つを両方入れても、足し算にはならないと見る（掛け算に近い）。** `mirror1` は生成器を呼ぶ回数（戻した数）を半分にし、`bb_unmove` は1回あたりを速くするので、効く場所は違うが、
  同じ生成器のサイクルに掛かる。ベンチの order で、生成器の外（候補ごとの `rankOf` と外枠）を R、生成器を G とすると、`base` ＝ G ＋ R ＝ 1,382、`mirror1` ＝ G/2 ＋ R ＝ 844 から
  G ≈ 1,076・R ≈ 306。`bb_unmove` で G は 631。両方なら 631/2 ＋ 306 ≈ 622 cycles（`base` から −760）で、2つの差の和（−985）の 8 割に届かない。
  `bb_unmove` を先に入れたあとで `mirror1` を足したときの取り分は −316 cycles（換算で −9.6 秒）、と見る（R が変わらず、半分にする効き方が同じという仮定。測っていない）
- **`bb_unmove` で残った予測ミスの大きいところ**: 元のマスの候補を取り出すループの抜け 2.49 / 局面（局面ごとに回数が変わるので分岐として残る）、
  打った手を戻せるかの条件 1.32（`&&` を `&` にするか、持ち駒の位置と「打てるか」を1つの表にして分岐を1つにできる見込み）、取った駒の持ち駒が無いか 0.96
  （4種類の持ち駒の有無をビットで先に集め、ある種類だけを回す形にできる）、X の駒のマスのループ 0.88、正規形の判定 0.83（`perf_branch_34` の推奨の「書いてから数を条件で足す」）。
  後ろ3つ（打てるか・持ち駒・正規形）で 3.1 / 局面ほどあり、1回 15〜23 サイクルなら `U_loop` で 1.4〜2.2 秒の上限
