# unmove_prune: 逆向きの生成器で、キャッチ局面になる前任を作る前に捨てる（記録試行ではない）

番号を取らず、`impl/` を作らず、タイムを `results/` にも README の記録表にも載せない。

**工夫は1つだけ入れる。** 逆向きの生成器に「作る前に絞る」だけを足す。「反転を1回にする」や、到達しない候補を減らす工夫は入れない。
キャッチ局面への手は、[`unmove_catch`](../unmove_catch/) の `drop` と同じく残りの後続の数から外したまま（全局面で答えが変わらないことを
確かめた形を土台にする）。

## 目的

作り替えた後退解析の見積もりは、[`attack_count`](../attack_count/) で 94.25 秒になり、いまの P1 ＋ P2 ＋ P4 ＋ 174段ループ（#33 本走、76.70 秒）より
まだ 17.55 秒遅い。残りの大半は `unmove_catch` の `drop` のループ（80.21 秒）、つまり逆向きの生成器そのもの。

`drop` の候補 1,094,348,081 個のうち 31.2%（341,669,361 個）は、**前任の候補がキャッチ局面**（その局面の手番側が、相手のライオンを取れる）という
理由で捨てられている。素朴な生成器は候補を作り、反転・正規化・ランクを済ませ、855 MB の `cls` を引いてから捨てている。
この 31% は候補を作る前に盤を見るだけで分かるので、先に判定して作らずに飛ばす。どれだけ速くなるかを確かめる。

## 考え方

用語: 局面 q（後退解析で決まった局面）の上で、直前に指した側を X、q の手番側を Y とする。前任 p は、q で X の手を1つ戻した局面で、
p の手番は X。

**前任がキャッチ局面になる条件。** いまの生成器（`nextBoardInvNormal`）は p を反転した盤の上で、手番側の駒（9〜13）を動かし、
相手のライオン（`LION1`）のマスへ動ける手があれば 0（キャッチ）を返す。逆向きの生成器では、手を指した直後の盤 nb（q か、その鏡像）から
X の手を1つ戻した盤 b′ を作り、p ＝ `invBoard`(b′) とする（[`unmove_bench`](../unmove_bench/)）。p を反転した盤は b′ そのものなので、
**p がキャッチ局面か ＝ b′ で X の駒（9〜13）が Y のライオン（`LION1`）のマスに利くか**。

「利く」は、いまの生成器の手の規則をそのまま写す（規則の正本は `nextBoardInvNormal`）:

- X の駒 k がマス s から s ＋ m へ（m は移動表の値）。0〜44 の外と、回り込みの2条件（s % 16 ＝ 0 かつ 行き先 % 16 ＝ 12、s % 16 ＝ 12 かつ
  行き先 % 16 ＝ 0）を捨てる
- X のひよこ（`CHICK2`）は s − 4 へ。s % 16 ＝ 0 なら動けない

**なぜ手を戻しても X のほかの駒の利きが変わらないか。** どうぶつしょうぎの駒は、どれも1マスしか動かない（遠くまで利く駒が無い）。
だから、駒が1つ動いても、ほかの駒の利きが遮られたり通ったりすることが無い。X の駒を1つ戻して変わる X の利きは、戻した駒の分
（いたマス d から、戻した先 s へ）だけ。取った駒を盤に戻しても、それは Y の駒なので X の利きは変わらない。Y のライオンは取られていない
（取る手は後続を作らずに 0 を返すので、そういう q は無い）ので、Y のライオンのマスも nb と b′ で同じ。

そこで、nb ごとに1回、**A ＝「Y のライオンのマスに利いている X の駒の、いるマスの集合」**を作る（q で Y にかかっている王手）。

**A は集合につけた記号で、盤の列（A・B・C）とは関係ない。** 言い換えると「q で Y に王手をかけている X の駒が、どのマスにいるか」。
A が空なら q で王手はかかっていない、A が1マスなら王手をかけている駒が1つある、A が2マス以上なら二重の王手。以下「A が1マス」などはこの意味。

| 戻す手 | 前任がキャッチ局面になる条件（作らずに捨てる） |
|---|---|
| X の駒 k を d から s へ戻す（取った駒を戻す・成りを戻す手も） | A から d を除いて空でない、または、s にいる k（成りを戻すならひよこ）が Y のライオンのマスに利く |
| 盤の駒を X の持ち駒に戻す（打った手を戻す） | A から d を除いて空でない |

ここから、局面と駒の単位で先に枝を落とせる。

- **A が2マス以上**: どの戻し方でも A から d を除いて空にならない。nb から前任は1つも出ない
- **A が1マス a**: a 以外のマスにいる駒は、どう戻しても前任にならない。a の駒を戻す手だけを作る（その中でも、戻した先 s から
  Y のライオンに利く戻し方は捨てる）
- **A が空**: どの駒も戻してよい。戻した先 s から Y のライオンに利く戻し方だけを捨てる

**A が2マス以上にならない理由。** 到達する局面は、初期局面と、未知局面（いまの生成器が正の数を返す局面）の後続だけ
（キャッチ局面とトライ負けの局面からは後続を作らない）。未知局面 p はキャッチ局面でないので、p では Y のライオンに利く X の駒が無い。
X が1手指して利きを足せるのは、動かした駒（打った駒）1つだけ。だから後続 q で Y のライオンに利く X の駒は多くても1つ。
初期局面も A は空。したがって全到達局面で A は 0 か 1 マスのはず。出たらどこかの理解が間違っている印なので、数えて報告する。

## 判定の作り（[`prune.c`](prune.c)）

- 表 `g_xatt[k][sq]`: X の駒 k（9〜13）がマス sq にいるとき利くマスの集合（12ビット）。いまの生成器の移動表から最初に1回作る。
  Y の駒と空きは 0。`attack_count` の B1′ と同じ形（向きと持ち主を X 側にした）
- `pruneChecks`: nb の Y のライオンのマス L を `rankFindKoma` で探し、12マスを分岐なしに1周して A を作る
- 絞った版（`unmovePrunedCandidates`）は `unmove.c` の `unmoveRaw` の写しに、次の2つの単位の判定を足したもの。ふるい（正規形・到達・未知）と
  前任の出し方は変えない
  - **局面と駒の単位**: A が2マス以上なら nb から何も作らない。1マスならそのマスの駒だけを戻す（ほかの駒の戻し方に手を付けない）
  - **戻し方の単位**: 戻した先 s の駒が L に利くなら、その戻し方（とそれに取った駒を戻す形）を作らない
- 一致の検査用に、同じ本体から「捨てずに全部作り、候補ごとに捨てる理由を残す」形（`unmoveClassify`）を作る（`always_inline` の本体を
  2つの口から呼ぶ。`attack_count` と同じやり方）
- 試作の後退解析の1段の絞った版（`pruneStep`）は、`catch.c` の `catchStep` の写しで、違いは逆向きの生成器の呼び出しだけ
- `unmove.c`（`unmove_bench`）と `catch.c`（`unmove_catch`）は書き換えずにビルドのときに写して取り込む。素朴な版の関数（`unmoveCandidates`・
  `unmoveSieved`・`unmoveVisit`・`catchStep`）は同じ `.so` の中にそのまま入る

## 一致の検査（[`run_verify.sh`](run_verify.sh)、[`bench.c`](bench.c) の `verify`）

全到達局面（246,803,167）の q ごとに見る。

- **(a)** 分類する版の候補の列が、素朴な版（`unmoveCandidates`）と、戻した手の種類まで順番も同じ
- **(b)** 絞った版の候補の列が、分類する版の「捨てない」候補の列と順番まで同じ
- **(c)** 絞った版の前任の多重集合（`unmovePrunedSieved`）が素朴な版（`unmoveSieved`）と同じ（q ごとに件数とハッシュ2つ。`unmove_bench` の `verify` と同じ形）
- **(d)** 絞った版の候補をふるうと、キャッチ局面を理由に捨てる候補が 0
- **(e)** 絞った版が作らなかった候補の数（素朴な版の候補 − 絞った版の候補）＝ 素朴な版でキャッチ局面を理由に捨てていた候補の数
  （全到達局面と、展開する局面の両方で）
- **(f)** 候補ごとの判定（捨てる・捨てない）が、候補のランクで `cls` を引いた正解（キャッチ局面か）と一致する。食い違いは、戻した手の種類
  （動かした・取った・打った・成った・成って取った）× A の大きさ（0 / 1 / 2以上）× 向き（捨てたが未知などだった / 残したがキャッチ局面だった）で出す

「展開する局面」は、試作の後退解析（`drop`）で展開する局面: 勝敗が決まっていて（`dat/` のファイル名が `unknown*` でない）、キャッチ局面でないもの。
`unmove_catch` の `drop` の「展開した局面」103,821,853 と同じ数になるはず（`verify` が数える）。

## ついでに数えるもの（何も変えない）

`verify` が、全到達局面と展開する局面のそれぞれで出す。

- A の大きさ（0 / 1 / 2以上）ごとの局面の数。q と鏡像の両方で（左右対称で鏡像を作らない q は別に数える）
- 素朴な版でキャッチ局面を理由に捨てていた候補の、捨てる理由ごとの内訳: 「A が2マス以上」「A が1マスで、ほかの駒を戻した」「戻した先から利く」。
  2つ目と3つ目に両方当たる候補は、生成器が先に見る2つ目に数え、重なった数を別に出す
- 戻した手の種類 × A の大きさ（0 / 1）ごとの候補と、そのうちキャッチ局面の数

## 条件

これまでの実験（`unmove_bench`・`unmove_catch`・`attack_count`）と揃えた。

- 入力は #33 本走の `dat/`。`cls.bin` と計時用の抜き出しは `unmove_catch` と同じ作り方・同じシード（20261005）で `runs/unmove_prune/` に作り直す
  （git に入れない。sha256 を `logs/prep.txt` に残す）
- 計時用の抜き出しに、`drop` で展開する種類（未知とトライ負け）から 1,000万局面を抜いた `sample_expand.bin` を足す（同じシードから始めた別の乱数の列）。
  生成器の計時は `unknown`（4,030,968 局面）・`try`（284,396 局面）・`expand` の3列
- `.so` は `impl/33_hot_layout` の `Makefile` の `gcc` 行のまま（入力と出力の名前だけ替えて）ビルドする（[`build_so.sh`](build_so.sh)）。
  ベンチ本体は `dlopen` して呼ぶ（`RTLD_LOCAL`）
- 計時はどの本も `numactl --cpunodebind=0 --membind=0` で固定。`cls`・状態の配列・`dtm`・`cnt` は 2 MiB の区切りで確保して `madvise(MADV_HUGEPAGE)` を頼む。
  先読みは素朴な版と絞った版で同じ（候補のランクで `cls` の行を、残った前任で状態の行を取り寄せる）。周波数の標本と、前後の `thp_fault_fallback` を残す
- 回す前の負荷は load average と CPU 使用率の合計だけを残す

### 測るもの

1. **生成器だけ**（[`run_time.sh`](run_time.sh)）: `unmove_bench` の `cand`・`sieve`・`visit` と同じ3段階を、素朴な版（`ncand`・`nsieve`・`nvisit`）と
   絞った版（`pcand`・`psieve`・`pvisit`）で。6つの版を5周、周ごとに順番を1つずつずらす。1本ずつ別のプロセスで、各列を1周温めてから1周測る
2. **試作の後退解析を丸ごと**（[`run_retreat.sh`](run_retreat.sh)）: `unmove_catch` の `drop` を、素朴な版（`naive`。`catchStep` そのもの）と
   絞った版（`pruned`。`pruneStep`）で入れ替えて、`naive pruned pruned naive naive pruned` の順に3本ずつ。初期化（`drop` と同じ。キャッチ抜きの数は
   B2 で数える）は計時に入れるが、比べるのはループ。毎回、全局面の手数が `dat/` と一致することを確かめる。ループの秒、展開した局面、候補、残った前任を出す

回す順: `run_verify.sh`（準備と一致の検査）→ `run_time.sh` → `run_retreat.sh`。

### 換算

[`summary.py`](summary.py) が出す。

- 作り替えた後退解析の見積もり ＝ 絞った版の試作のループ ＋ B1′ の費用（`attack_count` の `logs/timing.tsv` から同じ計算で、5.08 秒）＋
  全局面の種類と残りの数をランクの配列に書く費用（`unmove_bench` の `logs/timing.tsv` の `degw` から、8.96 秒）
- これを、いまの P1 ＋ P2 ＋ P4 ＋ 174段ループ（`results/33_hot_layout/retreat_summary.tsv` の生値、76.70 秒）と比べる
- `dat/` の形へ書き出す費用は未計測として別に書く

   素朴な版の候補 − 絞った版の候補 ＝ 素朴な版の「キャッチ局面を理由に捨てた候補」

## 比べ方（回す前に決めた）

- 生成器だけ: ns/局面は5周の中央値と範囲。絞った版 − 素朴な版は、段階ごとに同じ周どうしの差を取ってから中央値と範囲
- 試作の後退解析: 版ごとのループの中央値と範囲（3本）。差は並びの隣どうしの組（1-2、4-3、5-6）で取り、中央値と範囲
- 換算は、絞った版の3本それぞれのループで計算して中央値と範囲

### 食い違いの中身（診断。止めたあとに足した）

(c) が通っているので、余計に捨てた候補は未知局面ではない。`cls` は到達局面にしか種類を持たないので、**キャッチ局面の形をしているが到達しない候補は、`cls` では「到達しない」になる**、という読みを確かめるために、診断（`bench diag`、[`run_diag.sh`](run_diag.sh)）を足した。候補そのものをいまの生成器に通し、戻り値が 0（キャッチ局面）かで判定と比べる。結果は [`logs/diag.txt`](logs/diag.txt)（[`logs/console_diag.log`](logs/console_diag.log)）。

- **判定は、生成器の規則に照らして1個も外れていない**: 捨てた候補は全部キャッチ局面の形、残した候補にキャッチ局面の形は1つも無い
- 外れたのは検査 (e)・(f) の正解の取り方。「キャッチ局面か」を `cls` で引いたので、到達しない候補をキャッチ局面と数えなかった。見込みの「作らずに済む候補 ＝ 341,669,361」も同じ見落としで、到達しない候補のうち 173,954,810 個（`drop` の到達しない候補 256,947,768 の 68%）はキャッチ局面の形をしていて、作る前に捨てられる
- その結果、展開する局面の候補は 1,094,348,081 → 578,723,910（−47.1%。見込みは −31.2%）。残った候補のうち到達しない局面で捨てるのは 82,992,958（14.3%。見込みは約 34%）

## 言えないこと

- 換算は試験台の値で、段どうしの重なりは入らない。試作のループ（丸ごと測った値）に、抜き出しで測った B1′ の増分 × 件数と `unmove_bench` の `degw` を足したもの。**−1.92 秒はいまの4段とほぼ並んだというだけで、速くなるとは言えない。** 本当の効果は、記録にするときの門番で測る
- 試作の後退解析は、いまの後退解析と別の作り（ランクを添字にした配列、`dat/` の形への書き出しが無い）。書き出しの費用は未計測
- `naive` の測り直しは `unmove_catch` の値から 2.0% ずれた。ずれの原因（番地か、計測機の日による違いか）は分けていない。比べたのは同じ `.so` の中の隣どうしの組
- 生成器の計時の `expand` は未知（引き分けに終わる局面も含む）とトライ負けから抜いた列で、試作の後退解析が実際に展開する局面（勝敗の決まった局面）とは配分が違う

## 次の工夫の推奨（決めない）

作り替えた後退解析の見積もりは、いまの4段とほぼ並んだ（−1.92 秒）。記録にするには、まだ数秒単位の上積みがほしい。

- **反転を1回にする**（`unmove_bench` が挙げた工夫）: いまの逆向きの生成器は、戻した候補ごとに `invBoard` と `normalBoard` を通し、正規形でない半分ほどを捨てている。q（と鏡像）を先に1回反転して、反転した盤の上で手を戻せば、候補ごとの反転が無くなる。測っていないが、`pcand` が候補1個あたり約 83 ns（461.9 ÷ 5.591。A づくりを含む）で、そのうち反転と正規化の判定が数 ns 〜十数 ns だとすると、展開する局面1つあたり数十 ns、103,821,853 局面で **3〜6 秒前後**の見込み（根拠は浅い。正規形でない戻し方の割合は数えていない）
- **到達しない候補を減らす**: 絞った版では、残った候補 578,723,910 のうち到達しない局面で捨てるのは 82,992,958（14.3%）まで減った（素朴な版の 23.5% のうち 2/3 はキャッチ局面の形で、今回まとめて落ちた）。残りを全部ただで捨てられたとしても、候補1個あたりのふるい（`psieve` − `pcand` 229 ns ÷ 5.591 ≈ 41 ns）× 8,300万 ≈ **3.4 秒が上限**。作る前に見分ける手がかり（盤の形だけで分かる到達しない理由）は、まだ調べていない
- ほかに思いついたこと（入れていない）: A の作り方を、A が空の局面で「戻した先から利く」を表で引く形から、Y のライオンのまわりのマスの集合との論理積でまとめて落とす形にする（戻し方ごとの判定を局面ごとに1回にする）
